# ADR 0013 · Bounded PE parser for game executables

**Status:** accepted · 2026-11-05 · extends ADR 0004, ADR 0007, ADR 0011, ADR 0012 (`RawText`); amends ADR 0008 (amendment 2026-11-05, DLL hardening: the tests use `detect::pe`)

## Context
Phase 1 step 13 reads facts from executables: architecture, the imported DLLs (step 14 maps them to the Topo `api` values `ddraw`, `d3d8`, `d3d9`, `d3d10`, `d3d11`, `opengl`), the Large Address Aware flag, the subsystem and the version resource. Step 14 chooses the exe candidates of a game folder, maps imports to an API and hashes (`--hashes` only); step 13 only parses one given file.

Executables in game folders are untrusted input: any process of the user can replace or plant them (Steam grants `Users` full control, ADR 0007). They can be large (modern shipping and DRM-wrapped executables reach hundreds of MiB), truncated, or crafted to make a parser loop, recurse, allocate by header-supplied sizes or panic. Old games add old formats (DOS `MZ`, Win16 `NE`, `LE`/`LX`) and old toolchains (VC6 delay-load descriptors with virtual addresses, Borland/Delphi version resources with inconsistent length fields).

The same reader also replaces `tests/support/pe_min.rs`, the minimal PE32+ reader of the DLL hardening tests (ADR 0008): `DependentLoadFlags` of the load config, the static and delay-load import DLL names.

The plan so far was the `object` crate (0.40) plus an own VS_VERSIONINFO parser.

## Decision

### User decisions (2026-11-05)
1. **Own parser** with bounded range reads over `Read + Seek`, not the `object` crate (see Alternatives). No new runtime dependency: `std` and `thiserror` only.
2. **`rerun-launch` gets `rerun-core` as a dev-dependency only** (its hardening test); its normal dependencies stay `windows-sys` and `rerun-proto` (see "Hardening tests").
3. **Partial results:** a broken version resource does not hide headers and imports (`PeInfo::version` is a `Result`); a broken import table fails the file. "Broken" means a format error of the file; reading errors (`Io`, `ReadBudget`) are no property of the file and fail `Pe::info` also in the version part (security review of step 13, S1).
4. **Tolerant VS_VERSIONINFO** for the quirks of Borland/Delphi and other old toolchains, as below: `wValueLength` of string blocks ignored, missing padding tolerated, a broken fixed part is `None`; resource language neutral, then en-US, then the lowest; string table by `Translation[0]`, then `0409`, then the first; six kept keys.
5. **DLL names only** (no function names, ordinals, exports or forwarders) until phase 6; DOS, NE and LE/LX executables are recognised as `Legacy`.
6. **Manual read-only dumps** on the developer machine: `dump_system32_pe` and `dump_game_exes` (`#[ignore]`, see Consequences). They write nothing, print names only escaped, never run in CI, and their output is never committed.

### Layers
- `detect::pe` is a parser over `Read + Seek`: `Pe::parse(reader, &Limits)` reads the headers, everything else is read on demand by range (`imports`, `delay_imports`, `dependent_load_flags`, `version_info`, `info`). No dependency beyond `std` and `thiserror`, no `unsafe`, no recursion, no `sys` method. Tests use `std::io::Cursor`, the hardening tests a `std::fs::File` of the built binary.
- `detect::pe::open_game_exe(&GameDir, &RelPath, &Limits)` is the only reader for product code: `Dir::open_read` relative to the game handle (ADR 0007: never by absolute path, never through a reparse point, a restricted entry or an online-only cloud placeholder), then `Pe::parse`; it returns a `GameExe<'_>` (`Pe` over the boxed `ReadSeek` of the handle). The file length is never asked for (not from metadata, not by seeking to the end). Detection never takes a bare `&dyn Dir` (ADR 0007); a private helper on `&dyn Dir` exists only so the bound can be tested with a reader that never ends (as in ADR 0011).
- `Pe::into_inner` hands the reader back, so step 14 can hash the same handle it parsed (no second open, no swap between parse and hash).
- `RawText` moves from `detect::steam::text` to `detect::text` (re-exported from `detect::steam`); version strings are `RawText`.

### Reading
- No memory mapping and no whole-file read. Every access is one bounded range read at a file offset (`seek` + `read`), into a buffer whose size comes from a limit, never from a header field alone. A total read budget per `Pe` (`max_read_bytes`) is charged before each read; exceeding it is `ReadBudget`. All structures together stay far below the budget (worst case of every limit below: about 0.7 MiB), so the budget is a second, independently testable bound.
- A short read at end of file is `Truncated` where a structure must be complete; name reads accept a short read and look for the NUL in what came back.
- I/O errors keep only their `std::io::ErrorKind`.

### What is parsed
- **DOS and NT headers.** `MZ` required (else `NotExecutable`). `e_lfanew` at 0x3C; the four bytes there decide: `PE\0\0` is a PE, `NE` is `Legacy(Ne)`, `LE`/`LX` is `Legacy(Le)`, anything else, or an `e_lfanew` beyond the header region or the file, is `Legacy(Dos)`. The NT headers and the section table must lie within the header region (first `max_header_bytes`).
- **Optional header.** Magic `0x10B` is PE32, `0x20B` is PE32+, anything else `UnknownOptionalMagic`. `SizeOfOptionalHeader` must cover the fixed part (96 or 112 bytes) plus the data directories read; `NumberOfRvaAndSizes` above 16 counts as 16. Kept: `ImageBase`, `Subsystem`, `DllCharacteristics`, `SizeOfHeaders`, the data directories.
- **Machine.** `0x14C` is `X86` and must be PE32; `0x8664` is `X64` and `0xAA64` is `Arm64`, both must be PE32+; a mismatch is `MachineMismatch`. Other machines are `Other(raw)` with whatever magic they have. ARM64EC images report `X64` (their COFF machine), ARM64X images `Arm64`.
- **Flags.** `Characteristics` raw, with `large_address_aware()` (`0x0020`) and `is_dll()` (`0x2000`). The flag is reported for every machine; whether it matters (x86 only) is decided above `detect::pe`.
- **Managed.** `managed` is true when data directory 14 (CLR runtime header) has a non-zero RVA and size; the header itself is not read.
- **RVA mapping.** A section covers `[VirtualAddress, VirtualAddress + extent)` with `extent = VirtualSize`, or `SizeOfRawData` when `VirtualSize` is 0; the file-backed part is the first `min(extent, SizeOfRawData)` bytes from `PointerToRawData`. The first matching section in table order wins. An RVA below `SizeOfHeaders` maps to the same file offset. An RVA in no section is `RvaNotMapped`, one past the file-backed part `RvaNotBacked`. Deliberate deviation from the loader: `PointerToRawData` is not rounded down to 512 and `FileAlignment`/`SectionAlignment` are not enforced, so a crafted file can show different facts than the loader would see; nothing in Rerun authorizes anything on PE content (see Consequences).
- **Imports.** DLL names only, from the import directory (`IMAGE_IMPORT_DESCRIPTOR`, 20 bytes, `Name` at 12) and the delay-import directory (`IMAGE_DELAYLOAD_DESCRIPTOR`, 32 bytes, `DllNameRVA` at 4), in table order, until an all-zero descriptor. Descriptors are read in one range of at most `(max_import_dlls + 1) × stride` bytes; no terminator within the limit is `TooManyImports`, the end of the file-backed data before it `ImportsNotTerminated`. A delay descriptor whose `Attributes` bit 0 is clear (VC6 style) holds virtual addresses: `ImageBase` is subtracted, an address below it is `RvaNotMapped`. The terminator is deliberately stricter than the loader, which stops at a descriptor whose `Name` or `FirstThunk` is 0 (delay-load: `DllNameRVA` 0): a table with such a descriptor before an all-zero one reads further and may end in `BadDllName` or `ImportsNotTerminated`. The developer-machine dumps (amendment below) showed no such case; revisit if step 14 or 17 sees these errors on real games. No thunks, no function names, no ordinals, no exports or forwarders, no bound imports (not needed to name the graphics API; phase 6 may add function names). A data directory counts as present when its `VirtualAddress` is not 0 and lies within `NumberOfRvaAndSizes`; its `Size` is not used (only the CLR check above requires it). Error offsets: the directory entry for an unmapped directory RVA, the table start for `TooManyImports`, `ImportsNotTerminated` and a table cut by the end of the file (`Truncated`), the descriptor for an unmapped or unbacked name address, the name itself for `BadDllName`.
- **DLL names.** 1 to 255 bytes, every byte printable ASCII (`0x20` to `0x7E`), NUL-terminated within 256 bytes, else `BadDllName`. A `DllName` keeps the spelling and compares ASCII case-insensitively; it is safe to print (no control, bidi or non-ASCII character can pass).
- **Load config.** `DependentLoadFlags` at `0x4E` (`IMAGE_LOAD_CONFIG_DIRECTORY64`) or `0x36` (`…32`), `None` without a load config or if its `Size` field does not reach the field.
- **Version resource.** Fixed depth, no tree walk: in the root table of the resource directory the ID entry `16` (`RT_VERSION`); in its table the ID entry `1`, else the lowest ID; in that table the language `0x0000`, else `0x0409`, else the lowest ID. Levels 1 and 2 must be directories and level 3 a data entry (`BadResourceTree`). Named entries are skipped. Table offsets are relative to the resource directory RVA, the data entry's `OffsetToData` is an RVA. Each table read is `16 + 8 × entries` bytes (the 16-byte header, then the entries) with at most `max_resource_entries` entries, named ones counted; a table or the data entry not complete within the file-backed data is `Truncated`. Among equal IDs the first wins. The resource data is read with `min(Size, max_version_bytes)` bytes, clamped to the file-backed data and accepting a short read at the end of the file (the parser clamps every block to what is there; a `Size` of 0 leaves nothing and is `BadVersionBlock`). No `RT_VERSION`, no matching entry: `Ok(None)`.
- **VS_VERSIONINFO** (own parser over the at most 64 KiB read): blocks of `wLength`, `wValueLength`, `wType`, a NUL-terminated UTF-16 key, padding to 4 bytes relative to the start of the root block, the value, then children. An explicit loop over at most four levels (root, `StringFileInfo`/`VarFileInfo`, string table, string), no recursion. A block's extent is `wLength`, clamped to what is left of its parent; `wLength` below 6 is `BadVersionBlock` (every block consumes at least 8 bytes, so the loop always progresses). Root key `VS_VERSION_INFO` (else `BadVersionBlock`). Fixed part: `VS_FIXEDFILEINFO` (52 bytes) is kept only if `wValueLength` is 52 and the signature is `0xFEEF04BD`; otherwise `fixed` is `None` and parsing goes on. Tolerated quirks of old toolchains: `wValueLength` of string blocks is ignored (in words by the specification, in bytes by some writers); a string value runs from the aligned end of its key to the first NUL or the end of its block; missing trailing padding. String table keys are 8 hex digits (`lang` + `codepage`); a table with another key is skipped. Chosen table: the one matching the first `Translation` pair of `VarFileInfo`, else the first with language `0x0409`, else the first. Kept keys (compared ASCII case-insensitively, first occurrence wins): `CompanyName`, `FileDescription`, `FileVersion`, `OriginalFilename`, `ProductName`, `ProductVersion`; other keys are skipped without decoding. Details fixed in the implementation: every key (also `VS_VERSION_INFO`, `StringFileInfo`, `VarFileInfo`, `Translation`) compares ASCII case-insensitively and the hex digits of a table key in either case; the children of the root start after `wValueLength` bytes of its value, those of `StringFileInfo`, `VarFileInfo` and a string table at the aligned end of their key (their `wValueLength` is ignored, it is 0 by the specification); the first `Translation` pair is read when 4 bytes of value lie within its block; every child of `StringFileInfo` counts towards `max_string_tables`, whatever its key; blocks under other keys are skipped whole, never looked into; trailing bytes of a parent too short for a block header are padding. Error offsets are file offsets of the offending block. A kept value over `max_version_string` UTF-16 units is `StringTooLong`; unpaired surrogates become U+FFFD; nothing else is changed (output layers sanitize, step 16).
- **Not parsed:** overlay and installer signatures, Authenticode, Rich header, exports, TLS, relocations, debug directory, checksum, timestamps.

### Limits
`Limits` with the single constant `Limits::DEFAULT`; tests pass smaller ones. A value of exactly the limit is accepted, one more is an error.

| Limit | Value | Reason |
|---|---|---|
| header region (`max_header_bytes`) | 64 KiB | DOS header, NT headers and section table; real `e_lfanew` is 0x40 to 0x200, a table of 96 sections is 3,840 bytes |
| sections (`max_sections`) | 96 | the Windows loader's own limit |
| data directories | first 16 | `NumberOfRvaAndSizes` above 16 is ignored |
| import DLLs per table (`max_import_dlls`) | 1,024 (static and delay each) | real executables import 5 to 80 DLLs |
| DLL name (`max_name_bytes`) | 255 bytes + NUL | longest DLL file name Windows accepts |
| resource entries per table (`max_resource_entries`) | 1,024 | only the three tables of the `RT_VERSION` branch are read |
| version resource (`max_version_bytes`) | 65,536 bytes read | `wLength` of the root block is a `u16` |
| kept version string (`max_version_string`) | 1,024 UTF-16 units | real values are below 256 |
| string tables (`max_string_tables`) | 64 | real files have 1 or 2 |
| total bytes read per `Pe` (`max_read_bytes`) | 1 MiB | worst case of every limit above is about 0.7 MiB; at most about 2,060 reads |

### Errors
`PeError { kind: PeErrorKind, offset: Option<u64> }` with the file offset of the offending structure and a `#[non_exhaustive] PeErrorKind`: `Io(std::io::ErrorKind)`, `NotExecutable`, `Legacy(LegacyFormat)` (`Dos`, `Ne`, `Le`), `Truncated`, `HeadersOutOfRange`, `UnknownOptionalMagic`, `BadOptionalHeaderSize`, `MachineMismatch`, `TooManySections`, `RvaNotMapped`, `RvaNotBacked`, `TooManyImports`, `ImportsNotTerminated`, `BadDllName`, `BadResourceTree`, `TooManyResourceEntries`, `BadVersionBlock`, `StringTooLong`, `TooManyStringTables`, `ReadBudget`. Errors never contain file content: no names, no strings, no header values. `PeReadError` (`Open { file, source: SysError }`, `Parse { file, error }`) adds the `RelPath`.

`Pe::info` returns `PeInfo { headers, imports, delay_imports, version: Result<Option<VersionInfo>, PeError> }`: a malformed version resource does not hide the architecture and imports; a malformed import table fails `info` (the loader would refuse such an image), and so does a reading error (`Io`, `ReadBudget`) anywhere, also in the version part: only format errors of the version resource land in `version`. `PeReadError::Open` shows the message of the system layer only (its target already names the file, escaped); `PeReadError::Parse` shows the `RelPath`, which needs no escaping (`RelPath` refuses every character `shown_target` would escape, pinned by a test).

### Layout constants
Offsets and constants are written out from `winnt.h`/`verrsrc.h` (SDK 10.0.26100) in `detect::pe::layout` and pinned by a Windows-only test against the `windows-sys` structures and constants (`offset_of!`, `size_of`), through dev-dependency features only, like the CPU parser (ADR 0010). The shipped feature set of `windows-sys` does not change. `windows-sys` 0.61.2 has the structures behind `Win32_System_Diagnostics_Debug` (file and optional headers, sections, data directories, load config), `Win32_System_SystemServices` (DOS header, import descriptor, resource directory, signatures, language IDs), `Win32_System_WindowsProgramming` (delay-load descriptor), `Win32_Storage_FileSystem` (`VS_FIXEDFILEINFO`, normal feature), `Win32_System_SystemInformation` (machine constants, normal feature) and `Win32_UI_WindowsAndMessaging` (`RT_VERSION`, already a dev feature): three new dev features, `Win32_System_Diagnostics_Debug`, `Win32_System_SystemServices` and `Win32_System_WindowsProgramming` (correction in the implementation: the existing dev feature is `Wdk_System_SystemServices`, not `Win32_System_SystemServices`). `IMAGE_FILE_HEADER` and the NT headers need `Win32_System_SystemInformation`, a normal feature already. `LX` and the delay-load `RvaBased` bit have no SDK constant and are pinned as literals. Workspace MSRV is 1.99 (`rust-version`, toolchain 1.99.1); the parser uses nothing newer than `offset_of!` on nested fields (1.82).

### Hardening tests
`tests/support/pe_min.rs` is removed. `tests/support/hardening.rs` (included with `#[path]` as before) keeps only the test policy: `SEARCH_SYSTEM32`, `forbidden_import`, `SHIPPED_IMPORTS`, `check_imports`, `check_hardened` (PE32+ for the native machine, x64 in CI, as `pe_min.rs` required), now on `rerun_core::detect::pe::Pe` over a `std::fs::File` of `CARGO_BIN_EXE_*` (or `current_exe`). Reading the test's own build output by path is test code under the existing `#![expect(clippy::disallowed_methods)]`; ADR 0007 governs product code and untrusted folders. `rerun-launch` gets `rerun-core` as a **dev-dependency** only: its normal dependencies stay `windows-sys` and `rerun-proto` (the CI check uses `cargo tree -e normal`), and the size check builds the binary with `-p`, without dev-dependencies. Because the test-profile binary is linked with the features of the test build, CI builds the release shim first and the same hardening test checks it too (`RERUN_RELEASE_LAUNCH_EXE`; required on GitHub-hosted runners, skipped locally when unset).

## Alternatives
- **`object` 0.40** (gimli-rs, Apache-2.0 OR MIT, used by the standard library's backtraces, with `default-features = false` and `read_core` + `coff` + `pe`). Rejected for this use, not for quality: its PE reader works on a `ReadRef`, i.e. the whole file in memory (`&[u8]`) or its `ReadCache`, which allocates and caches ranges of the sizes the headers ask for. Bounded range reads would mean either reading each containing section whole (an `.rdata` or `.rsrc` of tens of MiB) and feeding `ImportTable::new`/`ResourceDirectory::new` per section, or an own `ReadRef` with interior caching, which needs `unsafe` or another crate to hand out borrowed slices. Its iterators are bounded only by the data length, not by counts, and it has no VS_VERSIONINFO, no DLL-name rules and no read budget, so every limit and every hard part would be ours anyway. What it would save (header structures, descriptor iteration, one resource level) is the small part; it would add a dependency (plus `memchr`) with a breaking minor release several times a year. If chosen after all, the public API, limits, errors and tests of this ADR stay as they are; only the internals and `Cargo.toml` change, and its MSRV, its feature set and `cargo tree` must be checked in the commit.
- **Whole file into memory with a cap** (as ADR 0011 does for VDF). Rejected: either the cap refuses modern shipping executables, or it reads hundreds of MiB per candidate during a scan.
- **Memory mapping** (`memmap2`): needs `unsafe` and a dependency, `Dir` exposes no handle, and another process can change a mapped user-writable file while it is read.
- **Strict version parsing** (refuse inconsistent `wValueLength`, missing padding): rejects valid resources of old toolchains, the games Rerun is for.
- **Function names, ordinals and exports now:** not needed to name the graphics API; more untrusted data to bound. Phase 6 (heuristic) may add them.
- **Overlay and installer detection:** step 14 filters candidates by name, version strings and subsystem first; added only if the acceptance on the developer machine shows the need.

## Consequences
- PE facts are hints for display, matching and suggestions, never authorization: a Topo matches an exe by path and hash (`docs/02-topo-format.md`), the elevated helper (phase 3) by the signed hash, and `laa_patch` (later) re-reads the file it changes and checks its hash at apply time.
- An exe that is missing, a reparse point, restricted, online-only or busy (Steam updating it) is a `PeReadError::Open`; a running game's exe can be read (shared read access).
- Packed or DRM-wrapped executables (UPX, SteamStub, Denuvo) show the stub's imports, not the game's; step 14 reports the API as unknown for them rather than guessing. Games that load their renderer from a DLL (`D3DDrv.dll`) or with `LoadLibrary` show no graphics import in the exe; step 14 handles that (ADR 0014: `None`, `RendererInDll`, `DxgiOnly`).
- DOS and Win16 games are recognised (`Legacy`), which step 14 can report as "needs DOSBox / not runnable on 64-bit Windows" instead of an error (ADR 0014: role `Legacy`).
- Tests: `docs/09-testing.md`, "PE parser": synthetic executables from a test-only builder (`detect/pe/testfx.rs`), every limit at and over the limit, every error kind with its offset, deterministic xorshift fuzzing, a reader that never ends and an instrumented reader for the budget, the layout pin, read-only smoke tests on System32 and SysWOW64 files (`kernel32.dll`, `ntdll.dll`, `notepad.exe`; `crates/rerun-core/tests/pe_system.rs`), and the migrated hardening tests. No differential test against `GetFileVersionInfoExW`: it would need `unsafe` and a `version.dll` import outside `sys::win`.
- Manual dumps (user decision 6, Windows only, `#[ignore]`): `dump_system32_pe` parses every top-level `*.exe` and `*.dll` of System32 and SysWOW64 and prints a summary per error kind; `dump_game_exes` runs `steam::scan`, opens every game folder with `open_game` and parses each top-level `*.exe` through `open_game_exe`. Both read only, print names escaped (`{:?}`) and version strings only as their length, and are never run in CI.
- `docs/06-security.md` gets scenario 13 (manipulated executables).
- Step 14 builds on this parser: exe candidates of a game folder, roles, ranking, the graphics API from the imports and the hashes on the parsed handle are ADR 0014.

## Amendment 2026-11-05: developer machine

The two manual dumps on the developer machine (Windows 11 build 26300, read-only, output not committed):

- `dump_system32_pe`: System32 4,404 files (4,281 x64 with a version resource, 84 x64 without, 39 x86), SysWOW64 2,735 files (2,708 x86 with a version resource, 19 x86 without, 2 x64, and 6 16-bit NE DLLs, correctly `Legacy(Ne)`); 0 parse errors and 0 version errors; at most 178,552 bytes read for one file (budget 1 MiB); 3.7 s and 2.1 s.
- `dump_game_exes`: 2 libraries, 43 top-level game executables, 0 parse errors (24 x64, 19 x86; 12 without a version resource; one .NET launcher detected as managed; the Large Address Aware flag seen on x86 and x64 images); 218 ms. Import lists with several `KERNEL32.dll` descriptors (duplicate descriptors) occur and parse as they are; step 14 de-duplicates if it needs to.
- No import table needed the loader's looser terminator rule (see "Imports").
- Finding for step 14 (exe candidates): 9 of the 33 game folders have no executable at the top level; their binaries lie in subfolders such as `Binaries\Win64`. Candidate selection must look below the top level (bounded depth and count), not only at `*.exe` in the game folder.
