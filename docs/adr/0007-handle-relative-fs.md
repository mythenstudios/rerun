# ADR 0007 · File operations relative to a root handle

**Status:** accepted · 2026-11-04 · replaces the `Fs` signatures of ADR 0004

## Context
The Phase 0 security review (finding 3) showed that `sys::Fs` took an absolute `&Path` per call. The check ("no reparse point in the path") and the operation resolve the path separately (TOCTOU). If a game folder is writable by the user, malware in the user context can replace a subfolder with a junction to `C:\Windows\System32` between the check and the write. If the write is done by the elevated helper, that is an elevated arbitrary file write (scenarios 4 and 7 in `06-security.md`).

This is the normal case, not an edge case: Steam grants `Users` full control on `C:\Program Files (x86)\Steam`, so `steamapps\common` is user-writable by default.

At the same time, legitimate libraries reached through junctions (a moved library) and data-transforming reparse points inside game folders (CompactGUI/WOF compression, dedup, OneDrive placeholders) must keep working.

## Decision

### One handle-based file API
- `Fs` keeps exactly one absolute operation: `open_dir(&Path) -> Box<dyn Dir>`. It follows reparse points in the given path, opens the directory and canonicalizes it.
- Every other file operation lives on `Dir` and takes a `&RelPath` (never empty, never absolute). `Dir::open_dir(&RelPath)` opens a subdirectory *relative* to the handle without following reparse points. There is no way to address a file in a root by an absolute path.
- The same API is used for game folders, the Steam folder and Rerun's own folder (`%LOCALAPPDATA%\Rerun`), so there is one set of safe semantics and one contract.
- `Dir::info()` returns `RootInfo`: canonical path, volume serial, 128-bit file ID, file system flags and whether the current (non-elevated) user can write it.
- `Dir::open_read` returns `Read + Seek` (needed for PE parsing).

### Only policy hands out roots
- `policy::root` wraps `Dir` in purpose-specific types (`StoreDir`, `GameDir`, later `AppDir`). Only policy can construct them. Detection and primitives take these types, never `&dyn Dir`. `Fs::open_dir` is listed in `clippy.toml` `disallowed-methods`; exceptions only in `policy::root` and `sys::snapshot`.
- **Who may follow a reparse point at the root:** only *store roots* (the Steam folder and its libraries, from the registry and `libraryfolders.vdf`) are opened by absolute path and may be reached through a junction (moved library). **A `GameDir` is never opened by absolute path.** It is opened from its `StoreDir` handle-relative (`steamapps\common\<installdir>`), so a junction at the game folder level is reported as an anomaly and never becomes a root. Otherwise same-user malware could turn `common\GameX` into a junction to an admin-only folder of its choice (review finding H1).
- Before handing out a root, policy validates the **canonical** path again (`RootPath`) and rejects:
  - network paths (`\\?\UNC\…`) and volumes without a drive letter (v1),
  - the root equal to or inside: `%windir%`, `%ProgramFiles%\WindowsApps`, `%ProgramFiles%\Common Files` and its x86 counterpart, `%ProgramFiles%\Windows Defender`, `%ProgramData%\Microsoft`, Rerun's own install folder, `%LOCALAPPDATA%\Rerun` (for game roots), other users' profiles, in the own profile `AppData\Roaming\Microsoft`, `AppData\Local\Microsoft`, `AppData\Local\Packages`, `AppData\Local\VirtualStore`, and on every volume `$Recycle.Bin`, `$*`, `System Volume Information`, `Recovery`, `Boot`, `Windows.old`,
  - the root equal to or an ancestor of: any volume root, `%ProgramFiles%`, `%ProgramFiles(x86)%`, `%ProgramData%`, the profiles folder, the own profile. Folders *inside* those stay allowed unless listed above.
- **The forbidden folders never come from environment variables** (`windir` and others can be overridden per user and are inherited by the helper). They are resolved with `GetSystemWindowsDirectoryW` and `SHGetKnownFolderPath` (machine-wide known folders) and canonicalized with the same open + final-path routine as the root. Comparison is component-wise and case-insensitive (`C:\Windows` does not match `C:\WindowsApps`) (review finding H3).
- `GameRoot::join` (absolute path out of a root) is removed.
- **Root identity:** the plan stores volume serial and file ID of each root. Every apply and revert, elevated or not, reopens the root and aborts on a mismatch (review finding M5). The preview always shows the canonical path.

### Reparse points below a root
- Each component is opened relative to its parent handle. *Name-surrogate* tags (junction, mount point, symlink, LX symlink) are reported as `EntryKind::Reparse` and never traversed; operations through them fail with `ReparsePoint`. Deleting the link itself is allowed.
- *Non-surrogate* tags on an allowlist (WOF, dedup, cloud files) are treated as normal files and directories, with the tag in the metadata. Unknown tags are rejected (this also covers AppExecLink and ProjFS).
- For data access to an allowlisted tagged file, the entry is reopened relative to the same parent **without** `FILE_OPEN_REPARSE_POINT` (disposition `FILE_OPEN` only, `OBJ_DONT_REPARSE`), and volume serial and file ID must equal those of the first open. Such files are only ever replaced, never written in place; cloud placeholders are never touched elevated and are not hashed during a scan if that would trigger a download (review finding M4).

### Other rules
- **Hard links:** files with more than one link are never changed in place (`SysErrorKind::Linked`); the link count is checked on the write handle. Unlinking and replacing the directory entry are allowed.
- **Replace:** create a temp file next to the target (`FILE_CREATE`, share mode 0, handle kept open until the rename; name supplied by the journal so it is known before creation), write, flush. Rename the old file by its handle to a journal-named `.old` entry, rename the temp file onto the target without `REPLACE_IF_EXISTS`, delete `.old` by handle. All renames by handle with the parent handle as root and a single-segment name. Hash check and backup of the old file happen on a handle without write sharing (review finding L3).
- **Revert:** the hash check and the delete happen on the same handle (review finding L4).
- **Invalid names:** `read_dir` returns raw names. `policy::path::classify` turns each into a valid segment or an anomaly (`d3d9.dll.`, `CON`, `x `, `~1`-style short names, invalid UTF-16, entries in case-sensitive directories). Anomalies are reported and never touched. After every open, the long name (`FileNameInformation`) must equal the requested segment, so 8.3 short names cannot be used to reach another entry (review finding L1). Writes in case-sensitive directories are refused (L2).
- **Packages copied from Rerun's cache** (user-writable): the source is opened with read sharing only, hashed while it is streamed into the temp file, and compared with the pinned SHA-256 before the rename (review finding M2).

### Elevation
- User-writable roots are always changed non-elevated. A non-elevated `AccessDenied` (Controlled Folder Access, TrustedInstaller-owned files) never escalates automatically; the step is rolled back and reported.
- The elevated helper treats the whole plan as untrusted:
  - It computes "only admins can write" itself from the security descriptor of every directory it writes into (no ACE granting write, delete, `WRITE_DAC` or `WRITE_OWNER` to any SID other than SYSTEM, Administrators or TrustedInstaller; owner one of those) and refuses otherwise. This also settles over-the-shoulder elevation (review finding M1).
  - It only writes into a root that contains the topo's target exe with the hash from the signed topo, verified by the helper on an open handle. No exe hash, no elevated apply.
  - It verifies the index signature and package hashes itself, never from bytes in the plan.
  - It opens its root by volume GUID path plus file ID (`NtCreateFile` with `FILE_OPEN_BY_FILE_ID`, not `CreateFileW`/`OpenFileById`, which need backup semantics for directories) and checks that the object is a directory and not a surrogate.
- The plan hash only catches accidents; the helper's own re-validation is the security boundary. Hardening of the helper process itself: ADR 0008.

### Implementation (`sys::win`)
- `NtCreateFile` with `OBJECT_ATTRIBUTES.RootDirectory` = parent handle and a single-segment name, `OBJ_CASE_INSENSITIVE | OBJ_DONT_REPARSE`, `FILE_OPEN_REPARSE_POINT`, `SYNCHRONIZE` + `FILE_SYNCHRONOUS_IO_NONALERT`. `FILE_DIRECTORY_FILE` for intermediate components, `FILE_NON_DIRECTORY_FILE` for files. Dispositions only `FILE_OPEN` and `FILE_CREATE`.
- `sys::win` re-asserts at this boundary that a name is a single segment (no `\`, `/`, `:`, NUL, `.`, `..`).
- After each open the tag is checked via `FileAttributeTagInfo`; this check on the same handle is the primary guard, `OBJ_DONT_REPARSE` the second layer.
- Rename, delete and attributes by handle (`SetFileInformationByHandle` with `FileRenameInfoEx`, `FileDispositionInfoEx`, `FileBasicInfo`). Path-based APIs (`DeleteFileW`, `MoveFileExW`, `ReplaceFileW`) are not used. Never `FILE_OPEN_FOR_BACKUP_INTENT`.

### Fake
- `sys::fake` models the file system as a node arena; a handle is a node ID, so a handle stays valid when its parent is renamed, like on NTFS.
- Test-only hooks run between two path components of an operation, so a test can swap a directory for a junction in the middle of an operation (TOCTOU test). The same scenarios run as contract tests against `sys::win`. The `fake` feature and its hooks never reach release builds (CI check).

### Requirements for later steps (from the implementation review)
- **Before `sys::win` is merged:** the file system contract must be able to tell a safe implementation from a check-then-use-by-path one. Either a deterministic pause point in the Windows fixture (an oplock on an intermediate directory) with the fake's mid-walk swap scenarios ported to it, or a stress race contract (a thread flips a directory between real directory and junction while the operations run; the canary must never change). Path-based Win32 file APIs (`CreateFileW` with a path, `DeleteFileW`, `MoveFileExW`, `ReplaceFileW`, `CopyFile*`, `GetFileAttributesW` …) are listed in `disallowed-methods` for `sys::win`. `replace` re-checks `FileNameInformation` on the held handle before each rename phase. In case-sensitive directories, `sys::win` refuses before looking up the entry.
- **With `policy::root`:** `Fs::open_dir` and the absolute `std` read APIs (`std::fs::read`, `read_to_string`, `read_dir`, `metadata`, `symlink_metadata`, `canonicalize`, `File::open`, `Path::{exists, is_file, is_dir, metadata, read_dir, canonicalize}`) are listed in `disallowed-methods`; a CI check ensures the `fake` feature of `rerun-core` never reaches release builds.
- Folding differences between Rust's `to_uppercase` and the NTFS upcase table (`ſ`, `ı`, Georgian) are checked by contract cases against real NTFS; longer term a pinned upcase table.

## Consequences
- The Phase 0 `Fs` trait, the fake file system, the contract tests and the snapshot are rewritten before any primitive depends on them.
- Each operation opens O(depth) handles; fine for game folders, measured before large hashing jobs.
- Manually added game folders (not from a store) are opened by absolute path like a store root and are therefore never written by the elevated helper unless the exe-hash rule above holds.
- Some Win32 details (since which build `OBJ_DONT_REPARSE` applies to file system reparse points, how WOF and cloud files behave when opened with `FILE_OPEN_REPARSE_POINT`) are settled by contract tests on real Windows (including "hash of a WOF-compressed file equals the hash of an uncompressed copy"); the design does not depend on them.
- Open for Phase 2: a `UserData` root kind for INI files under the user profile (must respect the forbidden folders above); `verify` warns about UAC VirtualStore shadow copies of managed files. **Rescheduled 2026-11-05** (see the amendment "phase 2 plan" below).

## Amendment · 2026-11-04 (`policy::root`)
Points the decision above leaves open, settled before `policy::root` is implemented:
- **A root must not contain a protected folder either.** A root handle gives relative access to everything below it, so a root that is an ancestor of `%windir%` (relocated), Rerun's install folder or any other "equal or inside" entry above is as dangerous as a root inside it. Every "equal or inside" entry is therefore also forbidden as "ancestor of". The "equal or ancestor" entries (`%ProgramFiles%`, profiles, …) keep allowing folders inside them.
- **Volume roots that are not drive roots.** `RootPath` rejects `X:\` lexically, but a volume mounted in a folder (no drive letter) has a canonical path such as `D:\Mounts\Data`. `RootInfo` therefore reports `volume_root: bool`, a fact about the handle (`sys::win`: `FileNameInformation` on the handle is `\`). Policy rejects every root whose handle is a volume root. "Ancestor of a volume root" needs no extra check: a mount point below a root is a name surrogate and is never traversed.
- **Resolving the forbidden list fails closed.** Each forbidden folder is kept in every valid form: lexical (`RootPath::new` of the raw known-folder path) and canonical (open + final path). If a known folder cannot be resolved, its open fails with anything other than `NotFound`, or it has no valid form, policy hands out no root at all. `NotFound` on open keeps the lexical form only (a missing folder cannot contain an existing root). Entries one segment below a known folder (`WindowsApps`, `Windows Defender`, `Microsoft`, `Packages`, `VirtualStore`, `Rerun`) are derived from every form of their parent and never opened (a standard user cannot open `WindowsApps`). A `RoamingAppData` on a network path is never opened (no SMB connection) and its derived entry is skipped: a drive-letter root cannot lie on a share, mapped drives canonicalize to `\\?\UNC\…` and are rejected. Rerun's own install folder is passed in by the caller (its image directory) and must open; otherwise fail closed.
- **More entries** (defense in depth): `%ProgramFiles(x86)%\Windows Defender` (equal or inside); on every volume `Config.Msi` and the Microsoft Store / Game Pass folders `WindowsApps`, `WpSystem`, `WUDownloadCache` (like `$Recycle.Bin`).
- `C:\Users\Public` and `C:\Users\Default` count as other users' profiles and stay forbidden in v1, even though some old installers default to `Public\Games`.
- The own-profile exemption (the only rule that *allows*) compares non-ASCII characters exactly, so a folding difference to the NTFS upcase table can only forbid more, never allow another user's profile.
- **Accepted limit:** other users' profiles are recognised only inside `FOLDERID_UserProfiles`. A single profile relocated elsewhere (`ProfileList\<SID>\ProfileImagePath`) is not on the list; the standard user usually cannot write there, and the elevated helper's ACL rule refuses it. Revisit if the registry is read for other reasons.
- **With `sys::win`:** per-volume folders are matched on the first segment below the drive letter only; on a volume mounted in a folder (`D:\Mounts\Data\$Recycle.Bin`) they are missed. `sys::win` reads `FileNameInformation` for `volume_root` anyway; it will also report the volume-relative path so policy can apply the per-volume rule to it.
- The elevated helper resolves its own list. Under over-the-shoulder elevation the administrator's profile is the "own" profile, so the user's profile counts as another user's. This is stricter and intended: user-writable roots are never changed elevated anyway.

## Amendment · 2026-11-04 (`sys::win` read side)
Points settled before `sys::win` is implemented (Phase 1, read-only):
- **Volume-relative path instead of a flag.** `RootInfo.volume_root: bool` becomes `RootInfo.volume_path: String`, the path of the directory below the root of its volume (`sys::win`: `FileNormalizedNameInformation` of the handle), empty for a volume root (`RootInfo::is_volume_root`). One field, so `sys::win` and the fake cannot report contradicting facts. `policy::root` applies the per-volume folder rule (`$*`, `Recovery`, `WindowsApps`, …) to the first segment of `volume_path` in addition to the first segment of the canonical path, so it also holds on a volume mounted in a folder (`D:\Mounts\Data\$Recycle.Bin`). This replaces the `volume_root: bool` wording in the "Volume roots that are not drive roots" bullet and the "With `sys::win`" bullet of the amendment above. `sys::win` takes `volume_path` only from `FileNormalizedNameInformation` on the same handle (one leading `\` stripped); if that query fails, `info()` fails. No fallback to `FileNameInformation` (8.3 names such as `WINDOW~1` would pass the per-volume rule), no derivation from `final_path` (drive-relative, misses folder-mounted volumes), never `""` as a stand-in. A volume mounted in a folder has its own volume serial (the fake models this too). `StoreDir::game` runs the forbidden check before the escape check, so the more specific reason is reported.
- **Absolute open (`Fs::open_dir`).** Input is drive-absolute only: `X:\…` or `\\?\X:\…`, `/` read as `\`, empty segments ignored. `.`, `..`, UNC, volume GUID paths and segments with control characters or `<>:"|?*` are `InvalidPath`, the same rules as the fake. `sys::win` builds `\??\X:\…` and calls `NtCreateFile` with `RootDirectory` NULL, `OBJ_CASE_INSENSITIVE` only (no `OBJ_DONT_REPARSE`, no `FILE_OPEN_REPARSE_POINT`: reparse points above the root are followed), `FILE_DIRECTORY_FILE`, `FILE_OPEN`, `FILE_SYNCHRONOUS_IO_NONALERT`. Not `CreateFileW`: opening a directory with it needs `FILE_FLAG_BACKUP_SEMANTICS`, which is `FILE_OPEN_FOR_BACKUP_INTENT`. A non-allowlisted tag on the opened directory is `ReparsePoint`, a file `InvalidPath`, a missing path `NotFound`.
- **Relative opens.** Every segment is opened with neither `FILE_DIRECTORY_FILE` nor `FILE_NON_DIRECTORY_FILE`, with `FILE_OPEN_REPARSE_POINT`, `OBJ_DONT_REPARSE | OBJ_CASE_INSENSITIVE`, the parent handle as `RootDirectory`, a single-segment name, `FILE_OPEN`, `SYNCHRONIZE` + `FILE_SYNCHRONOUS_IO_NONALERT`, and then classified on that handle (`FileAttributeTagInformation`): a surrogate or unknown tag is `ReparsePoint`, a file where a directory is needed `InvalidPath` (`metadata`: `None`), a directory where a file is needed `AccessDenied`. Walk handles carry `FILE_READ_ATTRIBUTES` only; the handle of a returned `Dir` adds list, traverse and `READ_CONTROL`. Only the data reopen of a file with an allowlisted data tag uses `FILE_NON_DIRECTORY_FILE` without `FILE_OPEN_REPARSE_POINT` (still `OBJ_DONT_REPARSE`, relative to the same parent) and requires the volume serial and file ID of the first open (`Busy` otherwise). A placeholder with `FILE_ATTRIBUTE_RECALL_ON_DATA_ACCESS`, `RECALL_ON_OPEN` or `OFFLINE` is `Unsupported` for `open_read` and is never hydrated. `sys::win` re-asserts the single segment (no `\`, `/`, `:`, NUL, not empty, `.` or `..`, at most 255 UTF-16 units). `NtCreateFile` is reachable only through `sys::win::nt::{open_relative, open_absolute_dir}`; flags are fixed there, callers pick an access and an open kind from closed enums. This replaces `FILE_DIRECTORY_FILE`/`FILE_NON_DIRECTORY_FILE` per component in the "Implementation" section: the type is checked on the handle, not by the open.
- **Long-name check (L1).** After every relative open, the last segment of `FileNormalizedNameInformation` on the new handle must equal the requested segment (exactly, or case-insensitively via the crate's 1:1 folding). A mismatch is `NotFound` (`metadata`: `None`), so `PROGRA~1` never reaches `Program Files`. Only if the file system does not support that class **and** the volume is FAT or exFAT does this check fall back to `FileNameInformation` (review L1: on any other file system an unsupported class is an error, so a filter driver failing the query on NTFS cannot let `PROGRA~1` through); `volume_path` never does (bullet above). This replaces `FileNameInformation` in the "Invalid names" bullet.
- **`user_writable`.** `GetSecurityInfo` on the directory handle (owner, group, DACL, label; hence `READ_CONTROL` on every `Dir` handle) and `AccessCheck(MAXIMUM_ALLOWED)` with the file generic mapping; writable means any of `FILE_ADD_FILE`, `FILE_ADD_SUBDIRECTORY`, `FILE_DELETE_CHILD`, `DELETE`, `WRITE_DAC`, `WRITE_OWNER`, `FILE_WRITE_ATTRIBUTES`, `FILE_WRITE_EA` is granted (review M1: `FILE_ADD_FILE` alone missed an owner with implicit `WRITE_DAC` and users with only subdirectory or delete-child rights). It describes the root directory itself only; entries below may have their own DACLs. The token is the user's non-elevated one: in a fully elevated process the linked token, otherwise a `SecurityIdentification` duplicate of the process token. With UAC off there is no other token, so the answer is for the administrator, which only makes more roots count as user-writable. Under over-the-shoulder elevation the linked token is the administrator's filtered token, not the interactive user's (review M2); in the elevated helper `user_writable` is therefore informational only and never a security decision, the helper's own security-descriptor check ("Elevation") is the boundary.
- **`read_dir`.** Entries from `NtQueryDirectoryFile(FileIdExtdDirectoryInformation)` (name, attributes, end of file, reparse tag, 128-bit file ID) with a 64 KiB buffer, `RestartScan` on the first call, `STATUS_NO_MORE_FILES` ends; `.` and `..` skipped. Only if the file system does not support that class on the first call (FAT) the listing uses `FileFullDirectoryInformation` (no file ID). Each entry is reopened relative to the listed directory by its raw UTF-16 name (`FILE_READ_ATTRIBUTES`, `FILE_OPEN_REPARSE_POINT`, `OBJ_DONT_REPARSE`, L1 check) and described by the same routine as `metadata`. An entry that vanished in between (`NotFound`) is skipped; every other error is returned, except `AccessDenied` (below). Names are converted lossily (U+FFFD), never dropped. Listing the handle's own directory is serialized per handle (the enumeration position belongs to the handle).
- **Restricted entries** (decided 2026-11-04). If the attribute-only reopen of a listed entry is denied (its own DACL denies the user even `FILE_READ_ATTRIBUTES`/`SYNCHRONIZE`, e.g. `%LOCALAPPDATA%\ElevatedDiagnostics`, `C:\ProgramData\ntuser.pol`), the entry is neither an error nor dropped: it is described from the listing with `Metadata.restricted = true`. Kind comes from the attributes and the tag (a surrogate or unknown tag is `Reparse`, a link target is unknown: `None`), length, attributes and file ID from the listing, the link count is unknown (`links: None`; `Metadata::is_single_link` is `false`, so the hard-link rule fails closed). `Dir::metadata` of such an entry gives the same description: on `AccessDenied` it lists the parent (a fresh `Dir` handle, no name filter, because NTFS keeps the first filter of a handle and filters also match 8.3 names) and takes the entry with exactly the requested long name, else the only case-insensitive match; no match is `None`. Without a file ID in the listing (FAT, which has no ACLs) the `AccessDenied` stays an error (fail closed). `open_read`, `open_dir`, `read_dir` of such an entry and every walk through it stay `AccessDenied`. Restricted entries are never opened by anyone: `sys::snapshot` records them as metadata only (kind, length, attributes, tag; not the link count) and never hashes or descends into them; `policy::path` and later primitives see them only as listing entries and never touch them.
- **Race contract.** The "safe vs. check-then-use" requirement above is met with a stress race contract on real Windows: a thread flips a directory between a real directory and a junction to an `outside/` canary while the operations run, and a naive path-based control implementation in the test must be caught by the same contract (so the contract demonstrably tells them apart). The oplock pause point is rejected: the read-only walk opens are attribute-only and never break an oplock, and directories only support read-handle oplocks, so there is no deterministic pause to hook.
- **Share modes.** `Dir` and walk handles share read, write and delete (a held root never blocks the user or a rename; a renamed or deleted directory is seen through the handle). `open_read` shares read only, so a concurrent writer yields `Busy` instead of torn content.
- **Phase 1 is read-only.** The writing `Dir` methods of `sys::win` return `Unsupported` ("sys::win is read-only in phase 1"). Path-based Win32 file APIs (`CreateFileW`, `CreateFile2`, `OpenFileById`, `FindFirstFile*`, `Get/SetFileAttributes*`, `DeleteFileW`, `RemoveDirectoryW`, `CreateDirectory*`, `MoveFile*`, `ReplaceFileW`, `CopyFile*`, `CreateHardLinkW`, `CreateSymbolicLinkW`, `GetFullPathNameW`, `Get{Long,Short}PathNameW`, `GetVolumeInformationW`, `GetCompressedFileSizeW`, `Get/SetFileSecurityW`, `Get/SetNamedSecurityInfoW`, `Set/DeleteVolumeMountPointW`, `DefineDosDeviceW`, `SetCurrentDirectoryW`) and `NtOpenFile` are `disallowed-methods` errors; `NtCreateFile` has exactly two exceptions.

## Amendment · 2026-11-04 (findings of the contracts on real Windows)
The read contracts now run against `sys::win` locally and on GitHub runners (`docs/09-testing.md`). What they settled:
- **WOF hides its tag.** While `wof.sys` is attached (every normal boot), a WOF-compressed file shows no `FILE_ATTRIBUTE_REPARSE_POINT`, no tag in `FileAttributeTagInformation` or the listing, and `FSCTL_GET_REPARSE_POINT` reports `ERROR_NOT_A_REPARSE_POINT`, even on a `FILE_OPEN_REPARSE_POINT` handle; reads return the uncompressed content. `sys::win` therefore reports such a file as a plain file without a tag; the allowlist and the data reopen stay for the case without the filter. This settles the WOF part of the "Consequences" bullet: a hash of a WOF-compressed file equals the hash of the uncompressed copy (checked on a synthetic file). Compressing a game folder does not change its snapshot.
- **`info()` during a rename of an ancestor.** `GetFinalPathNameByHandleW(FILE_NAME_NORMALIZED)` (and potentially `FileNormalizedNameInformation`) resolves the current path component by component and fails with `ERROR_FILE_NOT_FOUND` while an ancestor is renamed. `WinDir::info` retries `NotFound`-class failures of these two queries up to 32 times on the same handle; a persisting race is `NotFound` (fail closed, an identity is never guessed).
- **Race harness.** A swap by path is two renames of hundreds of microseconds each; a check-then-use with only `yield_now` between check and use was never caught in 30 s, with a 1 ms pause it is caught in well under a second. The control implementation pauses 1 ms. Windows refuses to rename a directory while a handle below it was opened without `FILE_SHARE_DELETE` (`open_read` shares read only); the flipper retries such renames. This confirms the share mode decision: a held `open_read` blocks renaming its parents, which is fine for reads and is reconsidered for the write path in phase 2.

## Amendment · 2026-11-04 (security review of the `sys::win` read side)
- **`user_writable`** (M1, M2): see the updated `user_writable` bullet above. Writable means any right that changes the directory or lets the user grant itself one; it describes the root itself only; in the elevated helper it is informational only.
- **L1 fallback** (L1): `FileNameInformation` only on FAT/exFAT, see the long-name bullet above.
- **Restricted lookup** (L2): `metadata` of a restricted entry lists its parent through a second walk; the reopened parent must have the volume serial and file ID of the walk's parent handle, else `Busy`. Accepted limit: the listing match uses the crate's 1:1 fold, which can differ from the NTFS upcase table (`ſ`, `ı`, Georgian); a mismatch only makes the lookup find nothing (`None`), never a different entry, because an exact match is preferred and a fold match must be unique.
- **`info()` consistency** (L3): `final_path` and `volume_path` are taken in one attempt and must agree (the final path ends component-wise with the volume path, case-insensitively); otherwise the attempt counts as a transient rename race, is retried up to 32 times and finally reported as `NotFound`.
- **Data reopen** (info): the recall attributes are checked again on the data handle of an allowlisted tagged file; a placeholder that shows them only there is `Unsupported` as well.
- **Bans** (L4): `clippy.toml` also bans the app-container, transacted, legacy (`OpenFile`) and ANSI variants of the path-based file APIs, the NT by-name file calls and their `Zw` twins (`NtDeleteFile`, `NtQueryFullAttributesFile`, `NtQueryInformationByName`, `ZwCreateFile`, `ZwOpenFile`, …), `NtSetInformationFile` (phase 2 renames and deletes by handle go through one `sys::win::nt` wrapper, which will be its only exception) and `CreateProcess*` (processes only through `sys::Process`). `sys/win/bans.rs` makes every `windows-sys` entry fail clippy if it does not resolve. Test fixtures may use `NtCreateFile` (resetting stale DACLs with `WRITE_DAC` only); the "exactly two exceptions" rule is about production code.

## Amendment · 2026-11-04 (default forms of the per-user folders, ADR 0009)
- **The default forms below the profile stay forbidden.** `LocalAppData` and `RoamingAppData` come from `HKCU\…\User Shell Folders`, which the user can redirect. Their derived entries (`AppData\Local\{Microsoft, Packages, VirtualStore, Rerun}`, `AppData\Roaming\Microsoft`) are therefore also derived from every form of `<Profile>\AppData\Local` and `<Profile>\AppData\Roaming`, for every form of `Profile`: those two folders are opened like a known folder (lexical and canonical form; missing: lexical only; any other failure: fail closed), so a junction there (`<Profile>\AppData\Local` → `D:\L`) protects `D:\L\Packages` too (security review, 2026-11-04). Same "equal or inside, and ancestor of" rule, reported as `Protected::ProfileDefault`. A redirection can only add entries, never remove one: with `LocalAppData` on `D:\Redirected\Local`, both `D:\Redirected\Local\Microsoft` and `<Profile>\AppData\Local\Microsoft` are forbidden. They are never opened.
- **Accepted denial of service: a per-user folder on a share.** A `LocalAppData` (or any known folder other than `RoamingAppData`) on a network path has no valid drive-letter form, so resolving the list fails closed (`ForbiddenListIncomplete`) and no root is handed out at all. Only the same user (or their administrator) can redirect it, so this harms nobody but that user; `RoamingAppData` on a share stays the one tolerated case (skipped, never opened), as above.

## Amendment · 2026-11-05 (phase 2 plan)
Where the points left open for phase 2 went:
- **Write side** (the "Replace", "Revert" and hard-link rules, the phase 2 renames and deletes by handle, `FileNameInformation` before each rename, share modes on the write path): ADR 0017. `FileGuard` holds hash and action on one handle; replace and delete take an expected SHA-256; hard-linked targets are refused, not only "never changed in place" (user decision D1); POSIX delete and rename are required, a volume without them gets no write handle; renames only by a single segment relative to a checked handle (observed: a rename target with `\` follows junctions).
- **`AppDir`** (`<LocalAppData>\Rerun`, the third root kind named in "Only policy hands out roots"): ADR 0019. Its own opening rules; it is not checked against the forbidden list, whose `LocalAppData\Rerun` entry keeps game and store roots out of it.
- **Root identity after a moved library or a reinstall** (`IdentityMismatch` on revert): strict `--rebind`, ADR 0020 (user decision D5).
- **`UserData` root kind** (`Documents`, `My Games`): phase 4 (user decision D6), with its own allowlist instead of the forbidden list; the plan format already carries a root kind per root (ADR 0020).
- **VirtualStore warning:** phase 3.
