# ADR 0022 · Launch profiles and rerun-launch

**Status:** accepted · 2026-11-08, amended the same day by the review of P3-1a (M1, M2, B-2, B-3), by P3-1b (the shim as built; B-2 without the group affinity attribute) and by P3-2 (post-launch check, result file) · extends ADR 0006, ADR 0008, ADR 0010 · phase 3, steps P3-1 (P3-1a: `rerun-proto`; P3-1b: the shim) and P3-2

## Context
Phase 3 starts a Steam game through `rerun-launch.exe` with a CPU rule (`docs/04-launch-methods.md`, `docs/08-roadmap.md`). The shim depends on `windows-sys` and `rerun-proto` only (ADR 0006): everything it shares with `rerun-core` (the rule selection, the profile format) must live in `rerun-proto`, without serde. The selection has to run in the shim at every start, because CPU Set IDs are runtime values (ADR 0010). `docs/03-cpu-topology.md` left four points open: LP E-cores were "never for games" without a step that removes them, the group of step 1 was "group 0 (or the largest)", step 5 said "truncate to 32" for a 32-bit game, and the SMT example of the plan (4 cores × 2 threads) contradicted step 6 ("cores before SMT siblings"). For the shim itself the plan review (P3 plan, conditions B1–B4, B13; decisions D1–D3, D5) asked for decisions before P3-1b, among them two Win32 questions: how a hard mask reaches a group other than 0 (B4), and whether a 32-bit game is limited by a count or by indices (B6).

## Decision

### Shared code in `rerun-proto` (P3-1a)
- `cpu::rule`: `CpuRule { max_threads, prefer, single_l3, prefer_l3, smt, mode }`, `Bitness`, `select(&CpuTopology, &CpuRule, Bitness) -> Result<Selection, SelectError>`. `Selection { group, mask, cpu_set_ids, threads, of }`; `SelectError::Empty { after: SelectStep }` names the step that emptied the candidates, `Invalid` carries a `TopologyError` (`select` validates first). Pure, no dependency, no `unsafe`.
- `profile`: `LaunchProfile`, `ProfileId`, `encode`/`decode` (format 1, below). No serde: the shim reads it as is (ADR 0006).

### Selection (docs/03, "Selection algorithm")
1. **Group:** the group with the most logical processors, on a tie the lowest number (B6). Within it, LLCs whose `level` is below the highest level in the group drop out: LP E-cores keep their own L2 as last level beside an L3, so the level separates them where the efficiency class may not (Panther Lake). A machine whose LLCs share one level loses nothing. No rule field selects LP E-cores in phase 3.
2. **32-bit:** an x86 game keeps indices `< 32` only (B6, below). Before the class and L3 steps, so the L3 choice sees only what the game can address.
3. `prefer: performance` → highest efficiency class.
4. `prefer_l3: largest` → largest size, then most candidates, then lowest `llc`; `single_l3` → most candidates, then largest size, then lowest `llc` (candidates = threads left before the SMT step; user decision: on Zen 5 + Zen 5c `single_l3` picks the cluster with more threads, full-size cores need `prefer_l3: largest`). Exactly one LLC with either flag; without them all LLCs stay.
5. `smt: false` → first thread of each core.
6. `max_threads: N` → first `N` of "first threads of all cores, then second threads …", by index (B5: the 5950X with `max_threads: 8, single_l3` is 8 cores × 1 thread on CCD 0, with or without SMT).
7. Empty → `Empty { after }`; only step 2 and `max_threads: 0` can empty a non-empty set.

`mode` (hard/soft) does not influence the selection.

### B6 · 32-bit games: indices below 32, not a count of 32
A WOW64 process holds affinity as pointer-sized values: `DWORD_PTR` in `SetProcessAffinityMask`/`GetProcessAffinityMask` and `KAFFINITY` (`ULONG_PTR`) in `GROUP_AFFINITY` are 32 bits wide in 32-bit code (Windows Data Types). A selection of 32 processors with any index ≥ 32 has bits the game cannot represent: `GetProcessAffinityMask` in the game cannot report them, and a game that reads its mask and sets it again (common in old engines, also the classic "single core" fixes) narrows or breaks its own affinity. Limiting the indices keeps the selection exactly representable in the game's own view; the count limit follows from it. The cost: on a group of more than 32 processors a 32-bit game never gets the processors at 32 and above, even if the best LLC sits there (Threadripper, Xeon; no consumer part with more than 32 threads per group is affected). The same rule applies in soft mode, so both modes agree. Manual check (docs/09, "32-bit game on a group with more than 32 logical processors"): only a measurement that shows bits above 31 to be harmless may relax this to a count.

### B4 · Hard limit: one `GROUP_AFFINITY` on the job, also for group 0
- The hard limit is set with `SetInformationJobObject(JobObjectGroupInformationEx)` and an array of exactly **one** `GROUP_AFFINITY { Mask, Group }`: "the affinity of the job for the processor groups to which the job is currently assigned" (`SetInformationJobObject`, `JOBOBJECTINFOCLASS`, Windows 8 and later). It names the group explicitly, so one code path serves group 0 and groups ≠ 0, and the single-group developer machine tests the same call a 128-thread machine uses.
- `JOB_OBJECT_LIMIT_AFFINITY` (`JOBOBJECT_BASIC_LIMIT_INFORMATION.Affinity`) is **never** set: it is a bare `KAFFINITY` without a group number, documented as "a subset of the system affinity mask obtained by calling `GetProcessAffinityMask`", i.e. of one (the primary) group, and on Windows 11 a process is no longer confined to one group by default ("Processor Groups": starting with Windows 11 and Windows Server 2022, process and thread affinities span all groups by default). Mixing both forms is undocumented.
- **Order (review B-2), fixed:** (1) create the job and set its extended limit flags (below); (2) create the child **suspended and inside the job**: `CreateProcessW` with `EXTENDED_STARTUPINFO_PRESENT`, `CREATE_SUSPENDED`, `PROC_THREAD_ATTRIBUTE_JOB_LIST` (Windows 10 and later; no window between creation and `AssignProcessToJobObject`) and `PROC_THREAD_ATTRIBUTE_GROUP_AFFINITY` with the selected `GROUP_AFFINITY` (Windows 7 and later), so the initial thread, and with it the process's primary group, is the selected group (*superseded by amendment P3-1b: `CreateProcessW` refuses that attribute; the read-back of step 4 guards the group instead*); (3) set `JobObjectGroupInformationEx` on the job, which now holds the child; (4) read back the job's group affinity (`QueryInformationJobObject`) and the initial thread's (`GetThreadGroupAffinity`); (5) `ResumeThread`. Any failure or difference in (3) or (4) terminates the suspended child (it never ran) and starts Steam's command unchanged (D3). Every `GROUP_AFFINITY` the shim passes has `Reserved` zeroed. That the attribute fixes the primary group is an assumption (*void since amendment P3-1b: `CreateProcessW` refuses the attribute; the multi-group case now measures three variants*) checked by the multi-group case in docs/09 (a Hyper-V VM with `bcdedit /set groupsize 8`) before P3-1b counts as accepted on multi-group machines; whether `JobObjectGroupInformationEx` can be set on an **empty** job (which would allow setting it before step 2) is a [DEV] measurement that may only simplify the order, not change the read-back.
- Job flags (B4): `JOB_OBJECT_LIMIT_BREAKAWAY_OK` yes (a launcher child that asks for `CREATE_BREAKAWAY_FROM_JOB` may leave; that such a start fails without the flag is **not documented**, an unmeasured [DEV] case; the flag costs nothing either way), `JOB_OBJECT_LIMIT_SILENT_BREAKAWAY_OK` no (every child stays unless it asks), `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` off until measured: with it, Steam's "Stop" (which ends the shim) would end the game too, but so would a crash of the shim. The [DEV] measurement decides. Nested jobs (Steam or a launcher holding the shim in a job, Windows 8 and later): the parent's limits keep applying; if the nested job cannot take the limit, the shim starts unchanged (D3), Sandbox case R3.
- Soft mode: `SetProcessDefaultCpuSets(child, ids)` on the suspended child before `ResumeThread`. It applies to the launched process only, not to its children (plan nit); the preview says so.
- Priority (D6 a): the creation flag of `CreateProcessW` (`NORMAL_`, `ABOVE_NORMAL_`, `HIGH_PRIORITY_CLASS`; never realtime) for `direct`, `SetPriorityClass` on the target for `watch`.
- The setters (`SetInformationJobObject`, `UpdateProcThreadAttribute`, `SetProcessDefaultCpuSets`, `SetPriorityClass`) are banned in `clippy.toml` (ADR 0010) except in one wrapper module of `rerun-launch` (`#[allow(…, reason)]`); P3-1b amends ADR 0010 with its name. Handles (job, process, thread, attribute list) are RAII; the shim keeps the job handle open while it waits (B3).

### D1 · Profile format 1
- UTF-8 text, at most 8 KiB (`MAX_PROFILE_BYTES`), header `rerun-profile 1`, then `key=value` lines in a fixed order, each ending in LF: `method` (`direct`/`watch`), `start`, `target`, `bitness` (`x86`/`x64`), `priority` (`none`/`normal`/`above_normal`/`high`), `watch_timeout_s` (1–120), `cpu` (`none`/`rule`), and with `rule` the six lines `cpu.prefer`, `cpu.single_l3`, `cpu.prefer_l3`, `cpu.smt`, `cpu.mode`, `cpu.max_threads` (`none`/1–4096). Every key always present (explicit `none`), so the encoding is canonical: a file decodes to one profile and encodes back to the same bytes.
- Refused: more than 8 KiB (before parsing), not UTF-8, no final LF, CR, any control character, an empty line, another header or format, an unknown, repeated, misplaced or trailing key, a value outside its set, a number with a sign or leading zero, `direct` with `target != start`. Errors carry the line and the key, never content.
- `start` and `target` are canonical absolute drive paths: `X:\` and components, none empty, `.` or `..`, none starting with a space or ending in a space or a dot, none a reserved device name (`CON`, `NUL`, `COM1`, `nul.txt`, …), none of `< > : " / | ? *`, no Unicode format or separator character (Cf, Zl, Zp: bidirectional controls, zero-width characters, U+FEFF, U+2028/U+2029), at most 2,048 UTF-16 units; never `\\?\`, UNC or relative. `bitness` is the target's PE machine, read when planning.
- `encode` checks its output with `decode` (a difference is `NotCanonical`) and fails rather than write a file the shim would refuse (a deviation from the plan's infallible signature).
- `ProfileId`: 16 bytes, 32 lower-case hex digits in the file name and the launch option. How core derives it (folded canonical start path, or app ID + start path; plan nit) is decided with the planner in P3-3.
- Place: `<LocalAppData>\Rerun\profiles\<id>.profile` (docs/01). Written only by `apply` as a journaled file op (P3-3).

### D2 · How the shim finds its profile
The launch option is `"<install>\rerun-launch.exe" --profile <32 hex> %command%`. The folder comes from `SHGetKnownFolderPath(FOLDERID_LocalAppData)`, never from the environment. That adds `shell32.dll` to `LAUNCH_IMPORTS` (ADR 0008 import allowlist, reviewed in P3-1b). If a cold start measures 50 ms or more until `CreateProcessW` (release build, [DEV]), the option carries the full profile path instead and the shim checks only its form (`<drive>:\…\Rerun\profiles\<32 hex>.profile`).
The read is bounded (`MAX_PROFILE_BYTES + 1`) and refuses a reparse point at the file. The profile is user-writable by design: for a **non-elevated** shim, whoever can write it can also start the game with any affinity and priority, so it is no privilege boundary. For an elevated shim it would be one, so an elevated shim never reads it (M1).

### M1 · An elevated shim ignores the profile
- **Elevated** is decided as in `rerun-core::sys` (`token::process_elevated`, fail closed): the token is elevated (`TokenElevation`), or that cannot be determined, or UAC is off (`TokenElevationTypeDefault` for a member of Administrators) — each counts as elevated (security review N3).
- An elevated shim (Steam started as administrator) does not open the profile, does not read the topology, sets no limit and no priority, and writes nothing (no result file, B13). It starts Steam's command unchanged (`lpApplicationName` by M2) and waits for it (B3). Rerun's preview says that a rule does not apply while Steam runs as administrator.
- R7 of the plan is corrected accordingly: the elevated case is not "harmless because it only sets affinity", it is closed by not reading user-writable input at all.
- `watch` (P3-4) accepts a target process only if it was created after the shim started, runs in the shim's session, has the shim's user SID and no higher integrity level than the shim. D4 (path only, hash at plan time) is justified for the non-elevated shim only, which is the only one that reads a profile.

### D3 · Fail closed for the rule, fail open for the start
Profile missing or invalid, Steam's first argument not equal to `start` (ordinal, case-insensitive; then `path_mismatch`), topology error, `Empty` selection, a job or verification failure: the shim starts Steam's command **unchanged**, without any limit, and records the outcome (D5). A rule is never applied to another path than the planned one. Without Rerun, Steam would have started exactly that command; an orphaned profile (revert while Steam was open) must not make a game unstartable. Exceptions, which start nothing (deliberate, both exit codes in B1): the DLL search restriction fails (ADR 0008, fail closed, B2), or the shim's own command line is unusable (missing `--profile`, no command after it, or Steam's first argument not an absolute drive path; B1, M2).

### B1 · No console; the shim's own command line
- `#![windows_subsystem = "windows"]`: no console window flashes up at a game start. The shim reports through its exit code and the result file only; `crates/rerun-launch/tests/hardening.rs` checks the exit code instead of stderr (P3-1b).
- The command line is taken raw from `GetCommandLineW`: the shim's own first token (by the `CommandLineToArgvW` rule for argument 0), the literal `--profile`, one token, then Steam's command as the raw tail, never re-quoted from `argv`. A token that is not 32 lower-case hex digits counts as an invalid profile (D3: start the tail unchanged, no result file, since there is no ID). Without `--profile`, or with nothing after the token, there is no command to start: exit code 2, nothing started. If the game started, the shim's exit code is the game's (B3); before a start, 1 means the hardening failed and 2 an unusable command line.
### M2 · `lpApplicationName` is always Steam's first argument
- Steam's first argument (`argv[0]` of the tail) is cut from the raw tail by the `CommandLineToArgvW` rule for argument 0: if the tail starts with `"`, everything up to the next `"`; otherwise everything up to the first space or tab. `lpApplicationName` is **always** that `argv[0]` (quotes removed), in every case: with a rule, on `path_mismatch`, on any D3 fallback and for the elevated shim (M1). `lpCommandLine` is the raw tail, byte for byte. `CreateProcessW` is never called with `lpApplicationName = NULL`, so Windows never searches the current directory or `PATH` for the program, and an unquoted path with spaces is never resolved piece by piece.
- `argv[0]` must be an absolute drive path (`X:\…`; not relative, not UNC, not `\\?\`). Otherwise the shim starts nothing and exits with 2 (D3 exception). With a profile, the rule is applied only if `argv[0]` equals `profile.start` ordinal case-insensitively; the layers start path (docs/04) is Steam's spelling then, which Sandbox case SB-L7 checks.
- [F] tests in P3-1b: quoted path, unquoted path without spaces, **unquoted path with spaces** (`argv[0]` ends at the first space, so it is then not the game and not absolute, or does not match `start`), quotes and `%` inside arguments, empty tail, trailing spaces; the tail always byte-identical. [DEV]: how Steam really quotes `%command%` (a game path with spaces, arguments from the launch options).
- Never a path from a handle, never `\\?\` (docs/04, layers start path). Handles are not inherited; environment and current directory are the shim's (Steam's).

### B2 · Elevation required (error 740)
- If `CreateProcessW` fails with `ERROR_ELEVATION_REQUIRED` (that `CreateProcessW` reports 740 for a `requireAdministrator` manifest is **not documented** on the pages below; an unmeasured [DEV] case before P3-1b relies on it), the shim starts Steam's command with `ShellExecuteExW`, without any rule, and records `elevation_required` (nothing when elevated, M1):
  - `lpVerb` NULL (default verb, Windows asks for consent per the game's manifest); `lpFile` = exactly the same absolute `argv[0]` as for `CreateProcessW` (M2), and only if it ends in `.exe` (ordinal case-insensitive), else nothing is started and the outcome is recorded; `lpParameters` = the raw tail from the first character that is not a space or tab after `argv[0]`, byte for byte, never re-quoted; `lpDirectory` NULL.
  - `fMask = SEE_MASK_NOCLOSEPROCESS | SEE_MASK_NOASYNC`; the shim waits on `hProcess` (RAII handle) and passes the exit code through (B3).
  - COM: `ShellExecuteExW` may use shell extensions, so the shim calls `CoInitializeEx(NULL, COINIT_APARTMENTTHREADED | COINIT_DISABLE_OLE1DDE)` once before it, on this path only, and `CoUninitialize` after the call. `CoInitializeEx` is banned (ADR 0008 amendment, DXGI); this is its second reviewed exception, in the same wrapper module, and it may add `ole32.dll`/`combase.dll` to `LAUNCH_IMPORTS` (reviewed in P3-1b).
  - [F] test in P3-1b with the M2 quoting cases: `lpFile` and `lpParameters` as above, nothing for a non-`.exe` `argv[0]`.
- `ShellExecuteExW` is banned (ADR 0010); the exception is this one call in the wrapper module of `rerun-launch`, because `CreateProcessW` cannot raise a consent prompt and the game must still start (D3). It needs `shell32.dll` (see D2).

### B3 · Lifetime
- `direct`: the shim waits for its direct child to exit and passes its exit code through, so Steam keeps tracking the game (risk R1: playtime, overlay, "Stop", cloud sync after the end). The post-launch check (P3-2) runs about 5 s after the start, while waiting. docs/04: "until the started process exits".
- `watch`: the shim lives at least as long as its direct child and at most until the target is found and checked; if the target never appears, it stops searching after `watch_timeout_s` (≤ 120 s) and writes `target_not_found` (≤ 130 s in all, plus the wait for the direct child).
- Rule 1 holds: never longer than the game, opt-in through the applied plan, the preview names the lifetime. A [DEV] measurement (overlay, Steam Input, cloud sync, a SteamStub game) may relax the wait, never extend it.

### D5 and B13 · Result file, not the journal
The journal has one writer under `journal\lock` (ADR 0019); a game start during an `apply` must neither block nor write records. The (non-elevated) shim writes the outcome of the last start to `<LocalAppData>\Rerun\launch\<id>.result` (codec in `rerun-proto::launch`, P3-2): handle-relative below `launch`, a reparse point at `Rerun` or `launch` refused, temp file + rename in that folder, bounded. Core reads it as untrusted input. It is Rerun-owned state like the journal: revert and `forget` of the profile leave it. **B13:** a shim that counts as elevated (M1) writes no result file, so an elevated process never writes into a user-writable folder. This writer is new surface for the shim and goes to the security review with P3-2.

### Not decided here
- D4 (`watch` target identity: path only, hash at plan time; non-elevated only, M1) and D6 (priority in the profile) are taken as decided in the plan; P3-4 records the `watch` details here. The result codec, `CheckOutcome` and `reset` without a culprit follow in P3-2.
- D6 addition: the post-launch check (P3-2) also checks the priority class.
- A missing `--profile` (or no command after it) is exit 2 without a start: a deliberate exception to D3, since there is no command Steam would have started.
- The planner (P3-3) refuses a start or target path whose profile would exceed 8 KiB, and a path longer than 260 characters unless long-path support is confirmed for that start (a [DEV] question for P3-3).

## Alternatives
- **Basic-limit `Affinity` for group 0, `JobObjectGroupInformationEx` only for other groups:** two code paths, and the group-0 path relies on the primary group, which Windows 11 no longer pins.
- **`SetProcessAffinityMask` on the suspended child, no job:** one group only (the primary), the game may undo it, children are not covered.
- **32-bit: a count of 32 anywhere in the group:** more choice on large groups, but masks the game cannot represent (B6).
- **JSON profile with a hand-written parser, or serde in the shim:** a larger parser to bound and test (D1 b), or against ADR 0006 (D1 c).
- **Do not start on any error (D3 b):** an orphaned profile would block the game in Steam.
- **Results in the journal:** a second writer, or a start that blocks behind an `apply`.

## Consequences
- `rerun-proto` grows by `cpu::rule` and `profile` (no dependency). The fixtures planned in docs/03 exist now (datasheet or synthetic, assumptions in their README) with a reviewed selection snapshot.
- P3-1b: `rerun-launch` gets its `Os` trait (real and fake), the copy of the two topology calls (x64 only, `compile_error!` otherwise, ADR 0010; *built as a run-time `Unsupported` instead, amendment P3-1b*), the wrapper module with the setter and `ShellExecuteExW` exceptions, `windows_subsystem`, and the reviewed `LAUNCH_IMPORTS` (`shell32.dll`); amendments to ADR 0008 and ADR 0010; docs/04 (lifetime, result file instead of journal, `reset` without culprit, start path rule) and docs/01 (exits immediately → lifetime) in the same commit.
- docs/03 states the selection precisely (group tie, LP-E rule, 32-bit indices, L3 ties only with `single_l3`/`prefer_l3`, B5).

## Amendment P3-1b (2026-11-08): the shim as built

### B-2 without `PROC_THREAD_ATTRIBUTE_GROUP_AFFINITY` (measured)
`CreateProcessW` refuses `PROC_THREAD_ATTRIBUTE_GROUP_AFFINITY` with `ERROR_INVALID_PARAMETER` (87): alone or together with `PROC_THREAD_ATTRIBUTE_JOB_LIST`, suspended or not, with a mask of one processor or of all 32 of group 0 (Windows 11 build 26300, Ryzen 9 5950X, one group; the attribute value carries the `PROC_THREAD_ATTRIBUTE_THREAD` bit). The job list alone works. The order is therefore:
1. create the job and set `JOB_OBJECT_LIMIT_BREAKAWAY_OK` (B4, unchanged);
2. `CreateProcessW` with `CREATE_SUSPENDED`, `EXTENDED_STARTUPINFO_PRESENT` and **only** `PROC_THREAD_ATTRIBUTE_JOB_LIST`;
3. `SetInformationJobObject(JobObjectGroupInformationEx)` with the one selected `GROUP_AFFINITY` (`Reserved` zero);
4. read back: the job must report exactly that one entry, and `GetThreadGroupAffinity` of the initial thread must equal it (group **and** mask). On the developer machine both are equal after step 3 (`win::tests::hard_limit_round_trip_on_a_child_cmd`): the job limit narrows the suspended thread itself;
5. `ResumeThread`.

The primary group is no longer set at creation. On a multi-group machine the read-back of the initial thread is the guard: if the job limit does not move the thread into the selected group, the read-back differs and the shim starts Steam's command unchanged (D3), so a rule is never applied with another primary group. The multi-group case in docs/09 (Hyper-V, `bcdedit /set groupsize 8`) decides whether that happens; if it does, the remedy is `SetThreadGroupAffinity` on the suspended initial thread before step 3, a further banned setter in the same wrapper module, decided with that measurement.

**Empty job (measured, same machine):** `SetInformationJobObject(JobObjectGroupInformationEx)` succeeds on a job that holds no process yet. The order above stays (the read-back is needed either way); setting the limit before the spawn is a possible simplification, not taken. Without step 3 the read-back reports the whole group for job and thread (`win::tests::read_back_without_the_limit_differs`), so a missing limit is caught.

### Shape of the shim
- Modules: `cmdline` (pure: the own command line, `argv[0]` by the `CommandLineToArgvW` rule, the absolute-path and `.exe` checks), `os` (`trait Os`, `Spawn`, `GroupAffinity`, `ReadBack`, `OsError`), `run` (every decision; returns a `Report` with the rule outcome, the start kind and the exit code: the input of the result file of P3-2, nothing is written yet), `fake` (`FakeOs`, tests only), `win` (`WinOs`: command line, token check, profile read), `win::launch` (the wrapper module, ADR 0010 amendment P3-1b), `win::cpu` (the copy of the two topology calls).
- `trait Os` splits the hard limit into `spawn` (steps 1 and 2), `limit_job` (3), `read_back` (4) and `resume` (5), plus `set_cpu_sets`, `terminate`, `shell_execute`, `wait`, `elevated`, `read_profile`, `topology` and `command_line`. `run` decides what a failure or a difference means; `WinOs` only calls Windows. The child is an associated type that owns its handles (process, initial thread, job), so the job stays open while the shim waits (B3).
- Soft mode: the child is created suspended **without** a job, then `SetProcessDefaultCpuSets` and `ResumeThread`; no read-back (the P3-2 check covers it). A profile with a priority but no CPU rule starts the child with the priority creation flag, not suspended, without a job.
- Any failure on the rule path (job, a spawn error other than 740, `limit_job`, read-back, CPU Sets, resume) terminates a created child (it never ran) and starts the command unchanged **once**; 740 on either start goes to `ShellExecuteExW`.
- A profile with `method: watch` starts the command unchanged until P3-4 implements it.
- Exit codes: the child's exit code (all 32 bits, through `ExitProcess`), 1 hardening, 2 unusable command line, and **3** (new): the command could not be started (also a non-`.exe` `argv[0]` after 740, or a declined consent prompt) or its exit code could not be read. A `ShellExecuteExW` start without a process handle exits with 0.
- `argv[0]` containing a `"` (an unquoted `C:\a"b c"\game.exe` cut at the space) counts as not an absolute drive path: exit 2.
- `ShellExecuteExW` gets `nShow = SW_SHOWNORMAL` (a zeroed structure would be `SW_HIDE`). If `CoInitializeEx` fails, `ShellExecuteExW` is still called (fail open for the start) and `CoUninitialize` is not.
- **M1 as built:** elevated if `TokenElevation` is set, or `TokenElevationType` is `TokenElevationTypeDefault` and `CheckTokenMembership(NULL, S-1-5-32-544)` is true (UAC off for an administrator), or any of these calls fails.
- **D2 as built:** `SHGetKnownFolderPath(FOLDERID_LocalAppData)` exactly as `rerun-core::sys::win::shell` calls it (`KF_FLAG_DONT_VERIFY | KF_FLAG_NO_PACKAGE_REDIRECTION`, the process token). The file is opened with `FILE_FLAG_OPEN_REPARSE_POINT`, shared for read and delete (a replace by rename during the read keeps the old content), refused if its attributes carry `FILE_ATTRIBUTE_REPARSE_POINT` or it is not a regular file, and read through `take(MAX_PROFILE_BYTES + 1)`. Reparse points at `Rerun` or `profiles` are followed (D2 names the file only; for a non-elevated shim the profile is no boundary).
- **32-bit build:** `win::cpu` exists for 64-bit targets only; a 32-bit shim reports the topology as `Unsupported` at run time (the form ADR 0010 allows besides `compile_error!`), so the CI's i686 clippy run of the shim still builds, and every CPU rule starts unchanged there. Only the x64 shim ships.
- Imports added to `LAUNCH_IMPORTS` (ADR 0008 amendment P3-1b): `advapi32.dll` (token), `shell32.dll` (known folder, `ShellExecuteExW`), `combase.dll` (`CoTaskMemFree`), `ole32.dll` (`CoInitializeEx`/`CoUninitialize`); all KnownDLLs. Release binary: 332,800 bytes (x64, 2026-11-08).
- The sources marked "not checked in this step" above stay unchecked (no web access in P3-1b).

### Review of P3-1b (2026-11-08)
- **Multi-group until measured.** Without the group attribute the hard mode may fall back to "unchanged" on a machine with more than one processor group (more than 64 logical processors, or a VM with a small group size): the read-back of the initial thread fails closed. The preview of a hard rule (P3-3) must say so on such a machine. The multi-group case in docs/09 measures three variants: (a) as built; (b) the group limit set on the **empty** job before the spawn (accepted by Windows, measured), then the same read-back; (c) `SetThreadGroupAffinity` on the suspended initial thread before step 3. `SetThreadGroupAffinity` is not built until that measurement decides.
- **Start path comparison.** `argv[0]` and `start` are compared with `CompareStringOrdinal(a, b, TRUE)` (kernel32, the comparison Windows uses for file names; no own folding): `Ä`/`ä` are equal, `Straße`/`STRASSE` differ. The planner (P3-3) uses the same rule wherever it decides that a Steam path is the profile's `start`.
- **Termination.** A child created with the rule that has to be ended is ended with `TerminateProcess`, then waited for up to 5 s; the outcome (`Ended`, `Failed(code)`, `NotConfirmed(code)`) is a field of the `Report` for the result file (P3-2). The unchanged start follows in every case (fail open).
- **Report.** `Report::Ran` carries the profile ID whenever the token is one (the result file's name, P3-2).
- **`Spawn.in_job: bool`.** The system layer creates the job; the group affinity reaches it only through `limit_job`.
- **Bans.** `SetPriorityClass` and `AssignProcessToJobObject` are banned in `clippy.toml` as this ADR states (B4); their exception would be the wrapper module `win::launch` (neither is used yet: the priority is a creation flag, the job is joined by the job list attribute).
- **STARTUPINFO.** The shim does not pass its own `STARTUPINFO` (show-window state, title, …) on; the child gets a zeroed one with only `cb` set. Whether a game behaves differently when started by Steam directly is a [DEV] observation (docs/09).

## Amendment P3-2 (2026-11-08): post-launch check and result file

### Check (docs/04, D6 addition)
- Only with the rule applied, after the resume: the shim waits up to 5 s on the running child without consuming it (`Os::wait_for`). If the child ends in that time the check is `exited_early` and nothing is read (a launcher stub that hands over: the Topo needs `watch`, risk R4); a failed wait is `failed:<code>`.
- Then it reads what Windows reports now and compares it with what it set. Hard: the job's `JobObjectGroupInformationEx` is exactly the one `GROUP_AFFINITY`, and `GetProcessAffinityMask` of the process equals its mask (the job narrows the process itself, measured: `win::launch::tests::check_reads_on_a_limited_child`; a 0, threads in more than one group, is a difference). Soft: `GetProcessDefaultCpuSets` holds exactly the selected IDs (any order). Priority: `GetPriorityClass` equals the class set; a profile without a priority checks none (the game may set its own).
- Any difference is `reset` with what differs (`cpu`, `priority`, both); no culprit is named. A failed read is `failed:<code>`. The check runs once; repeating it is `hold` (phase 6).
- Not covered: a thread the game pins inside the job's mask (still a subset), a child that breaks away from the job (`BREAKAWAY_OK`, B4), the soft mode's children (not inherited, as before).
- The reads `GetProcessAffinityMask` and `GetProcessDefaultCpuSets` are banned as topology sources; their exception is `win::launch` (ADR 0010 amendment P3-2).

### Result file, format 1 (`rerun_proto::launch`)
- `<LocalAppData>\Rerun\launch\<id>.result`, nine lines, each `key=value` with LF, at most 1 KiB, the same strictness as the profile (header `rerun-result 1`; `profile`, `time` in Unix seconds, `rule`, `cpu`, `priority`, `check`, `start`, `ended`; every key always present; a combination no writer emits is refused, so a file decodes to one `LaunchResult` and encodes back to the same bytes).
- `rule=applied` with `cpu` (`none` or `hard|soft:<threads>:<of>`), `priority` and `check` (`ok`, `reset:cpu|priority|cpu_priority`, `exited_early`, `failed:<code>`); `start=created`, `ended=none`.
- `rule=skipped:<reason>` with `start` (`created`, `shell`, `shell_no_process`, `not_exe`, `failed:<code>`) and `ended` (a child created with the rule and ended first: `ended`, `failed:<code>`, `not_confirmed:<code>`); `cpu`, `priority` and `check` are `none`. Reasons: `profile_missing` (Win32 2 or 3), `profile_unreadable:<code>` (Win32 error, or an `HRESULT` of the known folder as an unsigned number), `profile_reparse_point`, `profile_not_a_file`, `profile_invalid`, `method_unsupported` (`watch` until P3-4), `path_mismatch`, `topology_unavailable`, `topology_invalid`, `selection_empty`, `mask_too_wide`, `spawn_failed:<code>`, `job_failed:<code>`, `read_back_failed:<code>`, `mismatch`, `cpu_sets_failed:<code>`, `resume_failed:<code>`, `elevation_required`. An elevated shim and a token that is no profile ID write nothing, so they have no reason.
- Exactly one record per start with a profile ID, written right **before** the wait for the game: after the check, after an unchanged start, after a start that failed. Steam's "Stop", which ends the shim, cannot lose it; the exit code is not in it. A failed write changes neither the start nor the exit code.

### Writer (B13, D5)
- `run` writes only if the shim does not count as elevated (the same `elevated()` as for the profile, M1); `WinOs::write_result` asks again and refuses (`Elevated`). Never a write without a profile ID or for an unusable command line.
- `crates/rerun-launch/src/win/result.rs`, the one wrapper module of the shim's file writes (ADR 0007 amendment 2026-11-08): `Rerun` and `launch` opened as themselves (`FILE_FLAG_OPEN_REPARSE_POINT`, `FILE_FLAG_BACKUP_SEMANTICS` only to open a folder; a non-elevated process holds no backup privilege to enable) and refused if a reparse point or not a folder; held without `FILE_SHARE_DELETE` until the end; `Rerun` is never created, `launch` is created if missing (`CreateDirectoryW`, then opened and checked). The temp file `<id>.<pid>-<nanos>.tmp` is created with `CREATE_NEW`, share mode 0 and `FILE_FLAG_OPEN_REPARSE_POINT`; its final path must be the `launch` handle's plus its name (`Escaped` otherwise). An existing `<id>.result` that is a reparse point or a folder refuses the write: the reparse refusal of the profile read (D2 as built: links at `Rerun`/`profiles` followed) is **not** taken over here (security review condition). Rename by the temp file's handle (`FileRenameInfoEx`, replace if exists, POSIX semantics, so a reader holding the old file does not block it) to the full path below the held folders, since `SetFileInformationByHandle` refuses a `RootDirectory` (87, measured); the renamed file's final path is checked the same way. A failure before the rename deletes the temp file by handle. No flush: a lost record after a power cut is harmless.
- The result file is Rerun-owned state like the journal: `revert` and `forget` of a profile leave it; the next start of the profile replaces it.
- `crates/rerun-launch/tests/hardening.rs` now starts the shim end to end with a token that is no profile ID (it used an unknown ID): with a valid ID the shim would write into the real `LocalAppData\Rerun\launch` of a machine that has the folder.
- No new import: every new call is in `kernel32.dll`. Release binary: 359,424 bytes (x64, 2026-11-08).
