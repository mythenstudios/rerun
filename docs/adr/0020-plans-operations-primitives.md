# ADR 0020 · Plans, operations and primitives

**Status:** accepted (decided by the user) · 2026-11-05 · replaces the `Primitive` trait of `docs/01-architecture.md`; builds on ADR 0017, ADR 0018, ADR 0019

## Context
`docs/01-architecture.md` gave every primitive its own `plan`, `apply`, `verify` and `revert` over `&dyn System` (audit A1 nit: not over root types). The four phase 2 primitives (`file_install`, `registry_set`, `compat_layer`, `ini_set`) share a handful of effects: create a directory, create or replace a file, create a key, set a value. Each effect needs the same guard, intermediate phases, journal records, crash and power-loss tests (ADR 0017, ADR 0019); per primitive they would be written and tested four times. Phase 2 also needs an input before the Topo engine exists (phase 4), a plan hash that binds preview and apply, and rules for a revert that meets changed state.

## Decision

### Primitives are planners, effects are op kinds (user decision D9)
A primitive turns its spec into ops; `exec` applies, verifies and reverts op kinds. The round-trip test `apply → verify → revert → snapshot identical` stays mandatory **per primitive** (`docs/09-testing.md`); the crash, power-loss and tamper tests run per op kind.
```rust
// prim: durable spec types (serde, deny_unknown_fields) and one planner each
pub enum Step { FileInstall(FileInstallSpec), RegistrySet(RegistrySetSpec),
                CompatLayer(CompatLayerSpec), IniSet(IniSetSpec) }
pub struct PlanCtx<'a> { pub game: &'a GameDir<'a>, pub app: &'a AppDir<'a>,
                         pub sys: &'a dyn System, pub reg: &'a RegPolicy }  // reads only
pub fn plan(steps: &[Step], ctx: &PlanCtx<'_>) -> Result<Plan, PlanError>;

// plan
pub struct Plan { pub format: u32, pub roots: Vec<PlanRoot>, pub ops: Vec<Op> }   // format 1
pub struct PlanRoot { pub kind: RootKind, pub path: RootPath, pub id: RootId,
                      pub origin: PlanOrigin, pub main_exe: Option<RelPath> }
pub enum RootKind { Game }                    // `UserData` reserved (D6, phase 4)
pub enum PlanOrigin { Steam { store: RootPath, store_id: RootId, app_id: u32, installdir: RelPath },
                      Manual }
pub struct RootIx(pub u16);                   // index into `roots`, one per file op (condition S4)
pub enum Op {
    CreateDir   { root: RootIx, path: RelPath },
    CreateFile  { root: RootIx, path: RelPath, content: ContentRef, attrs: Attrs },
    ReplaceFile { root: RootIx, path: RelPath, old: FileState, content: ContentRef, attrs: Attrs },
    CreateKey   { slot: RegSlot, key: RegKey },
    SetValue    { slot: RegSlot, old: Option<RegValue>, new: RegValue },
    IniValue    { root: RootIx, path: RelPath, old_file: FileState, section: String, key: String,
                  old: Option<String>, new: String },
    TokenList   { slot: RegSlot, old: Option<RegValue>, add: Vec<String> },
}
pub struct FileState { pub sha256: [u8; 32], pub len: u64, pub attrs: Attrs }
pub enum ContentRef { Package { id: String, version: String, file: RelPath, sha256: [u8; 32], len: u64 } }
pub struct PlanHash(pub [u8; 32]);

// exec
pub enum Observed { Before, After, Drifted, Foreign }
// `fr`: roots are reopened through policy::root (StoreDir::open / game, GameDir::open_manual)
pub fn apply(sys: &dyn System, fr: &ForbiddenRoots, app: &AppDir<'_>, plan: &PlanHash) -> Result<TxnId, ApplyError>;
pub fn verify(sys: &dyn System, fr: &ForbiddenRoots, app: &AppDir<'_>, txn: &TxnId) -> Result<Vec<(usize, Observed)>, ExecError>;
pub fn revert(sys: &dyn System, fr: &ForbiddenRoots, app: &AppDir<'_>, txn: &TxnId) -> Result<RevertReport, ExecError>;
// rebind: `rebind_check` and `revert_rebound` with the binding the preview showed (P2-14 amendment)
pub fn forget(app: &AppDir<'_>, txn: &TxnId) -> Result<(), ExecError>;
```
- Ops whose old and new state are equal are not emitted (the same hash and attributes, the same value, a token already present). A plan without ops is "nothing to do" and starts no transaction.
- Every missing directory is its own `CreateDir`, every missing key its own `CreateKey` (ADR 0004). There is no delete op in phase 2: deleting is only ever a revert.
- `roots[]` with an index per op lets a plan span several roots and keeps room for `UserData` (D6) without a format change.
- An op that needs admin (an `HKLM` slot, a root the user cannot write) is marked `NeedsHelper` by the planner; phase 2 refuses such a plan, phase 3 sends that part to the helper. A non-elevated `AccessDenied` never escalates (ADR 0007).

### Plan hash
- `rerun plan` serialises the plan **once**; those bytes are the preview's source, are stored as `<AppDir>\plans\<hash>.json` and become `head.json` of the transaction (ADR 0019). `PlanHash` is SHA-256 over exactly these bytes. Nothing is serialised again for hashing.
- Head types use `BTreeMap` only, never `HashMap`; `RootId` (serial and file ID), every SHA-256 and every byte string (`REG_BINARY`, `Raw` data) are lower-case hex strings (no JSON number above 2^53); `format` is part of the hashed bytes.
- `apply` takes the hash the preview showed, reads the stored bytes (bounded), refuses unless their hash matches, then parses them as untrusted input. The hash binds what was previewed to what is applied and catches accidents; it is not a security boundary, the re-checks below are.

### Preview
Every op is shown before anything happens (core rule 5): root and path, key and value name, old and new value, content source and hash, attributes, and once per plan what a revert does not restore (ADR 0017, D3). Every untrusted field reaches output only as `escape::Shown` (condition S9; ADR 0016): `escape::path` for paths and value names, `escape::text` for values, INI sections and keys.

### Apply
In this order, all before `head.json` is written (ADR 0019): take the lock; check the hash; reopen every root through `policy::root` and `ensure_id`; for a Steam root re-read the app state, and refuse `UpdatePending` and `NotInstalled` (ADR 0012); **the game must be closed** (user decision D4): `users()` of every existing file-op target and of each root's main executable must be empty, else `Busy` with "<exe> is in use; close the game and try again later"; check stacking (ADR 0019); re-observe every op's old state (guard hash, value read) and refuse with `Mismatch` ("changed since the preview; plan again") on any difference. Then op by op (ADR 0019 write order), `verify` (every op must observe `After`), flushes, `Applied`. Any failure after the first change rolls back at once (ADR 0019, B-2). Revert checks D4 and the Steam state the same way.

### Observing and reverting
Each op kind observes its object on disk, never trusting a record alone:
- `Before`: as before the op. `After`: exactly as the op left it. `Drifted` (semantic ops only): the surrounding content changed, Rerun's own part is still exactly as it set it. `Foreign`: anything else.
- `After` is reverted, `Before` needs nothing, `Drifted` gets a semantic revert, `Foreign` is **never overwritten or deleted** (user decision D10, replacing "otherwise ask" in `docs/06-security.md` and `docs/02-topo-format.md`): the op stays unresolved, its backup stays in the journal, `status` names the backup's location, and `forget` closes the transaction after a preview.

| Op | `After` / revert |
|---|---|
| `CreateDir` | exists with the file ID from `Done`, empty / `remove_dir` by that ID; not empty or another ID: `Foreign` |
| `CreateFile` | content hash, one link / guard + `delete(expected)`; a user-edited file (a `config` file) is `Foreign` |
| `ReplaceFile` | new hash / guard + `replace(expected new, backup, old attributes)`; old hash is `Before` |
| `CreateKey` | exists, no values or subkeys / `delete_empty_key`; with content `Foreign` |
| `SetValue` | value equals `new` / set `old`, or delete it if there was none; equals `old`: `Before` |
| `IniValue` | file hash as written / restore the backup bytes; otherwise our key still has `new`: `Drifted`, set the key back to `old` (or remove it) in the current content and keep everything else; our key changed: `Foreign` |
| `TokenList` | value as written / restore `old`; otherwise our tokens still present: `Drifted`, remove only them (delete the value if nothing is left and there was none before); a token removed: `Foreign` |

For `ini_set` the semantic revert is the normal path, not an exception: games rewrite their INI files on every start, so `After` rarely holds by the time of a revert. The INI editor changes only the value span (line endings, encoding and every other byte kept), so a semantic revert of an unchanged file gives exactly the old bytes; the round-trip test pins that. The deviation is row X5 of the table "Exceptions to core rule 2". A semantic revert writes through `FileGuard::replace` with the hash just observed as the expected one.

### Exceptions to core rule 2 (audit A3 S1)

Core rule 2 says a revert restores the state before the first change exactly. These are all the documented places where it does not, collected in one table (A6 checks the code and the docs against it; every new primitive adds its rows). Behaviour is unchanged; the amendments below keep the details. "Where the user is told" is the preview, or, for a case that arises only at revert time, the report of `revert` and `status`. A row without a pinning test says so. The runtime effects of `rerun-launch` (job membership, CPU Sets, the priority class of a running game) are not system changes in the sense of rule 2 and have no row here: they belong to the process and end with it; what it writes (the launch profile) is an ordinary file op of the plan (ADR 0022).

### Rebind (user decision D5; rewritten by the P2-14 amendment, senior-dev B1)
After a moved Steam library, an app moved to another library or a reinstall, a revert halts at that root (gone: the library or the folder not found, no manifest, not installed; 6b-d) or is refused (`IdentityMismatch` of the library or of the game folder; E3). A rebind binds that root to the head's install folder in the Steam library that holds the app now, only if all hold: the transaction is applied; exactly one root does not open, and it is a Steam root (manual roots are never rebound); no file op of that root has a `RevertIntent`; the app is installed in that library in the head's install folder (P2-14b: the Steam scan finds exactly one such library, every listed library readable); the folder there opens through `policy::root` and the user can write it; every file op of that root observes `Before`, `After` or `Drifted` there (only `Foreign` refuses; games rewrite their INI files); and the user confirms a preview showing the old and the new folder (path, library, identity) and what the revert meets there. A created folder is proven by the file ID found there at the confirmed preview, recorded in the `Rebind` (a copy has new file IDs). The revert takes exactly the binding the preview showed (`revert_rebound(cx, txn, &RebindTo)`, not a `rebind: bool`), derives it again under the lock and refuses on any difference before its record. The `Rebind` record is written (flushed) first; the head is never rewritten, registry ops stay at its locations. Otherwise the transaction stays as it is and only `forget` closes it.

### Input until the Topo engine (user decision D7)
`rerun plan <steps.json>` reads a JSON step file: a throwaway envelope (`format: 1`, the game as a Steam app ID or a folder, `steps`) around **durable step objects**: each step is an object with exactly one key, deserialised into the spec types above with `deny_unknown_fields`. `registry_set`, `compat_layer` and `ini_set` are the Topo step objects of phase 4 and enter `schema/topo.schema.json` with their primitive (ADR 0005); `file_install` is what a Topo `package` step expands to (the package's files with their hashes) and is not a Topo step itself. The file is read through `policy::root` (its folder opened read-only by absolute path, the file a single segment), at most 1 MiB with a bounded read; every path field is parsed as `RelPath`, hashes follow `docs/02-topo-format.md`. No YAML at run time before phase 4.

### First primitive: `file_install` (user decision D11)
Sources are files below `<AppDir>\packages\<id>\<version>\` (`id` and `version` with the rules of `docs/02-topo-format.md`), each with a fixed SHA-256 in the step. In phase 2 only test fixtures are placed there (tests, the sandbox script); downloads, slots, `requires` and reference counting are phase 4. The planner emits `CreateDir` per missing parent, `CreateFile` for an absent target and `ReplaceFile` (old state from a guard) for an existing one; a source is opened sharing read only and is hashed while it is streamed into the temp file (ADR 0017). Audit A2 runs after this primitive.

### Moved
- `UserData` roots (`Documents`, `My Games`) to phase 4 (user decision D6: OneDrive placeholders and redirection need their own rules); the plan format already has `roots[]` with a kind.
- `gpu_preference` to phase 4 with `gpu.hybrid` and `gpu.integrated` (user decision D8; slot reserved, ADR 0018).
- The UAC VirtualStore warning (ADR 0007 "Open for Phase 2") to phase 3.

### CLI
`rerun plan <steps.json> [--dry-run]` (preview and `PlanHash`; without `--dry-run` the plan is stored), `rerun apply <plan-hash>`, `rerun revert <txn> [--rebind]`, `rerun status` (transactions with their state, unresolved ops, pending cleanups, backup locations), `rerun forget <txn>`. `apply`, `revert` and `forget` take the journal lock; `plan` and `status` do not. Output rules of ADR 0016.

## Alternatives
- **The per-primitive trait of `docs/01`:** four copies of the guard, phase, journal and crash logic; planners without a system are pure and cheap to test.
- **Hashing a re-serialised `Plan`:** serde output and map order are not stable across versions; a byte change would make an approved plan unappliable, or worse, a different plan hash the same.
- **Asking on revert** (the former "otherwise ask"): a dialog at revert time invites "overwrite" and destroys the user's or a mod manager's change; `forget` is explicit and keeps the backup until then.
- **Automatic rebind by app ID or name:** could attach a journal to a different folder.
- **YAML input in phase 2:** a run-time YAML parser before the loader rules of phase 4 exist (ADR 0005, ADR 0015 open point).
- **Restoring the INI backup whenever it matches, else refusing:** fails on nearly every game that rewrites its INI on start.

## Consequences
- `rerun-core` modules: `prim` (spec types and planners), `plan` (`Plan`, `Op`, `PlanHash`, storage), `exec` (apply, verify, revert, forget, `Observed`), `journal` (ADR 0019). `serde` with `derive` becomes a direct dependency of `rerun-core` (already in `Cargo.lock` through `serde_json` and `rerun-proto`), justified in its commit.
- `docs/01-architecture.md` (modules, primitives), `docs/02-topo-format.md` (`config: true`, `package`), `docs/03b-gpu-display.md` and `docs/08-roadmap.md` (`gpu_preference` in phase 4), `docs/06-security.md` (scenarios 6, 9, 10, 14) and `docs/09-testing.md` follow in the same commit.
- Core rules: rule 4 (no op kind runs code; content only from pinned hashes; roots and registry slots through policy), rule 5 (preview from the stored bytes), rule 2 (`Observed`, D10, LIFO), rule 6 (`NeedsHelper` refused in phase 2).

## Open points
- Exit codes of the new commands (refused before any change vs. rolled back vs. left open): fixed with the CLI step. **Closed (P2-13):** ADR 0016 amendment P2-13.
- The INI editor's accepted encodings and syntax (UTF-8, ANSI, UTF-16 with BOM; comments, duplicate keys, keys outside a section): P2-12, failing closed on anything ambiguous.
- `compat_layer` token list: P2-11 (ADR 0018).

## Amendment (P2-8, 2026-11-06; decided by the user after a senior-dev cross-check)

### Wire form of format 1 (`rerun-core::plan`)
- `{"format":1,"roots":[…],"ops":[…]}` exactly as `serde_json::to_vec` writes it: no whitespace, fields in declaration order, `deny_unknown_fields` everywhere, no maps. Enums are externally tagged in `snake_case` (`{"create_file":{…}}`; a unit variant is its name, `"origin":"manual"`). A SHA-256 is 64 lower-case hex digits, a `RootId` the string `<16 hex>-<32 hex>`, `Attrs` `{"readonly":…,"hidden":…,"system":…}`, paths are strings with `\` (`RelPath::parse` and `RootPath::new` again on read). Lengths are JSON numbers (at most 2 GiB).
- `ContentRef::Package` carries `config` (the step's `config: true`, shown by the preview), so the preview needs nothing but the plan.
- **One form:** `decode` checks `format` first (another value is `PlanError::Format`), parses strictly, and accepts the bytes only if re-encoding the result gives the same bytes; so `/`, a lower-case drive letter, whitespace or another field order is refused (`NotOneForm`), not normalised. Then the bounds of `encode`: at most 128 ops, 8 KiB per op serialised, 1 MiB per plan, 16 roots (no root listed twice, a Steam app ID ≥ 1), every `RootIx` inside `roots`, one op per object (root index and folded path), package ID and version by `docs/02-topo-format.md` and a valid segment, contents and old files at most 2 GiB, old files at most 4 GiB together, no `ReplaceFile` whose new hash equals the old one (ADR 0017 A2).
- `store` writes `plans\<hash>.json` with `create_new` and flushes `plans\`; the same bytes again are `Ok`, other bytes under the name are `HashMismatch`. `load` reads at most 1 MiB and refuses bytes that do not hash to the name.
- **Objects** (stacking, ADR 0019 B-2): `(RootId, folded path, created directory?)` per op; two overlap if equal, or if one is a directory an op creates and the other lies below it. Root identity, not the root index or app ID, so two Steam apps sharing one install folder overlap. Two different roots of which one lies inside the other (a manual root inside a Steam install folder) overlap as a whole, whatever the paths (fail closed, review S2).

### `file_install` and the planner context
`PlanCtx { game, app, steam_app, main_exe }` (no `sys`: the planner reads through the `GameDir` and `AppDir` handles; `RegPolicy` joins with P2-9). A Steam root needs its app ID, a manual one has none. Same content is no op whatever its attributes (senior-dev B1); new files get no R/H/S; refusals as in `docs/02-topo-format.md` and `prim::file_install`.
- **Name spelling (audit A2-B1; ADR 0017 D3: the case of a name is part of "exact").** The planner writes every existing segment of a target in its stored spelling (`Dir::stored_name`, `FileNameInformation` on an attribute-only handle, as the guard), whatever the step says: a replace names its target as the folder holds it. A segment the plan creates keeps the spelling of the first step that creates it; a new file keeps the step's. `exec` compares the guard's name (`FileGuard::name`) with the plan's last segment exactly (`RelPath::same_spelling`: `==` on a `RelPath` folds) in the old-state check and again on the apply's guard before backup and intent; another spelling is `Mismatch`. So the planned spelling is the one the file had when it was applied, and a recovery that renames `X.old` or `Yi.old` back in phase B renames onto it (before: onto the step's spelling, a silent snapshot difference at 4 of 217 crash points). A target found in another spelling after the apply (someone renamed it, case only) is not the planned object: the observation of a replace counts it as "other" in `S0` and every `Si`, so `verify` and the revert report it `Foreign` and leave it as the user named it (review S1); the restore checks the spelling on its own guard again (`Mismatch`). Existing ancestors are only opened, never renamed; their spelling in the plan is for the preview.

### `exec` (P2-8)
```rust
pub struct ExecCtx<'a> { pub sys: &'a dyn System, pub fr: &'a ForbiddenRoots, pub app: &'a AppDir<'a>, pub tag: InstanceTag }
pub enum Outcome { Nothing, Applied(TxnId) }
pub fn apply(cx: &ExecCtx, h: &PlanHash) -> Result<Outcome, ApplyError>;   // Refused | RolledBack | LeftOpen
pub fn verify(cx: &ExecCtx, t: &TxnId) -> Result<Vec<(u16, Observed)>, ExecError>; // read only, no lock
pub fn revert(cx: &ExecCtx, t: &TxnId) -> Result<RevertReport, ExecError>;  // also recovery; rebind with the CLI
pub fn forget(cx: &ExecCtx, t: &TxnId) -> Result<(), ExecError>;
```
- **Apply.** Nothing is written before `begin`: the stored plan (bounded, hash) is decoded; no ops is `Outcome::Nothing` (no lock, no transaction). Then the lock and the listing (stacking only there, below); every root reopened and checked by identity (a Steam root through its store, `app_manifest` with the plan's install folder and `Installed`, else `Refusal::Steam`); `!user_writable` is `NeedsHelper`; `users()` of every existing target and main executable (`Busy`); every created object still missing, every replaced file's guard holding exactly `old` (hash, length, R/H/S, one link), every source still hashing to its content (`Mismatch { op }`). Then `begin`; per op the order of ADR 0019, a replace checking the guard against `old` and asking `users()` on the guard again before backup and intent (senior-dev conditions 5 and 8); every op observed `After`; the touched game folders flushed (after every guard is dropped); `Applied`. A failure after `begin` runs the revert loop on the same writer and closes `RolledBack`; a failure between `begin` and the first intent leaves nothing to revert (closed `RolledBack`, or `Empty` if even that failed, which blocks nothing). A rollback that fails or meets a foreign op is `LeftOpen`.
- **Stacking on the listing** (only `list` sees a duplicate `seq`): a forgotten, closed or empty transaction blocks nothing; a `view` error, a damaged one without a usable head, a head whose hash differs from the listing's on its one `load` (condition 6) or that `decode` refuses (more than 128 ops included) is `Blocked` for every apply and for the revert of every earlier transaction; an open one, an applied one with any `RevertIntent` (condition 3) and a damaged one with a usable head have their head's objects open (`Interrupted` on overlap); an applied one is stackable. Revert is LIFO: a later open or applied transaction on an overlapping object is `Later`.
- **Revert = recovery = rollback**: the lock, the listing (the own entry must not be damaged), `resume`, `decode(w.head())` (the bytes read under the lock; refused: only `forget`), records that fit the head (an intent per existing op, temp names and backups by op kind, a replace's `BackupRef` equal to its `old`: else `Blocked`), LIFO, roots, Steam, `users()` of the intended targets; then newest op first: observe, `RevertIntent` (a temp name only when a restore starts, B2), act, flush the op's game folder (always, ADR 0019 amendment P2-8: a durable `RevertDone` must have a durable change and a durable undo of a failed sequence), `RevertDone`. With a restore, a `.old` holding `h0` is deleted only after the restore succeeded (review S1), so a damaged backup never costs the last copy of the old content. A foreign op gets `RevertIntent` and `RevertDone { Foreign }` and the lower ops are still reverted (**user decision D3, R1**); the transaction stays open, `RevertReport::closed` is `None`, only `forget` closes it. `verify` is the read-only preview of what a revert will meet (rule 5).
- **Observation** (every hash on a guard; a link count other than 1, other R/H/S, a restricted entry or a reparse point is "other"):
  - `CreateDir`: missing → `Before`; empty with `Done.file_id` → `After`, removed by that ID; otherwise `Foreign`. Without `Done` (**user decision D1**): the in-process rollback uses the call's result (an ID from `create_dir`; `AlreadyExists` from `create_dir` or `create_new` is foreign, never removed: condition 4); the recovery removes an empty directory by the ID it finds then, not empty is `Foreign`. `verify` counts a created folder holding only the targets of the plan's later ops as empty.
  - `CreateFile` (`X`): target missing → `Before`, `X` deleted; target `h1` → `After`, deleted with `h1` expected, `X` left; anything else `Foreign`, `X` deleted unless the target holds `h1`.
  - `ReplaceFile` (**senior-dev B2**): `S0 = (X, h0 → h1)` and one `Si = (Yi, h1 → h0)` per `RevertIntent` with a temp name. The newest `Si` whose `Yi` or `Yi.old` exists decides, else `S0`, by the table of ADR 0017 A3 for its direction: `S0` phase A or B → `Before` (B renames `X.old` back with `h0` expected), C or D → `After` (C deletes `X.old` with `h0` expected) and restore; `Si` phase A or B → `After` (B renames `Yi.old` back with `h1` expected) and a new restore, C or D → `Before`. A `X.old` holding `h0` next to a target holding `h0` after a restore was intended (or with `Done.old_left`) is the pending cleanup of step 8, not foreign. Once some `Si` decides, every earlier sequence completed (the ordered log of the folder's volume), so `X` and older `Yj` are no temp files of Rerun any more; a `.old` of them holding the expected hash is still cleaned up. Restore: `users()` on the guard, then `replace(h1, backup_reader(k), NewFile { Y, old R/H/S, sha256: BackupRef.sha256, max_len: BackupRef.len })`: the backup is checked while it is written, never before (TOCTOU). A step 8 that fails gets one more try on a fresh guard; still `Busy` (mapped) leaves `Y.old` as a pending cleanup named in the report (open point below).
- **Forget** (**user decision D2**): an empty, open or applied transaction (by the listing) is resumed and closed `Forgotten`; a damaged one, or one whose view is an error, gets the marker `journal\<txn>.forgotten` (ADR 0019 amendment). Backups stay.

### Open points (P2-8)
- A `.old` left mapped after a revert (`RevertDone.old_left`) is not cleaned up by a later run yet (cleaning up other transactions' `.old`, phase 5); the report names it. **Closed (P2-15):** the transaction stays open until a later revert of it deletes the `.old` with its known hash (amendment P2-15).
- `main_exe` is `None` for a manual root without a chosen executable (then only the targets are asked); fixed with the CLI step. **Closed (P2-13):** the step file requires `main_exe` (user decision E4 a).

- **Op form of registry slots (M2):** a registry op names a `RegSlot` whose executable is `{ root: RootIx, exe: RelPath }`, never a free-form path; `RegPolicy::check` builds the value name from `Plan::roots[root].path` (parsed again) on plan, apply and revert (ADR 0018 amendment P2-9).
- **6a, `CreateKey` without an identity proof (user decision a):** like D1 for directories: recovery deletes an **empty** key at the path of a `CreateKey` intent without `Done`; a key with values or subkeys is `Foreign`. P2-10 conditions: `Done` is written only for `create_key == true`; `false` (the key existed) is `Mismatch` and a rollback, never a delete (with a test); `verify` counts a key holding only later targets of the same plan as empty; the preview and `status` treat a game that fills the key or value later as the normal case (`Foreign`, then `forget`). Rest risk: `docs/06-security.md`, scenario 10.
- **6b, revert when a root does not open (user decision d, senior-dev):** the planner orders every registry op after every file op; `revert` opens roots lazily per op; a file op whose root does not open (for whatever reason) halts the revert **without a record**: the transaction stays open and resumable, and a rebind (D5) stays possible. Implemented in P2-10 (`exec`).
- **Op budget:** `SetValue { old }` cannot carry an old value of up to 1 MiB inside the 8 KiB op budget: the head holds `old: Option<ValueState { kind, len, sha256 }>` (small old values inline up to a limit), the bytes go to `Intent.before` or `op-NNNN.bin`; the preview shows kind, length and hash. `RegistryWrite::set(expected: Option<&RegValue>)` serves both (P2-10).
- **`create_key` errors (review S5):** after a failure past the create (its flags), the key may exist; `exec` treats an `Err` as "observe", never as foreign and never as "not created".
- **`RegWriter::delete_empty_key`** also deletes an empty key that existed before Rerun: `exec` deletes only keys it created itself (`Done` written after `create_key == true`), with a test.
- **Deserialising a `RegSlot`** (plan or journal) goes through `AsciiSeg::parse`, `AsciiName::parse` and `GameKey::new`, never through raw fields, so a manipulated journal cannot name a key the rules refuse.

### Dispatch by target (audit A2 should-item 3)
`Op::target() -> Target` replaces `Op::root()`/`Op::path()`: `Target::File { root, path, dir }` now, `Key` and `Value` with the registry op kinds (P2-10b). Every generic path matches on it: objects (`Object` is an enum by target, `root_path` always set) and "one op per object" in `plan`; in `exec` apply, observe, act, the record check, the game-closed check and the flushes (`Touched`: the game folders now, the hives with P2-10b; `flush_all` before `Applied`, `flush_for` the op's domain before each `RevertDone`). `exec::file` is the file domain behind it, unchanged; the revert loop stays one for every domain. The flush knobs of J6 are named by domain and place (`Flush::GameBeforeApplied`, `Flush::GameBeforeRevertDone`).

### Revert when a root does not open (user decisions 6b-d and E3)
An apply still needs every root open (`Roots::all`). A revert and `verify` open each root on its own (`Roots::each`) and sort it:
- **Open:** reopened and checked by identity. If the current user cannot write it (or its volume lacks POSIX semantics), its file ops cannot run; D4 still asks it (read access suffices).
- **Absent:** a manual folder whose path is not found; a Steam app without manifest, installed in another folder or not installed (the halt names which: `Refusal::SteamGone` or `Steam { NotInstalled }`). Extending E3's wording: a Steam library whose path is not found, and an app whose manifest says installed while its folder is not found. Only a `NotFound` of the open itself counts: `policy::root` reports a folder that changes while it is opened (`Dir::info` failing after the open, the `common` entry swapped) as `Busy` (review S-1). D4 does not ask an absent root, its file ops cannot run.
- **Undecided:** everything else (`UpdatePending`, a manifest that cannot be read now, `IdentityMismatch` (a rebind, D5, may bind it), busy (also the swap races above), access denied, a reparse point, forbidden). The revert is refused before any change.

D4 runs on the open roots (targets and `main_exe`; a missing `main_exe` is fine in a revert), and `Busy` refuses before any change. Then, newest op first, a file op whose root cannot run file ops **halts** the revert without a record (`Halt { op, root, why }`): `RevertReport { closed: None, halted: Some(..) }`, also at the first op (`Ok`, review N4). The transaction stays open and resumable, and a rebind stays possible. The halt is decided again on every run, so the revert goes on once the folder itself is back or the update has finished. A reinstall makes a new folder with a new identity: `IdentityMismatch`, undecided, refused until a rebind (D5). `verify` returns `Verified { ops, halted }`: newest op first; missing are the ops below the halt and the cleanly reverted ops of a root that cannot run file ops, while an op whose revert left it `Foreign` there is shown `Foreign` as recorded (security N-5). From P2-10b on, `check` refuses at encode and decode (the journal head is untrusted) any registry op before a file op, so a halt always comes after every registry op is reverted. The control K-R9 (every root opened eagerly, as before) fails H4.

### `verify` of a created directory (review S3)
`verify` observes newest op first, as a revert does, and hands each observation (`Seen`, with its actions) to the earlier ops. A created directory counts as gone what the later ops remove or never made: a target observed `After` or `Before`, and every temp name a later op deletes (`DeleteTmp`, review S-a). A later target observed `Foreign` stays, so the directories above it are `Foreign` too, as the revert will find them. Before, `verify` called them `After` (T2 changed accordingly), and called a folder holding only a later op's temp name `Foreign` while the revert closed it.

### The main executable and write access (user decision E2, review M1, S1; audit A2 should-item 8)
- A `main_exe` that is given must be a plain file of its root (not missing, not a folder, link or other reparse point, not restricted), checked by the planner (`PlanError::Step`) and again by the apply (`Refusal::MainExe`, before anything is written), since D4 would otherwise ask nothing about it. A revert tolerates a missing one. A file plan may still have none (its targets are asked; open point P2-8).
- Registry ops (P2-10b) need at least one root and a `main_exe` for every root: `check` refuses other plans on encode and decode, and the planner refuses a registry step without one. The hook is `Target::needs_main_exe` (false for files), so both rules apply as soon as the registry targets exist.
- Write access only for a root that file ops target (S1), in the planner and in the apply; D4 needs read access only, so a root without file ops may be read-only to the user.

### Registry op kinds in format 1
```rust
pub enum Op { /* file op kinds */
    CreateKey { slot: RegSlot, segs: u8 },   // the slot's key cut to `segs` segments below HKCU
    SetValue  { slot: RegSlot, old: Option<ValueState>, new: NewValue } }
pub enum NewValue { Dword(u32), Qword(u64), Sz(String) }   // {"dword":1} | {"qword":"<decimal>"} | {"sz":"…"}
pub struct ValueState { pub kind: u32, pub len: u32, pub sha256: [u8; 32], pub data: Option<Vec<u8>> }
pub const OLD_INLINE: usize = 1 << 10;      // `data` (hex) exactly when len <= OLD_INLINE: preview only
pub enum Target<'a> { File { .. }, Key { slot: &'a RegSlot, segs: u8 }, Value { slot: &'a RegSlot } }
pub(crate) enum Object { File { .. }, Key { key: RegKey, created: bool }, Value { key: RegKey, name: String } }
```
- A slot is written as `{"game_value":{"vendor":…,"product":…,"rest":[…],"name":…}}` (`compat_layers`/`gpu_preference` with `root` and `exe`) and read back through `AsciiSeg::parse`, `AsciiName::parse`, `GameKey::new` and `RelPath::parse` (ADR 0018 amendment P2-10b). `CreateKey` names its key by `segs` (`AllowedKey::cut`: below the anchor, at most the slot's key), so no key outside the slot can be expressed. `qword` is a decimal string (no JSON number above 2^53), without sign or leading zero.
- The old value of a `SetValue` is its type, length and SHA-256; its bytes ride along only up to 1 KiB, for the preview. The revert's source is always the journal (`Intent.before`, inline up to 16 KiB, else `op-NNNN.bin`). The worst case (the longest slot with a quote character, escaped to 2 bytes, in every segment and the name; 1 KiB of old data; a `REG_SZ` of 1,024 quote characters) is 5,345 bytes (review nit 6), inside the 8 KiB op budget (test P8).
- **`check` (encode and decode alike; the head is untrusted):** every slot passes `RegPolicy::check` with the plan's root paths (a `CompatLayers` slot is refused until P2-11, review N2; `GpuPreference` was reserved until P4-11), every new value `RegPolicy::check_new` (`PlanError::Registry`); every registry op comes after every file op (so a revert that halts at a file op has reverted every registry op, 6b-d); one op per key and per value (folded); `segs` within the slot; a `CreateKey` before every key and value below it; an old value with length at most 1 MiB, inline bytes exactly up to 1 KiB with the length and hash they claim, not equal to the new value, and absent in a key the plan creates; a plan with registry ops has at least one root and a `main_exe` for each (E2, review M1).
- **Objects:** a created key holds every key and value below it; a value is its key plus the folded name; a file and a registry object never overlap. `Object::of` fails closed: a slot the policy refuses is `Blocked`, never a missing object.
- **Preview:** the key (`HKCU\…`), the value name (`(default)` for `""`), the old value (numbers and strings decoded from the inline bytes, strings through `escape::text`; anything else by type, length and SHA-256; `missing`), a type change marked, the new value; once per plan with registry ops the note that a game filling the key or changing the value later (also with another type, review S4) is left as it is and closed with `forget`, and that a revert does not restore the last-write times of keys. This is the one place where old registry data reaches output (review N6; ADR 0016 output rules apply).

### `registry_set` (`prim::registry_set`)
- Step object (Topo step and step file alike, `deny_unknown_fields`; `docs/02-topo-format.md`, `schema/topo.schema.json`): `{"registry_set":{"key":"HKCU\\Software\\<Vendor>\\<Product>[\\…]","values":[{"name":…,"dword"|"qword"|"sz":…}]}}`. `key` begins exactly with `HKCU\Software\` (`HKLM\` and `HKEY_LOCAL_MACHINE` in any case are `NeedsHelper`); segments through `AsciiSeg::parse`, the key through `GameKey::new` (deny list, folded); 1 to 32 values with unique folded names (`AsciiName::parse`) and exactly one of `dword`, `qword` (decimal string, no leading zero), `sz` (`null` refused, review N5); every new value through `check_new`.
- `PlanCtx { game, app, steam_app, main_exe, reg }`: `reg` is a `RegReader` (`RegPolicy::reader`, the non-changing methods of the write side, so a link or volatile key on the way is refused, never followed). Per value: equal to the new value → omitted; otherwise `SetValue` with the old value's `ValueState` (another type, raw, more than 16 KiB included; over 1 MiB is `TooLarge`, refused). Missing keys (`missing_keys`, below the anchor) → one `CreateKey` each, top-down, once over all steps.

### `exec` for registry ops (`exec::reg`)
- **Dispatch:** `Target::Key`/`Target::Value` go to `exec::reg` (apply, observe, act, `records_fit`); `Touched` holds the hives an apply wrote into, the `RegWriter` and the system. Registry ops never halt and need no root; D4 asks the main executable of every root (E2).

| `CreateKey` | missing | `Before` |

| | anything else (another type, a `REG_SZ` without its NUL, a link or volatile key, too large) | `Foreign` (S4) |

## Amendment (P2-14, 2026-11-07; plan `P2-14` with the user decisions E-R1 to E-R6 and the senior-dev conditions; this is the core cut P2-14a)

### The binding of a root (user decisions E-R3, E-R4 a; senior-dev B2, S3)
- A recorded head is never rewritten. The `Rebind` records of a transaction (ADR 0019 amendment P2-14) bind its roots (`exec::bind::Bindings`): root `i` is the head's root, or the head's install folder `<store>\steamapps\common\<installdir>` in the library of the last `Rebind` of `i`, with that record's identities. The record names no game path (S3): app ID and install folder always come from the head.
- A binding acts only where a root is opened (`roots::open_root`): the file ops, the game-closed check (D4, also the executable of a compatibility layer) and the file objects of stacking. Every registry location is built from the head's roots (`plan::allowed`), so a `TokenList` reverts the `Layers` value under the executable path Rerun wrote, and a value under the new path is another object that is never touched. The control K-RB1 (the head's roots rewritten with the binding for the revert loop) fails RB-T3: Rerun's tokens stay in the old value.
- Checked on every revert, `verify` and stacking decision (the journal is untrusted, `docs/06-security.md` row 14): the root index inside the head; a Steam root; `old` equal to the identity bound before (the chain); a binding that changes the library, its identity or the folder's identity (a refinement of the draft's `old != new`: a library renamed on its volume keeps the folder's file ID); directory proofs only for `CreateDir` ops of that root; no `RevertIntent` of a file op of that root before the record (E-R3; the replay keeps the lowest op that had one). Any violation is `Blocked` (RB-T8).

### `CreateDir` in a rebound root (user decision E-R2 a)
The proof is the file ID the `Rebind` names for the op (`DirProof`), taken like `Done.file_id`: an empty folder (but for what later ops remove, in `verify`) with that ID is `After` and removed by it; without a proof only a missing folder fits (`Before`), anything else is `Foreign`. The IDs are those found at the check under the lock, which must equal the confirmed preview's (`Changed` otherwise), and they are the IDs the revert loop then checks. Before the record the observation takes the folder found there (`Proof::Found`, read only): exactly what the preview shows as "not provably Rerun's". The control K-RB2 (the proof from `Done.file_id` only) fails RB-T1.

### Stacking (user decisions E-R3, E-R6)
A transaction with a `Rebind` is of the open class (a revert has begun; P2-15: a transaction whose cleanup is pending cannot be rebound, every file op of its root has a `RevertIntent`, E-R3, so only `forget` ends it if its folder moved) and its file objects lie at the head's roots and at the bound folders until it is closed; applies on them are `Interrupted`, beside them they go on. The revert of an earlier transaction with an object in the new folder is `Later` (LIFO as before). An earlier transaction in the new folder is not looked at (E-R6 keeps `for_revert`; the draft's `Overlap` refusal is not taken). The control K-RB3 (objects from the head only) fails RB-T7.

### What `Reverted` means after a rebind (rule 2; senior-dev S2 and the docs/06 condition)
After a move, "the state before the first change" is that of the old folder, which exists only as the copy Steam made: `Reverted` means the bound folder is exactly as it was before the apply (Rerun's exact states restored there, registry exact at the head's locations), not every copy; an old folder renamed by the user (`Game.bak`) is not recognised and stays as it is. **Risk (S2, not measured):** what Steam keeps when it moves a library or an app (R/H/S, case, temp names, `.old` files) is unknown; any difference is `Foreign` and refuses the rebind (fail closed, then `forget`). No manual test is planned (`docs/09-testing.md`, open row). Table "Exceptions to core rule 2", row X9.

## Amendment (P2-15, 2026-11-07; plan `P2-15` with the user decisions E-C1 to E-C4 and the senior-dev conditions B1, B2, S1 to S4)

### The cleanup of a `.old` left mapped (E-C1 A, E-C3 a, E-C4)
- **Where it comes from:** a step 8 that stays `Busy` after its second try (a restore, a rewrite) and a `DeleteOld` that is `Busy` (the apply's `X.old` with `Done.old_left`, or the `.old` of an earlier sequence) leave the `.old`; `act` collects the sequence index (`Acted.old_left`), and the `RevertDone` names it (ADR 0019 amendment P2-15). Nothing waits or polls, and nothing deletes on reboot (`MOVEFILE_DELAY_UNTIL_REBOOT` is path based, needs administrator rights and acts in the background).
- **`cleanup_pass`** runs after the revert loop of every revert and every rollback that did not halt and met no foreign op, and in `verify` (read only, `Verified::cleanup`, rule 5). For every op whose `RevertDone` is not `Foreign`, every `.old` of `OpLog::pending_old` is observed: missing is `OldSeen::Gone`; another content, a link, a folder or a reparse point is `OldSeen::Foreign` (never touched, reported, the transaction still closes: E-C4, "foreign files at Rerun's names are not Rerun's changes", ADR 0017 amendment P2-15); Rerun's content (the start state of its sequence, `file::expected_old`) is deleted through a guard with that hash expected (`OldSeen::Deleted`; `Busy`: `OldSeen::InUse`) **only if the target still holds the state the revert left** (senior-dev S2: the end state of the op's newest sequence, the old content when the revert ran none; a replace: `Before`; an INI file: `Before`, or the end of its last rewrite). Otherwise it is `OldSeen::Kept`: it may be the last copy on disk of a state, and the target changed since the revert. (Precisely: the end state of the newest sequence with a temp name; if that sequence was recorded but never ran, the copy is kept too, conservatively, and only a deletion by hand or `forget` ends the transaction; review N3/N4, pinned by a test.) Something at the name that cannot be checked as Rerun's (access denied, a cloud placeholder, a restricted entry) counts as `Foreign`; a sharing violation on the guard is `InUse`. The pass does nothing but these deletions (no `DeleteTmp`, `RenameBack` or `DeleteTarget`). In `verify` a guard whose `users()` is not empty shows `InUse`, else `Ours` (what the revert deletes).
- **Closing:** `Closed` only if no item is `InUse` or `Kept` (`OldSeen::holds_open`). A revert then reports `RevertReport { closed: None, cleanup }`; a rollback ends as `ApplyError::CleanupPending { txn, cause, cleanup }` (senior-dev B1: "rolled back, cleanup pending", not `Closed { RolledBack }`); `ApplyError::RolledBack` carries the items too (only `Deleted`, `Gone` or `Foreign`). A root that cannot run file ops halts the pass before anything of its ops is touched (a `Halt`, no record), as the loop would.
- **Who cleans up (E-C3 a):** only an explicit `revert` of the same transaction: its checks (`revert_check`, D4, LIFO, roots), its preview (`verify`) and its question; a run with an empty loop goes straight to the pass. No apply, no revert of another transaction, no command of its own, never `status` (journal only).
- **A deletion is a change (senior-dev B2):** `revert_run` counts it; an error after one is never `Refused`, a `Closed` that fails after one is never "nothing changed".
- **The tenth flush site** (`Flush::GameBeforeClosed`): ADR 0019 amendment P2-15.
- **`status`:** `TxnLine::CleanupPending` (every op reverted, none foreign, a `.old` named by the journal); a transaction closed `Reverted` or `RolledBack` shows no cleanup item (it is closed only once there is none), a forgotten one shows them from the records (they may remain).
- **Stacking:** a transaction with a pending cleanup is of the open class with its own refusal, `Refusal::CleanupPending { txn }`, for an apply on its objects and for the revert of an earlier transaction on them (LIFO), with the text what to do (close the game and any window showing its folder, then revert it).
- **`records_fit`:** `Done.old_left` and a non-empty `RevertDone.old_left` only on a `ReplaceFile` or an `IniValue` (`Blocked` otherwise): the pass looks only where a `.old` can come from.
- **Tests** (`exec/cleanup_tests.rs`, `exec/cleanup_crash_tests.rs`, fake): CL-T1 to CL-T9 (`docs/09-testing.md`), the controls K-CL1 (closed despite the cleanup), K-CL2 and K-CL2b (the tenth flush site), K-CL3 (a cleanup without the hash); `exec/combo_tests.rs` checks over every run that a journal names a pending `.old` only where a mapping was injected. Windows: no own test; that the deletion of a mapped `.old` is `Busy` and succeeds once it is unmapped is W19 (the logic is the same in `exec` for the fake and Windows).

### Nits of audit A2 (P2-15)
- **N2, nested roots:** `plan::check` refuses a plan with a root inside another root (`RootPath::contains` both ways, also the same folder twice) under `Rules::Current` (planning, encode, apply): the rule of `Object::overlaps` and `Bindings::of` (`SharedFolder`) for the roots of one plan. ## Amendment (P3-3, 2026-11-08; plan `P3-3` with the user decisions E1 to E3 and the senior-dev conditions B1, A1 to A5; this is the format and `exec` cut P3-3a)

A launch profile (ADR 0022) is written by `apply` as a normal, journaled file op. Format 1 grows by three variants (additive: a head without them decodes as before) and `exec` by one root kind; the journal is unchanged.

### Format (`plan`)
- **`RootKind::Profiles`** with **`PlanOrigin::AppDir`** (`"kind":"profiles"`, `"origin":"app_dir"`): Rerun's `<LocalAppData>\Rerun\profiles`. Its identity is always **`PROFILES_ROOT_ID`** (`0000000000000000-00000000000000000000000000000000`) and it has no main executable (F1). No identity is kept: a `RootId` of `profiles` does not exist before the first run, and asking for one would create `profiles` before the preview (review S6 of `rerun plan --dry-run`); one fixed value keeps a plan's bytes and hash the same with and without `--dry-run`. `AppDir::path_of` gives the canonical path without creating anything.
- **`ContentRef::Inline { bytes, sha256 }`** (`{"inline":{"bytes":"<hex>","sha256":"<hex>"}}`, lower-case hex): the bytes the plan carries, at most `MAX_INLINE_BYTES` (2 KiB; a profile with a start path of at most 259 UTF-16 units is about 1.8 KiB, and as hex the op stays below `MAX_OP_BYTES`; the phase 3 plan's "8 KiB" is narrowed on purpose). `create_new` and `replace` check the hash while they stream it, as for a package file.
- **`profile_id(app_id)`** (`plan`, user decision E1 a, condition A4): the first 16 bytes of SHA-256(`"rerun-profile-id\0"` ‖ `1u8` ‖ `"steam\0"` ‖ the app ID as 4 bytes little-endian). One profile per Steam app: a new plan, another start or a moved library keep the ID and the pasted launch option. The domain tag leaves room for another form (without Steam) that cannot collide. Pinned by a test (app 220: `323ad79fbc93ca3e73b0b152a5d44616`, app 40960: `79ac7ab577e4075a93c65cf04abd5211`).

### The fence (`plan::profile`, encode and decode alike; condition B1)
The head is untrusted (`docs/06-security.md` row 14), so the fence holds for both rule sets where it is a rule of form:
- `kind: profiles` exactly with `origin: app_dir`; such a root has `PROFILES_ROOT_ID`, no main executable and a path ending, folded, in `\Rerun\profiles`; at most one; a plan with it has exactly two roots, a Steam game root at index 0 and the profiles root at index 1. **No game root carries `PROFILES_ROOT_ID`** (condition A2; the fake never hands out serial 0 with file ID 0, a test pins it).
- On the profiles root only `CreateFile` and `ReplaceFile`, as **op 0** (F3: a revert, newest first, reaches it last, so a missing `profiles` halts only once everything else is reverted), named `<32 lower-case hex digits>.profile` (one segment), content `Inline`, no attributes; the old file of a `ReplaceFile` at most 8 KiB (the shim's read limit). No registry slot names the profiles root.
- `Inline` only on the profiles root, at most 2 KiB, with the SHA-256 of its bytes.
- **`Rules::Current` only** (planning, encode, apply): the bytes decode as a launch profile (`rerun_proto::profile`), its `start` and `target` lie below the path of root 0 (folded), `start` has at most 259 UTF-16 units, the file name is `profile_id` of root 0's app, and root 0 names its main executable (P3-3c, review S2: D4 asks it also for a plan whose only op is the profile). A recorded head keeps only the form (a recorded profile head without a main executable is accepted; its revert then asks no main executable, as any head of before P3-3c would) (user decision E4 of P2-11): a revert observes hashes and never reads the profile, so no later rule blocks it.
- The rule "registry and INI ops need the main executable of every root" counts game roots only.
- The preview shows the profiles root as "Rerun's launch profiles", the source `inline (launch profile)` and the profile decoded (`ProfilePreview::Decoded`: ID, method, bitness, rule in the words of `docs/02-topo-format.md`, priority, start); bytes a recorded head carries that do not decode are a hint (`ProfilePreview::Unreadable`, the reason only), never an error of the preview.

### `exec` (condition A1, F2)
- `roots::Opened { Game, Profiles }`: the profiles root is opened only through `AppDir::profiles` (banned outside `exec` in `clippy.toml`; `profiles` is no `AppSub`, so `AppDir::sub_write` cannot reach it, review F1) (handle-relative below Rerun's folder with the write capability, a reparse point refused, its final path exactly `<AppDir>\profiles` on the same volume, else `Escaped`), never by the head's path, without an identity check. `ProfilesDir::dir_write` is for `exec` only (`clippy.toml`).
- **Apply** creates `profiles` if it is missing (`Create::IfMissing`, before `begin`, Rerun's own state like `journal`; no op of the plan, never removed by a revert or `forget`), and refuses with `Refusal::ProfilesMoved { planned, now }` before any change if its path is not the plan's now (`<LocalAppData>` moved since planning). An apply refused after that (another root, the game running, an old state that changed) may leave an empty `profiles` behind: Rerun's own state like `journal`, no change of the user's. `check` creates nothing (a missing `profiles` counts as empty there) and refuses the same way.
- **Revert and `verify`** never create it: missing is an absent root, so the revert halts at the profile op without a record (`forget` closes it). They work at the `profiles` of Rerun's folder **now**, whatever path the head names (A1): every profile op is decided by its hashes, so another path decides nothing; the difference is reported (`RevertReport::profiles_moved`, `Verified::profiles_moved`).
- The profile op is a plain `CreateFile`/`ReplaceFile`: write-ahead, temp name, backup of a replaced file, the folder flushed before `Applied` and before `RevertDone`, the observation table of ADR 0017. **No new X row for the profile itself**: it is a normal file op and reverted exactly (a created profile deleted when it holds `h1`, a replaced one restored to `h0`; anything else `Foreign`, never overwritten, the transaction open until `forget`). An old file Rerun finds at the name (a rest after `forget`) is replaced, and restored by the revert.
- **Stacking:** the objects of the profiles root are `PROFILES_ROOT_ID` and the folded name: two plans for the same app overlap (LIFO: the second replaces the first, the revert of the first is `Later` until the second is reverted), two apps' profiles never do.
- **Rebind:** the profiles root is never rebound (`Bindings::of` needs a Steam root at the record's index; a planted record for it is `Blocked`; `rebind_check` looks only at game roots, so a missing `profiles` does not make a moved game "more than one root", and a halt at the profiles op, which comes after every game op, does not refuse the rebind: it reverts the game ops and halts there, as a revert without a rebind; review F3). After a rebind of the game root the profile still names the old start (the shim reports `path_mismatch`); its revert runs normally.
- **The game folder gone before the revert (condition A3):** the revert halts at the newest game op, and the profile (op 0) stays. If the transaction is then closed with `forget`, the profile stays in `profiles` and keeps applying through the launch option until the user removes the option; the `forget` preview says so (P3-3d).
- **Program Files games (rule 6):** a plan whose only file op is the profile writes nothing in the game folder, so a game folder the user cannot write needs no helper; the planner's `NeedsHelper` rule counts root 0 only.

## Amendment P4-4 (2026-11-09): plans from a Topo, `PlanSource`, the anti-cheat rule
The Topo engine (`rerun_core::topo`, plan `P4` step P4-4 with the user decisions E2 a, E4 "a+" and the lead decisions L8 to L10) turns a Topo of the signed index (ADR 0024) into a plan of the existing primitives. `prim::StepFile` stays as the local, unsigned input (L8).

- **Match:** the Topos of the index whose `match.steam_appid` is the app; per Topo every `match.exes` entry is opened, parsed and hashed on the very handle that was parsed (`detect::exe::inspect_exe`, ADR 0014). An entry matches when the file is there with every hash it names (SHA-256 and SHA-1); a Topo matches when one entry does, and the first matching entry in the Topo's order is the plan's main executable. Exactly one Topo must match; another content, a missing file or two matching Topos offer nothing (a report says why). `appinfo.vdf` is not read (L9).
- **Report (no `--pick`):** per issue the `when` result here (ADR 0015 amendment P4-4), per variant its status, kind and what the engine says (refused and why, anti-cheat warnings). A report preselects nothing and stores nothing.
- **Plan (`--pick <issue>/<variant>`, at most one variant per issue, 1 to 32):** `when = no` is refused, `unknown` is planned with a warning (only ever on an explicit pick); a retired Topo is refused, `needs-retest` warned. Steps map one to one: `registry_set`, `compat_layer`, `ini_set` unchanged; a `cpu` step becomes the one `launch_method` step with the Topo's method, `launch.start` and `launch.priority` (two picked `cpu` steps are refused); `steam_input` is a hint, no op; `package` is refused until P4-7. `launch.method: auto` is resolved at planning time: `direct` when `launch.chain` is exactly `[steam]`, else `watch` (L10); the preview names the result. `hold`, `ifeo` and `inproc` refuse a `cpu` step until their phase. `launch.cpu` is not planned by P4-4 (open point below).
- **Same bytes:** the steps go to `prim::plan` unchanged, so a Topo plan without its `source` has exactly the bytes of a step file with the same steps (test TB).
- **`Plan.source`** (`PlanSource`, optional, omitted on the wire when absent): `{"index":"<sha256 of the signed index bytes>","topo":"<id>","rev":<n>,"picks":[{"issue":"<id>","variant":"<id>"},…]}`, the last field of the plan. Checked on encode and decode alike: IDs of the Topo form, `rev` from 1, 1 to 32 picks, each issue once. The index hash names the bytes kept under `<AppDir>\index` (ADR 0024), so a later revert and the elevated helper (P4-1, L8: helper ops only with a `PlanSource`) can find the signed data the plan came from (P4 condition R1). It is display and binding only: nothing in it authorises anything when read back.
- **Anti-cheat rule (user decision E4 "a+"):** `detect::exe::anti_cheat` looks for markers of anti-cheat systems (a fixed table with sources, `docs/05-sources-policy.md`) in the game folder and the folders of the Topo's executables and `launch.start`; any entry of a marker's name counts, an entry that cannot be asked counts too (fail closed, P4 risk R7). If one is found, `topo::policy::ANTI_CHEAT_RULES` decides per step kind: **refused** `package`, `laa_patch`, `firewall_rule`, `compat_layer` and a CPU rule with `watch` (it opens the protected process); **warned** a CPU rule with `direct`, `ini_set`, `registry_set`, `gpu_preference`; nothing for `steam_input`. The kinds of later steps are in the table now, so their planners inherit the rule. A Topo may release a system as dead (`anti_cheat: { dead: [...], source }`, `docs/02-topo-format.md`): a found system it names does not count; an unreadable marker always does. Until that field is reviewed it is draft only (`catalog::check::ANTI_CHEAT_RELEASE_REVIEWED`), so the signed index holds none yet.
- **CLI:** `rerun plan <target> [--pick …] [--dry-run]`: a target of digits only is a Steam app ID (the engine on the current index), anything else a step file; `--pick` with a step file is a usage error. The plan's origin and warnings are printed before the preview, which is the step file's (`plan::show_and_store`).
- **Tests (fake):** `topo/tests.rs` TW (`when` truth table), TM (match), TL (`auto`, the loader's `start` rule), TP (picks), TA (anti-cheat per E4, the dead release), TB (bytes equal to the step file, the source's form), TC (from an index signed with the test key); `detect/exe/anti_cheat.rs`; CLI `topo_tests.rs` C-TE1 to C-TE6.
- **Open points:** `launch.cpu` (a Topo-wide CPU rule outside a variant) is shown but not planned; whether it joins every plan of the Topo or becomes a variant is decided with the first Topo that needs it (P4-13). The anti-cheat markers without a vendor source (`EasyAntiCheat`, `EasyAntiCheat_EOS`, `GameGuard`, `XIGNCODE`, `EAAntiCheat.GameServiceLauncher.exe`) need one, or a dump of a real machine, before A6 (also on the A6 list of `docs/08-roadmap.md`); the third-party link for `start_protected_game.exe` is replaced by Epic's own documentation once found.
- **Review follow-ups (P4-4, senior-dev):** (1) the anti-cheat rule holds for **every plan source**: `rerun plan <steps.json>` looks for markers in the game folder and the folders of `main_exe` and of a `launch_method` start and applies `ANTI_CHEAT_RULES` per step kind (`file_install` counts as `package`); a step file has no Topo, so nothing is released as dead. (2) A marker the user may not open and a named folder that is a link or cannot be asked are `unreadable` (each named folder is asked once), never released by `anti_cheat.dead`, and trigger the rule without any find; a marker that is itself a link counts as found. (3) `hold`, `ifeo` and `inproc` are refused with anti-cheat (they open the process, sit in its start or run inside it). (4) Retired Topos are listed and never chosen; `check_index` (and with it `rerun-workbench index build`) refuses two Topos that are not retired with the same `match.steam_appid` and an executable hash in common, so at most one matches. (8) `match.exes` holds at most 8 entries (schema and loader). (9) A target of digits only that is 0 or above 4294967295 is a usage error, never a step file path.
- **Open point, the dead release (`ANTI_CHEAT_RELEASE_REVIEWED`):** unlocked in P4-13 with the first PunkBuster Topo; the schema's `if/then` (draft only with `anti_cheat`) and a `Rules::Release` test move with it, and a release is accepted only with a source of type `official` or `pcgw`.

## Amendment P4-7 (2026-11-10): the `package` planner

## Amendment P4-8 (2026-11-10): `Op::Hold`, DLL slots

- **The op:** `{"hold":{"root":<ix>,"path":"<RelPath>","content":{"package":{…}}}}` (`Op::Hold { root, path, content }`, `Target::File`, a file op: before every registry op, one op per object). A plan of nothing but holds changes nothing and starts no transaction (`prim::plan` clears it: "nothing to do").
- **`exec`:** the apply re-observes the held file on a guard (`roots::holds`: hash, length, one link, no cloud placeholder, the planned spelling; `Mismatch` otherwise, also in `check`), then writes `Intent` (no temp name, no old state) and `Done` with the file's ID. The observation is `After` while the file holds the content in the planned spelling and `Before` otherwise, never `Foreign`: a hold changed nothing, so nothing of it can be foreign, and its revert acts on nothing either way (`RevertIntent`, `RevertDone`). `records_fit`: no temp name, no old state, no restore, no `.old`. The journal's record forms are the existing ones (no ADR 0019 amendment).
- **Stacking (L7; superseded by amendment P4-8b for created files: they are handed over; it holds for replaced files):** the object of a hold is its file, so a later transaction that holds a file of an earlier one overlaps it, and the earlier one's revert waits until the later one is reverted (LIFO). The refusal has its own text when the later transaction holds one of the objects (`Refusal::Held`: "transaction T2 uses a file this transaction installed (a shared package file, such as a loader several fixes need); revert T2 first, then this one"); an apply over an interrupted transaction that holds the file is `Interrupted` as before. So reverting the first transaction never removes a file the second relies on, and reverting both newest first restores the game folder exactly.
- **E6 (deviation, recorded; closed by amendment P4-8b):** the user decision E6 of the P4 plan asks for more: the earlier transaction's revert removes its own parts while the shared file stays until the last holder is reverted (`docs/08-roadmap.md`, phase 4: "a revert removes its own files, a file another open transaction still holds stays until the last one is reverted"). P4-8 builds the conservative half: the shared file stays until the last revert because the earlier revert is refused until then. The handover (the last holder deletes a file it did not create, after the creator's revert kept it) is not built: it needs a cross-transaction rule for the deletion duty (owner reference in the hold, the owner's `RevertDone` read by the holder's revert, a forgotten owner) and also for folders: two ASI plugins put their files in one `scripts` folder the first transaction created, so the first one's `CreateDir` would have to be held as well. Open point below.
- **DLL slots:** a slot is a DLL a package puts into the game folder. The loader binds them (`catalog::check::slots_bound`, ADR 0025 open point): every file whose `to` is a `.dll` is a slot of the package for each API it is installed for (`slots`, or `slots_by_api` of that API), and once a package names files, every slot is installed by one of them. So the DLLs of a transaction's head (its package files) are exactly its slots. Conflicts are refused, never chainloaded (the format has no chainloading field yet; one comes with the first package that needs it): in one plan by the engine (`topo::slots_free`: two packages with a DLL at one place, "the slot of package X too … Rerun does not chainload DLLs"); against live transactions (open, applied, damaged with a usable head; an op not reverted yet) from their heads, by the planner (`prim::plan`, every plan source) and again by the apply and `check` under the lock (`Refusal::SlotTaken`: "op N: <dll> is the DLL slot of package X from transaction T; … revert T first, or keep that fix instead"). A DLL of the same package is no conflict (it is held). Folded paths and root identities as for objects; a head that cannot be read is left to stacking (`Blocked`).
- **`supports_exe_sha1` and `requires_gpu`** (ADR 0025 open point): a package that lists the builds it supports is planned only when the matched executable's SHA-1 (hashed on its parsed handle, `ExeCheck::sha1`) is listed, else `EngineError::Package`; the signed index also refuses a Topo whose `match.exes` names a SHA-1 a package it installs does not list. `requires_gpu: [vulkan]` is not checked (the architecture table knows a Vulkan version per architecture, but not the driver, and on a hybrid system not the game's adapter): the plan warns (`Warning::RequiresGpu`).
- **Preview (rule 5; the text of `HOLD_NOTE` superseded by amendment P4-8b):** `keep shared file <root>:<path> from <package> <version>: <file>`, `holds sha256 …, n bytes (not written)` (CLI: `holds: … (kept as it is, not written)`), and `HOLD_NOTE` once: the file is kept, this transaction relies on it, an earlier transaction that installed it is reverted only after this one, and this one's revert leaves it. `verify` and the revert report say "nothing to undo" for a hold.
- **X rows:** none. A hold changes nothing, so its revert restores exactly.
- **Tests (fake):** `exec/hold_tests.rs` H1 (round trip of a held file: the earlier revert refused with `Held`, nothing written, then newest first identical), H2 (holds only: nothing to do), H3 (the held file changed: `Mismatch`, and the creator's op finds it), H4 (a hold retargeted in the head touches only the transaction's own objects; a hold turned into a create does not fit its records: `Blocked`), H5 (`SlotTaken` at the plan and at the apply of an earlier plan; the same package is a hold; free again after the revert); `exec/combo_tests.rs` CM2 kind `StackHold` (T2 holds T1's file next to a replace: a failure and a crash at every call of T2's apply and revert, a power loss at every pair of cuts, the recovery newest first identical); `topo/tests.rs` TS1 (EaglePatch and a widescreen fix share the loader in two plans: the second holds it, the wrong order refused, the right order identical; the preview lines), TS2 (two packages of one slot in one plan and against an open transaction), TS3 (`supports_exe_sha1`, `requires_gpu`); `plan/tests.rs` p6 (wire form, rules, object, preview); `catalog/tests.rs` (slots bound to files, `supports_exe_sha1` over a Topo's builds); `prim/tests.rs` t9 (the same content is a hold); CLI `preview/tests.rs` (the hold lines).

## Amendment P4-8b (2026-11-10): E6 hand-over of shared files and folders

### Lead decisions (from the senior-dev cross-check)
- **B1, a recorded keep:** the creator records `RevertDone { observed: Kept }` (ADR 0019 amendment P4-8b: one more value, no new record, names no other transaction; `records_fit` allows it only for `CreateFile` and `CreateDir`). Only a `Kept` op makes a duty (not every `RevertDone { After }`), so the "handed over" of §1 is the `Kept` record, and a creator whose revert deleted its object (`After`) never makes one. Generations: a file duty needs the holder's `Done.file_id` equal to the creator's; a folder with another file ID than the creator's is not Rerun's (skipped, not reported as installed by it). Fail closed (HO8) only for a duty whose object still exists with the creator's file ID, read under the lock before the first record. Which entries count as unknown (review follow-ups, security 3, senior S-3; `share::read`): the journal reader lists every record of an entry that is readable and not damaged (it stops only at damage, `journal::read`), so a readable, undamaged entry whose records hold no `Kept` handed nothing over and never blocks; unknown are an entry whose records cannot be read (a view error), a damaged one (its listing holds only the valid prefix: a `Kept` may follow the damage), one that is not closed whose head cannot be used (its reliance is unknown), and a closed one with a `Kept` op whose head cannot be used, does not decode, is another than the listed one, does not bind its rebinds or does not fit its records (a creator whose objects are unknown). None of them is ever a basis of a deletion; while one exists, the revert of a transaction is refused (`Blocked`, before any record) as long as a file it holds still has the ID it recorded or a folder above one of its relying ops that it did not create is there (this covers every duty); a journal read that fails while the hand-over reads the other transactions is an error of the revert, never a creator skipped (found by the unreduced power-loss matrix). File IDs are assumed not to be reused for another object while a transaction records them (N1).
- **S1, the invariant:** every inherited or released deletion relies only on records read in this run under the lock and happens after this run's flushed `RevertIntent` of the carrying op. Control K-HO5 (the act before that intent) breaks "deleted under a live reliance" in the power matrix.
- **S2:** `for_apply` refuses a plan that replaces or edits a file a live `Hold` holds (`Refusal::HeldChange`).
- **S3:** a forgotten heir leaves the object only until a new holder holds it: the new holder's `Hold` records the same file ID and inherits from the creator's `Kept` op; the `forget` preview says so.
- **S4, cost:** forgotten, empty and rolled-back transactions are skipped from the listing; a closed one is read only if the reverting transaction has a relying op and its listed records hold a `Kept`; at most `MAX_SHARE_HEADS` (1,024) heads are read, else `Refusal::TooManyTransactions`. Measured: `ho_cost_with_500_closed_transactions` (docs/09).
- **S5:** the creator's ID chain is checked read only before the first record (`shares_hold`, also in `revert_check`): `Refusal::Held`, nothing changed (instead of the halt of §1).
- **S6:** a relying op is only a `CreateFile`, a `CreateDir` or a `Hold`.
- **S7:** retention keeps a closed creator with a `Kept` op, records included, while a transaction that is not closed has an op on that object (ADR 0019 amendment P4-8b).
- **N2, the rationale against an owner reference in `Op::Hold`:** for a file the user put there the owner is unknown at plan time, and a creator can be forgotten after the plan was made; the records at revert time are the only stable facts.
- **N3:** an heir with a `Rebind` gets no duty (X14). **N4:** `verify` of the heir predicts an inherited folder empty after its own later ops (the names they remove). **N5:** an open, not applied holder (an interrupted apply) counts as relying: the creator's revert waits (`Held`), and condition (d) counts every op with an intent and no `RevertDone`. **N6:** every reader of `RevertDone` was audited for `Kept` (status, CLI, the helper's report, the profile fate: a kept op is not foreign and its object stays).
- **Defaults (the user is informed):** (1) a file a transaction **replaced** stays newest first (`Held`): handing over a restore would need the creator's backup after it closes, a partial deviation from E6 for replaced files only; (2) a **forgotten holder** no longer counts, and the `forget` preview of every live holder names the files it holds ("after forget, the revert of T… may remove …"); (3) **changed inherited objects** are left and reported, and the inheritor closes (X14).

### Terms
- **Created object:** a file of a `CreateFile` or a folder of a `CreateDir` of a transaction `C` (the creator) with `Done`; its identity is the object of P2-8 (root identity, folded path) **and** `Done.file_id`.
- **Relying op:** an op of a later transaction `L` on a created object: a `Hold` of a created file whose content (hash and length) equals the `CreateFile`'s, or any file op whose object lies below a created folder (the overlap "below a directory an op creates" of P2-8) and overlaps no other object of `C` (a relying `Hold` of a file `C` created in that folder relies on both). A relying op **relies** while it has `Done` and no `RevertDone`.
- **Handed over:** the creator's op has `RevertDone { observed: After }` and the object still exists with the creator's file ID. Nothing else marks it: a revert that deleted the object destroyed that ID (NTFS file IDs carry a sequence number, ReFS IDs are not reused; volumes without POSIX semantics are refused anyway, ADR 0017), and a durable `RevertDone` has a durable act (flush before `RevertDone`, ADR 0019 P2-8).

### 1. Recording: derived, no new record
- **Creator side (`C` reverted first).** `for_revert` no longer refuses an overlap whose later op is a relying op that has `Done` and no `RevertIntent`, in a transaction that is not damaged and has no `Rebind` on that root; it returns those ops of `C` as **keep candidates** (with the later transactions). In the loop, a candidate is observed as today plus: a file `After` (hash, length, R/H/S, one link, spelling) whose current file ID equals `C`'s `Done.file_id` and every relying `Hold`'s `Done.file_id` is **kept**: `RevertIntent`, no act, the usual flush, `RevertDone { After }`. A folder with `C`'s file ID whose entries are exactly names the relying ops account for (the first segment below it of each relying object; S3 of P2-10a extended to later transactions) is kept the same way; an empty one is removed as today; anything else is `Foreign` as today (D10). A file `After` whose ID chain does not hold (rewritten with the same content, a copy) **halts** the revert before its record (`Halt { why: Refusal::Held }`; resumable, newest first then succeeds). `C` closes `Reverted`: P2-15's "nothing of Rerun's is left" now reads "nothing this transaction still owns".
- **Inheritor side.** Under the lock, before the first record (in `revert_roots`, and read-only for `verify` and `revert_check`), `stack::inherited` derives the **duties** of the reverting transaction `R` from the listing: for each relying op of `R` (only ops without `RevertDone`) and each created object it relies on, a duty exists iff (a) the creator `C` is earlier, listed, not forgotten, not closed `RolledBack`, its head usable and its records fit; (b) `C`'s op has `RevertDone { After }` (a creator op without `RevertDone`, also mid-revert, still owns the object: no duty); (c) for a file, `R`'s `Hold` has `Done.file_id` equal to `C`'s; (d) no other non-forgotten, non-closed transaction has an op on the object (a folder: at or below it) without `RevertDone`, the creator included. Disk facts (the current ID, content, emptiness) are checked in the loop, never in the derivation.
- **Where a duty is carried out.** A file duty belongs to `R`'s `Hold` of it; a folder duty to `R`'s lowest-index op at or below the folder (the last one its newest-first revert reaches there), after that op's own act, deepest folder first. The act: a file on a guard with `C`'s content, R/H/S, one link, the planned spelling and `C`'s file ID is deleted with its hash expected; a folder empty with `C`'s file ID is removed by that ID, and its parent joins the flush before the op's `RevertDone`. An object gone needs nothing; anything else is **left and reported** (X14 below), never deleted. The `Hold` keeps its observation (`After` or `Before`, never `Foreign`), so `records_fit` is unchanged.
- **Write-ahead and crash safety (ADR 0019).** The record before an inherited change is the carrying op's `RevertIntent` (flushed); what it does follows from durable records plus the disk, as a `DeleteTmp` follows from `Intent.tmp`. The evidence (`C`'s `Done` and `RevertDone`) are journal files on the same volume, written before that `RevertIntent`; its flush makes them durable with it (the ordered log, ADR 0019 amendment P2-3), so no cut keeps an inherited deletion and loses its evidence. A crash after the deletion: the next run finds it gone. A crash of `C` between `RevertIntent(k)` and `RevertDone(k)`: no duty exists (b), the holders release, and `C`'s next run decides again (with no holder left it deletes). A crash of a holder mid-revert: its op has no `RevertDone`, so the others defer to it (d) and its own next run inherits. Inputs change only under the lock, and a transaction mid-revert is open for stacking (an apply on its objects is `Interrupted`), so no new holder appears in between.
- **Fail closed.** If a duty arises and the listing holds a blocked entry (view error, unusable head) or a damaged one with a usable head and an op on that object, the revert is refused `Blocked` naming it, before any record (`forget` it, then revert again). Blocked later entries refuse as today.

### 2. Several holders: order independence
Invariant: a created object that exists with its creator's ID is owned by its creator while the creator's op has no `RevertDone`, and afterwards by the set of ops that rely on it without `RevertDone`. Reverts run one at a time under the lock; each leaves the set; the one that finds the set empty except itself (d) deletes, exactly once, with the expected hash and ID. Any order of `C`, `T2`, `T3` ends with the object deleted after the last revert, which is the state before `C`. A holder never needs another holder's records: every duty refers to the original creator's `Done.file_id` (no chain of hand-overs). A `Hold` over an earlier `Hold` of the same file no longer blocks (neither changed anything); LIFO between them is dropped.

### 3. `forget` and objects Rerun did not create
Rerun deletes only what a transaction it still tracks created. A **forgotten creator** gives no duty, before or after its hand-over: a forgotten transaction blocks nothing and is never acted on (D2), so its records are no evidence; the object stays (X11 and X14). A **forgotten holder** is no reliance (it blocks nothing): the remaining last holder deletes. A **forgotten inheritor** after the hand-over leaves the object (X14); `forget`'s preview names each object it would have inherited ("kept for this transaction, installed by T1; stays"). A **user-provided file** (held, no creator with its file ID) and a file the user put back after the creator deleted it (another file ID) are never deleted: no creator matches (c). A created object rewritten with the same content keeps no ID chain: kept by a halt on the creator side, left on the inheritor side.

### 4. Folders
No folder hold and no new op: reliance on a parent folder follows from the objects below it, which the plan has already (P2-8 overlap). A folder the creator made (`scripts\` of EaglePatch) stays while a later transaction has an object below it (a widescreen fix's `scripts\WS.asi`), and the last of them removes it when it is empty and has the creator's file ID; nested created folders deepest first. A folder that holds anything else (a user file) is `Foreign` for the creator as today, or left by the inheritor (X14).

### 5. Stacking, `verify`, `status`, preview, recovery, tamper
- **Still refused (LIFO):** a later op that changes an object of `C` (a replace or an INI edit of its file); a `Hold` of a file `C` **replaced** (`Refusal::Held`: restoring `C`'s old content would need `C`'s backup after `C` closes; see the user points below); a later relying op with an intent and no `Done`, or with a revert begun; a `Rebind` on that root on either side; registry and rule objects as before. `for_apply` and `slot_taken` are unchanged (a reverted creator op is skipped by the slot check; the holder's `Hold` keeps the slot).
- **`verify` / `revert --dry-run` (rule 5)**, from the same derivation: a kept op "kept for T2 (it relies on it; the last revert that relies on it removes it)"; a carrying op "removes <path> (installed by T1, handed over) if unchanged" or "keeps <path>: T3 still relies on it"; a halt "T2 relies on a file this transaction installed that cannot be handed over (its file ID changed); revert T2 first". `status` (journal-only) lists per live `Hold` "inherits <path> from T1 (removed on revert if unchanged)" when (a), (b) and (c) hold. `HOLD_NOTE` replaces "an earlier transaction that installed it is reverted only after this one, and this one's revert leaves it" with "if the transaction that installed it is reverted first, it keeps the file for this one, and the last revert that relies on it removes it if it is unchanged; a file no transaction of Rerun installed is left". The report adds `Detail::Kept { by }` and `Detail::Inherited { from, path, outcome }` (outcome `Removed`, `StillRelied(txn)`, `Gone`, `Left(why)`); every path through `escape::path`.
- **Tamper (docs/06 row 14):** an inherited deletion removes only an object whose creator's own revert would remove it: the file ID a tracked creator recorded, its exact content, after that creator's `RevertDone { After }`. A forged `Hold` over a user file finds no creator (no delete); one retargeted to another file of `C` fails the ID chain (c); a forged live holder only delays the deletion (its later revert does it, its `forget` leaves the file: denial, never a wrong deletion); a planted `RevertDone { After }` on a live creator's op makes a holder delete exactly what that creator's revert would delete. Rest risk of the same-user class: a planted complete creator transaction naming a user file's ID makes a genuine holder's revert delete that file; the revert preview names the deletion and its origin ("installed by T…"), as a forged `CreateFile` head with the file's hash could already (row 14).

### Alternatives
- **Explicit records** (`Handed { op, to }` in the creator, `Inherit { from }` in the holder): a new record kind and grammar rows for facts the existing records plus the file ID already prove; a record naming another transaction is a new tamper surface and goes stale when that one is forgotten.
- **An owner reference in `Op::Hold`** (P4-8's sketch): the owner is known at plan time but changes with each revert and forget; the plan hash would bind a fact that is not stable.
- **Keep L7** (P4-8): contradicts E6 and keeps the oldest-first order refused.
- **The creator stays open until the last holder:** the grammar reverts newest first, so the ops below a kept op could not be reverted without its `RevertDone`.
- **A folder hold op:** a new op kind and a planner that reads the journal for something the P2-8 overlap already expresses.

### Points for the user (conservative defaults chosen)
- **A file a transaction replaced** stays newest first (`Held`): handing over a restore would need the creator's backup after it closes. Rare for packages (the slot rule keeps two packages off one DLL).
- **A forgotten holder** counts as no reliance (the remaining last holder deletes); the alternative, a forgotten holder keeps the file for good, leaves files after every revert.
- **Changed inherited objects** are left and reported and the inheritor closes (X14), instead of keeping the inheritor open until `forget` (D10 for the creator's own objects is unchanged).

## Amendment P4-10 (2026-11-10): `ContentRef::Patch`, the primitive `laa_patch`
The Large Address Aware flag of a 32-bit game executable (plan `P4` step P4-10, user decisions E1 = 0 and E4 "a+", lead condition R6). Format 1 stays unstable until A6; the change is additive.

### `ContentRef::Patch`
- **The content:** `{"patch":{"base":<FileState>,"edits":[{"offset":<n>,"old":<byte>,"new":<byte>},…],"sha256":"<hex>"}}` (`ContentRef::Patch { base, edits, sha256 }`, `ByteEdit { offset, old, new }`): the file as it is with single bytes changed, the same length (`len()` is `base.len`), `sha256` the result's SHA-256 as the planner computed it. Checked on encode and decode alike (`plan::patch_check`, both rule sets: the head is untrusted): only the content of a `ReplaceFile` on a `Game` root, `base` exactly the op's `old`, 1 to `MAX_PATCH_EDITS` (8) edits strictly ascending by offset, each inside the file and changing its byte; a patch in a `CreateFile` is refused. `Op::package_file` is `None` for it (no slot, no hold). No new op kind: the op is a `ReplaceFile`, so its backup, guard, records, observation, revert, stacking (a patch of a file a live `Hold` holds is `HeldChange`, P4-8b S2), crash and power-loss behaviour are the replace's (ADR 0017, ADR 0019).
- **`exec`:** the guard is held until the rename (the old file cannot be read through it while `replace` consumes it), so the old bytes are streamed from the backup the op has just written and read back against `old` (`TxnWriter::backup_reader`), through `plan::Patched` (also the planner's reader), which applies the edits and fails (`InvalidData`) where an edited byte is not the edit's `old`; `replace` checks the result's SHA-256 and length before the rename (ADR 0017), so a backup changed in between, a stale or a forged edit writes nothing (`Mismatch`, rollback). The pre-check of the apply and `check` is the replace's (`old` on the guard); there is no package to check.
- **Observation (ADR 0020 table, `ReplaceFile` row):** the patched file is `After`; the old file is `Before` (Steam's "Verify integrity of game files" or the game's repair put it back: the revert changes nothing and closes, P4-10 question c); the old bytes with other R/H/S, or any other content (an update), are `Foreign`, left, the transaction open until `forget` (D10).
- **Preview (rule 5):** the action `patch file`, the new and the old content as for a replace, every changed byte (`byte at 0x<offset>: 0x<old> -> 0x<new>`, numbers only) and `PATCH_NOTE` once (the whole file is kept in the journal; a put-back original is found as it was; an update is left; a patch makes a signature invalid).
- **X rows:** none. A patched file is restored exactly from its backup, or found as it was.
- **Tamper (docs/06 row 14):** a forged patch head can change at most 8 bytes of a file whose exact old content it names and writes only the result it names; a forged package or inline op could already write any content over such a file (the control K-LM1 of P3-3), so this is the same same-user class, not a new power.
- **Tests (fake):** `exec/patch_tests.rs` PT1 to PT6, `plan/tests.rs` p8, CLI `preview/tests.rs` `a_patch_shows_its_bytes` (docs/09).

### `laa_patch` (`prim::laa_patch`, the Topo step, the engine)
- **Topo step:** `laa_patch: { exe }` (`TopoStep::LaaPatch`, schema `laaPatch`): `exe` an `.exe` that names an entry of `match.exes` in exactly its spelling, that entry with a `sha256` (ADR 0024, R6; `catalog::check`). Draft only until reviewed (`LAA_PATCH_REVIEWED`; reviewed since P4-10: Smart App Control decided (question b below) and the [SB] case green, CI run 42788275603), so a signed Topo may hold it now. The step file refuses it (`StepFileError::TopoOnly`): its executable and hash come only from a Topo.
- **Engine:** the step's executable must be the `match.exes` entry that matched here; the planner gets that entry's path and SHA-256 (`prim::LaaPatchSpec { exe, sha256 }`), never the step's spelling; two picks of one executable plan it once; a certificate table gives `Warning::SignedExe`. The anti-cheat rule refuses the step (E4, already in `ANTI_CHEAT_RULES`).
- **Planner** (reads only, through the game folder's handle): refuses an admin-only folder (E1 = 0, with a hint; the helper does not replace files before phase 6), a file another step of the plan changes, a file that is not plain, hard-linked or over 2 GiB; parses the headers (`detect::pe`) and refuses x64 or PE32+, a DLL, Large Address Aware already, a CLR header, a section of a protection wrapper (`PROTECTED_SECTIONS`, with sources: Steamless for SteamStub's `.bind`, Detect It Easy for SecuROM, SafeDisc and StarForce); then streams the file twice on the same handle: the SHA-256 (must be the Topo's) and the image checksum of the bytes with the flag set, then the SHA-256 of the result. The edits: the low byte of `Characteristics` with `0x20` set; if the stored `CheckSum` is not 0, every byte of the new checksum that differs (question a below); the old R/H/S are kept; the path in its stored spelling.
- **Question a, the checksum (decided):** recompute when one is stored, keep 0. Evidence: the PE format says the checksum is validated at load time only for "all drivers, any DLL loaded at boot time, and any DLL that is loaded into a critical Windows process" (Microsoft Learn, PE Format, `CheckSum`), so a game starts either way; `CheckSumMappedFile` is "used by any application that creates or modifies an executable image … It is recommended that all images have valid checksums" (Microsoft Learn, `CheckSumMappedFile`). A recomputed value keeps a game or launcher that compares the field with `MapFileAndCheckSum` (a cheap self-check some old games and DRM wrappers do) seeing what it saw before; leaving it would turn a valid checksum into an invalid one for no gain. A stored 0 means "not computed" (most game linkers leave it): writing one would change a field no loader or game reads. The value is computed as `CheckSumMappedFile` does (ADR 0013 amendment P4-10, pinned against the real function on Windows).
- **Question c, Steam's file check:** "Verify integrity of game files" writes the original back; the op observes `Before` (the old hash, length and R/H/S), the revert changes nothing and closes; another build (an update) is `Foreign` (PT2, PT3, LA3).
- **Question b, Smart App Control (user decision of 2026-11-10: measure on the developer machine, then A or C):** Microsoft: when the cloud service has no confident verdict, "if the app is unsigned, or the signature is invalid, Smart App Control will consider it untrusted and block it", and there is no per-app exception (Support, "Smart App Control FAQ"); in enforcement mode it "prevents your app from running if its signature is invalid" (Learn, "Test App Signatures with Smart App Control"). Measurement (docs/09 manual row): with Smart App Control enforcing, the unpatched, locally built test program started (exit 16), its patched copy did not ("Permission denied"). Decision **A**: `hw::sac` reads `VerifiedAndReputablePolicyState` (0 or absent: off; 1: enforcing; 2: evaluation; anything else or a failed read: unknown) into the system profile; the engine refuses a `laa_patch` step while it enforces (`Refusal::SmartAppControl`, in the report and the plan) and plans it with `Warning::SmartAppControl` in evaluation mode (Windows may turn it on later) or when the state is unknown. Signed or not makes no difference under A. The rule is the planner's: the check runs at plan time, and a Smart App Control switched on between plan and apply is not re-checked (accepted: it then blocks the game until the revert, which restores the original). The step was draft only (`LAA_PATCH_REVIEWED`) until the reviews were done; it is reviewed since P4-10.
- **A patched build still matches (P4 lead condition R5):** after the patch the executable has another SHA-256, so the Topo would no longer match until the revert. `exec::patched_now` lists the patches of live transactions (not forgotten, not closed, head usable, the op done and not reverted; read without the lock, a journal that cannot be read gives none) of the game folder's identity (after a rebind, the bound one), and `topo::read_game_with` counts a file whose SHA-256 is such a patch's result, at the patch's path, as the `match.exes` entry whose `sha256` is the patch's base (`ExeCheck::patched_by`; its SHA-1 is the entry's, for `supports_exe_sha1`). `rerun plan <app-id>` reads with it (the report says "matches (as patched by Rerun's laa_patch)"). Such an entry is never an anchor of the elevated helper (`elevate::check_plan` refuses it: the helper hashes the file itself and would refuse), and `laa_patch` of it again is refused with the reason. The helper's own derivation keeps `read_game` (no derived match).
- **[SB]:** `sandbox_laa_patch_round_trip_starts_the_patched_exe` patches the repository's own 32-bit test program (`tests/support/laa_stub.rs`, linked without the flag and with a checksum) on the CI runner, starts it before (no large address space), after (large address space) and after the revert (none), and checks the file bit for bit and the checksum against `CheckSumMappedFile` (docs/09). It runs in the CI sandbox job; not run on the developer machine.
- **Review follow-ups (security-reviewer, senior-dev):**
  - *A patch and a rule of one executable:* a plan that picks `laa_patch` and a `firewall_rule` of the same executable is refused by the engine (the helper would hash the patched file after the prompt and refuse); the refusal names the order that works: the rule in its own plan first, then the patch. The rule is bound to the executable by its path and only its add hashes the file, so a later patch does not disturb it, and either revert order ends identical (`exec/fw_tests.rs` F8). The other order is refused anyway: a patched file is never an anchor (`patched_by`).
  - *Two builds of one path (S2):* the loader wants a `sha256` on every `match.exes` entry of exactly the spelling a `laa_patch` or `firewall_rule` names; the engine patches the entry of that spelling that matched (with its hash); `elevate::derive_add` gives an anchor every SHA-256 of that spelling (`Anchor::sha256` is a list) and the helper accepts the file if it hashes to one of them, as `check_plan` (any matching entry) already did, so another build no longer fails only after the prompt.
  - *A forged live patch (security 2):* a transaction planted in the journal can make another file match as a patched build; that only affects matching for steps without elevation, because no elevated anchor takes a `patched_by` entry. Every future elevated anchor (IFEO in phase 6, files in admin-only roots) must exclude `patched_by` the same way.
  - *`supports_exe_sha1` after a patch (security 3), decided:* the patch's base carries only the SHA-256, so a patched build has the SHA-1 its `match.exes` entry names, or none. Rerun does not read the journal backup to hash it again (it would make the matcher read user-writable journal files of up to 2 GiB). Accepted: a package with `supports_exe_sha1` is refused for a patched build whose entry names no `sha1` (the refusal names `supports_exe_sha1`); curators give such entries their `sha1`.

## Amendment P4-11 (2026-11-10): `Op::GpuPref`, the primitive `gpu_preference`
Windows' graphics preference ("High performance") for one game executable (plan `P4-11`, user decisions E-G1 c, E-G2 d, E-G3 a; senior-dev conditions S2 to S4, N1 to N6). Format 1 stays unstable until A6; the change is additive. The registry side is ADR 0018 amendment P4-11.

### `GpuPref` in format 1
- `{"gpu_pref":{"slot":{"gpu_preference":{"root":0,"exe":"bin\\game.exe"}},"old":null,"pref":"high_performance","new":"GpuPreference=2;"}}`: the slot, the old value as planned (`ValueState`, always inline: at most 1 KiB), the preference (`GpuPref`, v1 only `high_performance`; `power_saving` may follow without a format break) and the new value. A registry op (`Target::Value`, after every file op, `needs_main_exe`); no `SetValue` ever names a `GpuPreference` slot (both rule sets).
- **`check`, both rule sets:** the slot a `GpuPreference`; the old value missing or an inline `REG_SZ` that hashes to what it claims; with an old value not in a key the plan creates; `new` other than `old` and exactly `old` with Rerun's pair (`plan::pref_relation`: the first piece `GpuPreference=…;` replaced by `GpuPreference=<digit>;`, else the pair appended; without `old` the pair alone). The relation is plain string pieces, no grammar, so a later grammar never blocks a revert, and a manipulated head can never make the restore of `After` write another pair (the S-1 analogue of `TokenList`). **`Rules::Current`** adds the grammar (`gpu_pref::parse`) of old and new, `RegPolicy::check_pref` (not "Power saving", not set already) and `new == gpu_pref::set(old, pref)`.
- **Budget (P-G3):** the longest relative path (240 characters outside the BMP) with an old value of 476 `"` in pairs (inline hex, and escaped in `new`) fits the 8 KiB op budget.

### `exec` for `GpuPref` (`exec::reg`)
- **Apply** like `TokenList`: re-read the value (`Mismatch` before the intent when it is not `old`), the old bytes inline in the intent, then `RegWriter::set_pref(expected = the value read, pref)`: `policy` forms the new value; read back, flush (the registry path of P2-10b).
- **Observation, first matching row:** (1) a link, volatile key or a value too large on the way → `Foreign`; (2) exactly `new` and not `NotWritten` → `After`, the old value restored exactly from the journal (or the value deleted); (3) the old value (missing for none) → `Before`; (4) anything else after `NotWritten` → `Foreign`; (5) missing (Settings' "Remove") → `Drifted`, nothing written; (6) a `REG_SZ` in the grammar holding Rerun's `GpuPreference=<digit>` → `Drifted`, `RegWriter::unset_pref(expected = the value seen)`: the pair back to the old digit or removed, the value deleted when no pair is left; (7) in the grammar without Rerun's pair (another digit) → `Drifted`, nothing written (D10: the user's choice wins); (8) anything else (another type, no NUL, outside the grammar, the pair twice) → `Foreign`, left until `forget`. A crash after `unset_pref` and before `RevertDone` leaves a value without Rerun's pair: the next run sees row 3, 5 or 7, never `Foreign` (R-G5).
- **S3:** the user choosing High performance in Settings after the apply writes Rerun's bytes: row 2, and the revert sets the old preference back. Not distinguishable; X15 and `GPU_PREF_NOTE` say so.
- **D4:** the executable of the op is asked like the executable of a compatibility layer (`exec::roots::game_closed`: `users()` empty, else `Busy`), at apply and at revert; the main executables as for every registry op.
- **Shared keys:** `DirectX` and `UserGpuPreferences` (`AllowedValue::shared_keys`): a created one that is not empty, or existed, is `Drifted` and left (E6 b, E7); `verify` counts a value of a later `GpuPref` as gone when its revert deletes it.
- **X rows:** X3 and X8 extended to `DirectX` and `UserGpuPreferences`; new X15.

### `gpu_preference` (`prim::gpu_preference`, the Topo step, the engine)
- **Step:** `gpu_preference: { exe, preference }` (`GpuPreferenceSpec`, `deny_unknown_fields`, both required; schema `gpuPreference`). In a Topo `exe` names an entry of `match.exes` in exactly its spelling, **without** a `sha256` requirement (R6 / ADR 0024 is about elevated anchors and changes of an executable; this is an `HKCU` value naming a path); the issue's `when` must have `gpu.hybrid: true` (load error otherwise), so the step is never offered on a PC with one adapter. Draft only until reviewed (`GPU_PREFERENCE_REVIEWED = false`; the gate is the SB-G1 dump of what Settings writes, `docs/09-testing.md`). A step file may carry it with any plain `.exe` of the game folder (needed for the [SB] case).
- **Planner** (reads only): a game folder reached through a link or another name than its canonical path is refused (as `compat_layer` E3 a; how DirectX matches the value name is not measured), a case-sensitive folder, a link or volatile key on the way, two steps for one executable, a plan without the main executable; `stored_exe` names the executable in its stored spelling; the value: missing → new; in the grammar → merged; `=2` already → no op; `=1` → refused with a pointer to Settings (E-G3 a); anything else → refused as unusual. The missing keys below `Software\Microsoft` become `CreateKey` ops, once for all steps.
- **Engine:** `TopoStep::GpuPreference` → `Step::GpuPreference` (`StepKind::GpuPreference`: the anti-cheat rule warns, E4). A step that plans nothing because the preference is High performance already gives `Warning::GpuPreferenceSet { exe, by }`, naming the open Rerun transaction that set it if one did (N2: reverting that one takes it back).
- **Preview (rule 5):** `set gpu preference HKCU\…\UserGpuPreferences @ <path>`, the old and the new value (`escape::text`; a recorded head masks both: the new value holds the old one's pairs), and `GPU_PREF_NOTE` once (only the pair changes and takes effect at the next start; a revert is exact or takes back only Rerun's pair; the user's own High performance after the apply is reverted too; a preference set already is left; the keys are shared; OpenGL and Vulkan depend on the driver).
- **Tests (fake):** `policy/registry/gpu_pref/tests.rs` G-P1, `policy/registry/tests.rs`, `plan/gpu_pref_tests.rs` P-G1 to P-G4, `prim/gpu_pref_tests.rs` T9-G, `exec/gpu_pref_tests.rs` R-G1 to R-G4, X15, D4, `exec/gpu_pref_crash_tests.rs` R-G5 (failures, crashes and every power-loss cut of `GpuNew`, `GpuMerge`, `GpuDrift`, `GpuStacked`; J6 for `unset_pref`), `topo/gpu_tests.rs` GP1 to GP4, the schema fixtures `topo-gpu-preference*.yaml` (docs/09).
- **Open:** the [SB] case on the real `HKCU` (SB-G2) and the manual SB-G1 dump (Settings > Graphics, both directions, S4) before `GPU_PREFERENCE_REVIEWED = true`; whether a game really follows the value needs a hybrid machine (docs/09, manual matrix).
