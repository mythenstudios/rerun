# ADR 0008 · Win32 bindings

**Status:** accepted · 2026-11-04 · amended 2026-11-05 (DLL hardening; DXGI on `windows-sys`; import allowlist per binary) · P4-2a, P4-2b (helper imports; the helper start) · P4-5a (firewall read side, hand-written COM; re-evaluation of `windows` before P4-5b open)

## Context
Phase 1 needs NT file APIs (`NtCreateFile`), registry, CPU sets, version info and GPU enumeration. Phase 3 needs Job Objects, IFEO and the firewall COM interface (`INetFwPolicy2`). `rerun-launch` and `rerun-cpu` must stay small (ADR 0006). `windows-sys` 0.61 no longer contains COM interfaces such as DXGI.

## Decision
- **`windows-sys`** (Microsoft, MIT OR Apache-2.0, depends only on `windows-link`) for all plain Win32/NT functions in every crate, with only the features that are used.
- **`windows`** (Microsoft, MIT OR Apache-2.0) **only in `rerun-core`**, only for COM: DXGI now (`Win32_Graphics_Dxgi`), the firewall COM interface in Phase 3. *Superseded for DXGI by the amendment of 2026-11-05 (hand-written binding on `windows-sys`); re-evaluated for the firewall in Phase 3.* It pulls about nine `windows-*` crates; acceptable for the core, not for `rerun-launch`/`rerun-cpu`.
- All `unsafe` stays in `sys::win` (and later `rerun-launch`, `rerun-cpu`), each block with a `// SAFETY:` comment. Handles are wrapped in `std::os::windows::io::OwnedHandle`; file I/O goes through `std::fs::File::from(OwnedHandle)`.

## Alternatives
- Hand-written COM vtables on `windows-sys`: no extra crates, but vtable order and reference counting become our risk.
- `D3DKMTEnumAdapters2`/`D3DKMTQueryAdapterInfo` via `windows-sys` for the GPU: no COM, but a less common WDK thunk API; does not help with the firewall in Phase 3.

### Hardening of the elevated helper (from the security review, H2)
`windows`/`windows-sys` import DLLs directly; a DLL that is not a KnownDLL (such as `dxgi.dll`) would first be loaded from the application directory. If that directory is user-writable (Tauri's default per-user install under `%LOCALAPPDATA%\Programs`), malware could plant a DLL or replace the executable and get elevated code execution. Therefore:
- Every Rerun executable is linked with `/DEPENDENTLOADFLAG:0x800` (load dependencies from System32 only) and calls `SetDefaultDllDirectories(LOAD_LIBRARY_SEARCH_SYSTEM32)` first thing.
- The elevated code path uses no COM/DXGI; GPU code is only reachable from non-elevated commands (delay-loaded or in a separate binary, decided in Phase 3).
- At startup the helper refuses to run if its own image directory is writable by any principal other than SYSTEM, Administrators or TrustedInstaller. Elevated features therefore require a per-machine install (Phase 5).
- The helper removes `SeBackupPrivilege`, `SeRestorePrivilege`, `SeTakeOwnershipPrivilege` and `SeDebugPrivilege` from its token at startup.
- COM in the elevated helper uses `CLSCTX_INPROC_SERVER` only (Windows ignores per-user COM registrations for elevated processes).

## Consequences
- `cargo deny` covers the extra crates; the CI dependency check for `rerun-launch` stays (`windows-sys` and `rerun-proto` only).
- `windows-core` pulls the proc-macro crates `windows-implement`/`windows-interface` plus `syn`/`quote`, i.e. code that runs at build time. `windows` features are kept minimal; duplicate `windows-sys`/`windows-targets` versions are watched in `cargo deny` (bans: `multiple-versions = "warn"`).

## Amendment 2026-11-05: DLL hardening of the shipped executables (H2, implemented)

H2 is implemented now (phase 1, step 10) instead of with the helper, so that no shipped binary ever loads a DLL from its own folder, before the first DLL that is not a KnownDLL (`dxgi.dll`) is loaded.

- **Link flag.** The `build.rs` of `rerun-cli` and `rerun-launch` emits `cargo::rustc-link-arg-bins=/DEPENDENTLOADFLAG:0x800` when `CARGO_CFG_TARGET_ENV == "msvc"`. The linker writes `0x800` (`LOAD_LIBRARY_SEARCH_SYSTEM32`) into `IMAGE_LOAD_CONFIG_DIRECTORY64::DependentLoadFlags` (offset `0x4E`, winnt.h); the loader then resolves the image's static imports from System32 only (KnownDLLs and API sets are unaffected). Not set for `rerun-cpu` (a DLL loaded into a game; its imports are `kernel32` only, and a DLL's flag would only govern its own static imports) and not for `rerun-workbench` (not shipped). The Tauri app gets the same `build.rs` line in phase 5.
- **Search path.** The first statement of `main` in `rerun` is `rerun_core::sys::win::restrict_dll_search()` (`SetDefaultDllDirectories(LOAD_LIBRARY_SEARCH_SYSTEM32)`); `rerun-launch` has its own copy of the one call (`src/dll.rs`, it does not depend on `rerun-core`; `windows-sys` with `Win32_System_LibraryLoader` only, ADR 0006 already allows the crate). If the call fails, the binary exits non-zero (fail closed). This removes the application directory, the current directory and `PATH` from every later `LoadLibrary*` of the process, including loads Windows makes on Rerun's behalf. A successful call is recorded in a process-wide flag; code that loads non-KnownDLLs (`sys::win::dxgi`) refuses to run without it (`Unsupported`, "DLL search not restricted; call restrict_dll_search first"), so a future binary that forgets the call fails visibly instead of loading DXGI's dependencies from its own folder.
- **Never inside a game process.** `rerun-cpu.asi` runs inside the game and must never call `SetDefaultDllDirectories` (or any other DLL search path call): it would change how the game loads its own DLLs. Its imports are `kernel32` only today; if it ever imports more, it gets `cargo::rustc-link-arg-cdylib=/DEPENDENTLOADFLAG:0x800` in its own `build.rs`, which only governs the ASI's own static imports.
- **Tests.** `crates/rerun-cli/tests/hardening.rs` and `crates/rerun-launch/tests/hardening.rs` read the built binary (`CARGO_BIN_EXE_*`) with `rerun_core::detect::pe` over a `std::fs::File` of the build output (ADR 0013, "Hardening tests"; until step 13 a minimal PE32+ reader `tests/support/pe_min.rs`); the test policy lives in `tests/support/hardening.rs` (included with `#[path]`, with a teeth test on a PE32+ it writes itself: a `d3d9.dll` import, an unlisted import, a delay-load import and other `DependentLoadFlags` fail, a hardened image passes; `rerun-core` is a dev-dependency of `rerun-launch` only; the binary must be PE32+ for the native machine; CI also checks the release `rerun-launch.exe` of the size step through `RERUN_RELEASE_LAUNCH_EXE`): `DependentLoadFlags == 0x800`, every static import in an exact **allowlist** (`SHIPPED_IMPORTS`: `kernel32.dll`, `ntdll.dll`, `api-ms-win-core-synch-l1-2-0.dll`, found on 2026-11-05 for both binaries, debug and release, x64; a new import fails the test and needs a review, then this list and this ADR are updated), never `dxgi.dll`, `d3d*`, `dxcore.dll`, `vcruntime*`, `msvcp*`, `ucrtbase*` or `api-ms-win-crt-*` even if listed, an empty delay-import table; and the binary runs past the restriction. `crates/rerun-core/tests/win_gpu_restricted.rs` does the same for a binary that links all of `WinSystem` (its allowlist `CORE_IMPORTS` adds `advapi32.dll`, `combase.dll`, `shell32.dll` from `windows-sys` and `bcryptprimitives.dll`, `userenv.dll` from `std`).
- **Source rule** (security review of step 10): `crates/rerun-core/tests/source_rules.rs` scans every `.rs` file of the workspace and fails on a hand-written import (`extern "…" { … }` or `extern { … }` blocks, also `unsafe extern` of edition 2024, `#[link(…)]` also inside `cfg_attr`, `raw-dylib`), outside an allowlist that is empty. Function pointer types and exported functions are not imports. All Win32 imports therefore come from `windows-sys`, where `clippy.toml` fences them.
- **Bans** (`clippy.toml`, checked by `sys/win/bans.rs`): `LoadLibraryA`/`W`, `LoadLibraryExA`/`W`, `LoadPackagedLibrary`, `LoadLibraryShim`, `QueryOptionalDelayLoadedAPI` and `GetProcAddress` outside `sys::win::loader`; `LoadModule` (starts a process) everywhere; `SetDefaultDllDirectories`, `SetDllDirectoryW`/`A`, `AddDllDirectory` and `RemoveDllDirectory` outside `loader::restrict_dll_search` (and `rerun-launch`'s copy).
- **Phase 5 (Tauri app).** `SetDefaultDllDirectories(LOAD_LIBRARY_SEARCH_SYSTEM32)` also removes the application directory for the app. `WebView2Loader.dll`, which Tauri/wry loads from next to the exe by default, would then not be found: the app must link the WebView2 loader statically (wry's static-loader option) or add exactly its own install directory with `AddDllDirectory` after checking that it is not user-writable (per-machine install). Decided in phase 5; the ban on `AddDllDirectory` makes that a reviewed exception.

### Alternatives (hardening)
- **Delay-load `dxgi.dll`** (`/DELAYLOAD`): keeps the `windows` crate's static style, but the delay-load helper resolves through the same search path and adds a delay-import table the elevated helper must never have; an explicit `LoadLibraryExW(…, LOAD_LIBRARY_SEARCH_SYSTEM32)` is narrower and visible.
- **Only `SetDefaultDllDirectories`, no link flag:** the static imports are resolved before `main` runs, so a planted DLL that shadows a non-KnownDLL import would load anyway.
- **Only the link flag:** covers the static imports, not `LoadLibrary*` calls made later by Windows components (COM, shell, drivers' user-mode parts).

## Amendment 2026-11-05: DXGI on `windows-sys`, no `windows` crate (user decision)

Supersedes the `windows` bullet of the decision for DXGI. `windows-sys` 0.61.2 has no DXGI at all: no `Win32_Graphics_Dxgi` feature, no `DXGI_ADAPTER_DESC1`, no `CreateDXGIFactory1` (nor DXCore). Rerun needs four COM methods, so `rerun-core::sys::win::dxgi` binds them by hand on `windows-sys` types (`GUID`, `HRESULT`):

- **Binding.** `DXGI_ADAPTER_DESC1` as `AdapterDesc1` (`repr(C)`, x64: 312 bytes, alignment 8; a test pins size and every offset). Vtable prefixes, 0-based slots from the `*Vtbl` structs of `dxgi.h` (SDK 10.0.26100): `IUnknown::Release` 2, `IDXGIFactory1::EnumAdapters1` 12, `IDXGIAdapter::CheckInterfaceSupport` 9, `IDXGIAdapter1::GetDesc1` 10; the slots in between are untyped placeholders that are never read; `offset_of!` tests pin the four. IIDs from `dxgi.h`: `IDXGIFactory1` `770aae78-f26f-4dba-a829-253c83d1b387`, `IDXGIDevice` `54ec77fa-1377-44e6-8c32-88fd5f44c84c` (tested against the `DEFINE_GUID` bytes). A `Com<V>` guard holds one reference, calls `Release` on drop and is neither `Send` nor `Sync`; no interface pointer outlives one enumeration. No `QueryInterface`, no `AddRef`.
- **Loading.** `dxgi.dll` is loaded on the first `Gpu::adapters()` with `LoadLibraryExW("dxgi.dll", NULL, LOAD_LIBRARY_SEARCH_SYSTEM32)` (`sys::win::loader::load_system32`: bare ASCII name only, never freed) and `CreateDXGIFactory1` is taken with `GetProcAddress` (the `FARPROC` is transmuted directly to the export's function type) and cached in a `OnceLock`; a load or symbol failure is cached as well, for the life of the process. Enumeration requires `restrict_dll_search` first (see the hardening amendment). No static import, no delay-load import (the hardening tests check both binaries). DXGI needs no `CoInitialize`. The elevated helper (phase 3) builds a `System` without a GPU and never loads `dxgi.dll`; that settles "delay-loaded or in a separate binary" of H2.
- **Semantics.** A fresh factory per call (a factory caches the list of its creation time); `EnumAdapters1(0, 1, …)` until `DXGI_ERROR_NOT_FOUND`, more than 64 adapters is an error; DXGI order is kept, nothing is deduplicated (the contract requires unique LUIDs). Name: the units before the first NUL within the first 127, lossy, control characters and bidirectional formatting characters (`Bidi_Control`: U+061C, U+200E, U+200F, U+202A to U+202E, U+2066 to U+2069; they could reorder the surrounding UI text) as U+FFFD, untrimmed; other format characters such as U+200D stay. The GPU contract checks the same. LUID: `(HighPart as u32) << 32 | LowPart`. `software` is `DXGI_ADAPTER_FLAG_SOFTWARE` (value 2); `DXGI_ADAPTER_FLAG_REMOTE` is ignored. Driver version from `CheckInterfaceSupport(IID_IDXGIDevice)`, `None` on any failure. Errors: a load or symbol failure is `NotFound` with the Win32 code; a failed `CreateDXGIFactory1`, `EnumAdapters1` or `GetDesc1` (which fails the whole list) carries its `HRESULT`: `E_ACCESSDENIED` is `AccessDenied`, `DXGI_ERROR_UNSUPPORTED` `Unsupported`, `DXGI_ERROR_NOT_CURRENTLY_AVAILABLE` `Busy`, anything else `Other`.
- **Bans** (`clippy.toml`, checked by `sys/win/bans.rs`): `D3DKMTEnumAdapters`, `D3DKMTEnumAdapters2`, `D3DKMTEnumAdapters3`, `D3DKMTQueryAdapterInfo` and `D3DKMTOpenAdapterFromLuid` everywhere (GPU data only through `dxgi`); COM activation (`CoCreateInstance`, `CoCreateInstanceEx`, `CoGetClassObject`, `CoInitialize`, `CoInitializeEx`, `CoGetObject`) until phase 3 gives it one wrapper with `CLSCTX_INPROC_SERVER` only. `CreateDXGIFactory`, `CreateDXGIFactory1`, `CreateDXGIFactory2`, `DXGIGetDebugInterface1`, `DXGIDeclareAdapterRemovalSupport` and `DXCoreCreateAdapterFactory` do not exist in `windows-sys` 0.61 and cannot be listed; they are reachable only through `GetProcAddress`, which is banned outside `loader`, or through a hand-written import, which the source rule refuses (and which the import allowlists of the shipped binaries and of the `WinSystem` test binary would also catch). Security review of step 10 added the remaining COM activation paths: `CoCreateInstanceFromApp`, `BindMoniker`, `CoRegisterClassObject`, `CoInitializeSecurity`, `CoGetInstanceFromFile`, `CoGetClassObjectFromURL`, `OleInitialize`. The ones behind `windows-sys` features `rerun-core` does not use (`Win32_System_Com_StructuredStorage`, `Win32_System_Com_Urlmon`, `Win32_System_Ole`, `Win32_System_ClrHosting`) resolve through test-only features of the existing dev-dependency, so `bans.rs` checks every entry.
- **Found on the developer machine (2026-11-05, Ryzen 9 5950X, RX 9070 XT, Windows 11 build 26300):** two adapters, `AMD Radeon RX 9070 XT` (vendor `0x1002`, device `0x7550`, 16 GiB, driver `32.0.32015.7029`) and `Microsoft Basic Render Driver` (vendor `0x1414`, device `0x8c`, software, `10.0.26100.9711`); the first enumeration (loads `dxgi.dll`) takes about 11 ms, a later one under 1 ms. The same list comes back with the DLL search path restricted to System32.
- **Phase 3:** the firewall COM interface (`INetFwPolicy2`) re-evaluates the `windows` crate (0.62); until then no crate is added. *Done in P4-5a: hand-written as well (amendment P4-5a).*

## Amendment 2026-11-05: import allowlist per binary (ADR 0016)

From phase 1 step 16 `rerun.exe` builds `WinSystem` and links all of it, so its static imports are no longer those of `rerun-launch.exe`. The hardening policy (`tests/support/hardening.rs`) takes the allowlist as a parameter, `check_hardened(image, allowed)` and `check_hardened_file(path, allowed)`, with one list per binary:
- `LAUNCH_IMPORTS` for `rerun-launch.exe`: the former `SHIPPED_IMPORTS`, unchanged (`kernel32.dll`, `ntdll.dll`, `api-ms-win-core-synch-l1-2-0.dll`).
- `CLI_IMPORTS` for `rerun.exe`: the former `CORE_IMPORTS` of `crates/rerun-core/tests/win_gpu_restricted.rs`, moved here; it adds `advapi32.dll`, `combase.dll`, `shell32.dll` (from `windows-sys`) and `bcryptprimitives.dll`, `userenv.dll` (from `std`). `win_gpu_restricted.rs` checks its own binary against the same list, so the binary that links all of `WinSystem` and `rerun.exe` cannot drift apart.

The forbidden names (graphics DLLs, dynamic CRT), the `DependentLoadFlags` check and the empty delay-import table apply to every list. A new import of either binary still fails its test and needs a review, then its list and this ADR. The PE writer of the teeth test moves to `tests/support/pe_image.rs`, which the CLI tests include as well.

Alternative rejected: one list for both binaries, which would grant `rerun-launch.exe` `advapi32`, `combase` and `shell32` without review, against its minimal surface (ADR 0006).

### Alternatives (DXGI)
- **`windows` 0.62 (`Win32_Graphics_Dxgi`):** generated, reviewed bindings and reference counting, but about nine `windows-*` crates plus the build-time proc-macro crates `windows-implement`/`windows-interface` with `syn`/`quote`, and its `CreateDXGIFactory1` is a static import of `dxgi.dll` (which the hardening forbids), all for four methods. Re-evaluated with the firewall in phase 3.
- **Delay-load `dxgi.dll`:** see the hardening alternatives; an explicit System32 load is narrower.
- **`D3DKMTEnumAdapters2`/`D3DKMTQueryAdapterInfo`** (`windows-sys`, `Wdk_Graphics_Direct3D`): no COM, but a WDK thunk API with versioned, driver-specific query structures, no driver version in the DXGI form, and no help for the firewall. Banned instead.


## Amendment P3-1b (2026-11-08): `LAUNCH_IMPORTS` of the shim
`rerun-launch.exe` now starts processes, so its allowlist grows by four reviewed imports (ADR 0022): `advapi32.dll` (`OpenProcessToken`, `GetTokenInformation`, `CheckTokenMembership`: an elevated shim ignores the profile), `shell32.dll` (`SHGetKnownFolderPath` for the profile folder, `ShellExecuteExW` for the 740 fallback), `combase.dll` (`CoTaskMemFree` for the known-folder string) and `ole32.dll` (`CoInitializeEx`/`CoUninitialize` around `ShellExecuteExW`). All four are KnownDLLs on Windows 11 and resolve from System32 under `/DEPENDENTLOADFLAG:0x800`. `ole32.dll` is in `LAUNCH_IMPORTS` only, not in `CLI_IMPORTS`. `CoInitializeEx` has its second reviewed exception to the COM ban in `rerun-launch`'s wrapper module (ADR 0010 amendment P3-1b), on the 740 path only; the shim activates no COM class itself.

## Amendment P4-2a (2026-11-09): `HELPER_IMPORTS` of the elevated helper
`rerun-helper.exe` (ADR 0023) gets its own exact list in `tests/support/hardening.rs`, found on the P4-2a scaffold: `kernel32.dll`, `ntdll.dll`, `api-ms-win-core-synch-l1-2-0.dll` and `advapi32.dll` (`OpenProcessToken`, `GetTokenInformation`, `AdjustTokenPrivileges` for the privilege removal of ADR 0023 §3 step 2). `shell32`, `combase`, `ole32` and `oleaut32` (ADR 0023 §13) join only with the slices that use them, after a review. Besides the checks every list gets, the helper's image must pass `check_helper_content`: no `dxgi.dll` (ASCII or UTF-16LE, case-insensitive), no `CreateDXGIFactory1`, and no run-time loader name (`LoadLibrary*`, `LoadPackagedLibrary`) except `std`'s own `LoadLibraryA` and `LoadLibraryExW`, which its backtrace support uses for `dbghelp.dll` (measured in the release `rerun-launch.exe`, which does not depend on `rerun-core`; the reviewed exception). A byte search over the file, like the console check of ADR 0016, so `detect::pe` stays without function names (ADR 0013). The control is `crates/rerun-core/tests/win_gpu_restricted.rs`, which links `WinGpu` and must fail both the content check and `HELPER_IMPORTS`. The helper is linked with `/MANIFEST:EMBED` and `/MANIFESTUAC:level='asInvoker' uiAccess='false'` in addition to `/DEPENDENTLOADFLAG:0x800`. `AdjustTokenPrivileges` is a `clippy.toml` ban with two call sites: the product one in `sys::win::token::drop_privileges` and the test-only `SeRestorePrivilege` fixture in `sys::win::testfx`.

## Amendment P4-2b (2026-11-09): the helper start in the CLI (ADR 0023 §2, §7; audit A4 S2, N3)
- `rerun-core`'s `sys::win::elevation` is the only place in `rerun-core` that calls `ShellExecuteExW` (the helper start, verb `runas`, `SEE_MASK_CLASSKEY` with the `HKLM\SOFTWARE\Classes\exefile` key opened read-only through `reg`, `lpDirectory` = the helper's folder), `CoInitializeEx`/`CoUninitialize` around it (apartment-threaded, `COINIT_DISABLE_OLE1DDE`, as `ShellExecuteExW` asks; the CLI's named exception to the COM ban, A4 N3; it activates no class) and `QueryFullProcessImageNameW` (the started process's image in the native form, readable also after the process exited). Each call site carries an `expect`; `clippy.toml` names both reviewed `ShellExecuteExW` and `CoInitializeEx` sites (the shim's and this one) and bans `QueryFullProcessImageNameW`/`A` outside this one and `rerun-launch`'s `win::process::image`.
- `CLI_IMPORTS` grows by `ole32.dll` (`CoInitializeEx`, `CoUninitialize`), a KnownDLL like in `LAUNCH_IMPORTS`; `HELPER_IMPORTS` is unchanged (the helper never starts a process). No new `windows-sys` feature: `Win32_UI_Shell`, `Win32_System_Com`, `Win32_System_Console` (`GetConsoleWindow`, the prompt's owner), `Win32_System_Threading` and `Win32_Security` (`GetSecurityDescriptorLength`) were already enabled.

## Amendment P4-5a (2026-11-09): the firewall read side, hand-written COM (ADR 0023 §8, §13; audit A4 S10, S11)
The re-evaluation of the `windows` crate for the firewall ends here (P3 decision D12 a, ADR 0023 §13): the read side is bound by hand on `windows-sys`, like DXGI.
- **`sys::win::com`** holds everything generic: the one `CoCreateInstance` (`activate`, `CLSCTX_INPROC_SERVER`, no aggregation), reached only through `create_inproc`, which first runs the A4 S10 environment check (`SystemRoot` and `windir` must name the folder `GetSystemWindowsDirectoryW` reports, compared folded; otherwise no activation); the MTA guard `Apartment` (`COINIT_MULTITHREADED | COINIT_DISABLE_OLE1DDE`, `CoUninitialize` on drop when the call took a reference, a thread already in another apartment is used as it is); `Com<V>` (one owned reference, `Release` on drop, `QueryInterface` as `cast`, neither `Send` nor `Sync`); `Bstr` and `Variant` (`repr(transparent)`), the only `SysStringLen`, `SysFreeString` and `VariantClear`. `std::env::var_os` is read in exactly one place, that S10 comparison; the environment is never a path source.
- **`sys::win::firewall`** binds read-only: the `INetFwPolicy2` prefix up to `get_Rules` (slot 18), `INetFwRules` up to `get__NewEnum` (slot 11), every getter of `INetFwRule` (7 to 41), `INetFwRule2::get_EdgeTraversalOptions` (43), the getters of `INetFwRule3` (45 to 55) and `IEnumVARIANT::Next` (3). Setter slots are untyped placeholders, so the read side cannot write. Slots and IIDs are pinned against `netfw.h`/`oaidl.h` of SDK 10.0.26100 by tests; the `NET_FW_*` values `sys::firewall` uses are pinned against `windows-sys`. The getters go through three macros that take a vtable field of the object they are called on, one `unsafe` call each. About 590 lines of binding code without tests and comments (`com` about 220, `firewall` about 370): below the ADR 0023 §13 threshold of about 600 for re-evaluating `windows`.
- **S10, measured on build 26300** (`sys::win::tests::firewall::com_and_the_process_environment`): `InprocServer32` of `HNetCfg.FwPolicy2` is a `REG_SZ` `C:\Windows\System32\FirewallAPI.dll`, not the `REG_EXPAND_SZ` `%SystemRoot%\…` A4 assumed; a child process whose own `SystemRoot` and `windir` name an empty decoy folder still activates the class and loads `FirewallAPI.dll` from System32. The check stays (another build or class may register `%SystemRoot%`, and the elevated helper's environment comes from the user-writable `HKCU\Environment`); in that child `create_inproc` refuses before any activation.
- **Bans** (`clippy.toml`, `sys/win/bans.rs`): `CoCreateInstance` only in `com::activate`; `CoInitializeEx` gains its third reviewed call site (`com::Apartment`, next to `elevation` and the shim); new bans `SysFreeString`, `SysStringLen` (only `com::Bstr`) and `VariantClear` (only `com::Variant`).
- **Features** of the existing `windows-sys` (no new crate): `Win32_NetworkManagement_WindowsFirewall` (the `NetFwPolicy2` CLSID and the `NET_FW_*` constants), `Win32_System_Variant` (`VARIANT`, `VariantClear`, `VT_*`) and `Win32_System_Ole` (which `VARIANT` requires; it was a dev feature, now a normal one).
- **Imports:** `CLI_IMPORTS` grows by `oleaut32.dll` (`SysStringLen`, `SysFreeString`, `VariantClear`; a KnownDLL); `ole32.dll` now also serves `CoCreateInstance`. Outcome A of ADR 0023 §8 (measured, docs/09) makes the firewall read part of every `WinSystem`, so the CLI links it now rather than in P4-2c. `HELPER_IMPORTS` is unchanged until the helper builds its `System` (P4-2c).

## Re-evaluation of the `windows` crate (before P4-5b) — decided 2026-11-09
ADR 0023 §13 sets a threshold of about 600 lines for the hand-written firewall binding; P4-5a ends at about 590 (without tests and comments), and the write side of P4-5b will pass it. Nothing is switched before the lead decides.
- **Hand-written, extended (the P4-5b estimate):** the setters Rerun's one rule form needs (`put_Name`, `put_Description`, `put_ApplicationName`, `put_Grouping`, `put_Direction`, `put_Action`, `put_Profiles`, `put_Protocol`, `put_Enabled`: today untyped placeholders, so typing them changes no slot), `INetFwRules::Add` and `Remove`, a `BSTR` allocation guard (`SysAllocStringLen`, one more ban with one call site), `CoCreateInstance` of `NetFwRule` (already on the allowlist). Three setter macros like the getter macros. Estimate: 150 to 200 more lines, about 750 to 800 in total; the slot and IID tests and the [SB] write contract cover them as they cover the read side. No new crate, no change to `HELPER_IMPORTS` beyond what the read side brings (`ole32`, `oleaut32`, `combase`).
- **`windows` 0.62 (Microsoft, MIT OR Apache-2.0, maintained, frequent releases with breaking changes):** generated, reviewed bindings for every `netfw.h` interface and RAII types for `BSTR`/`VARIANT`; about nine crates (`windows`, `windows-core`, `windows-result`, `windows-strings`, `windows-link` and others) plus the build-time proc-macro crates `windows-implement` and `windows-interface` with `syn`, `quote`, `proc-macro2`. It would enter the elevated helper's dependency tree (audits A5, A6: every crate is supply chain of the elevated binary), its build time is not measured here (proc macros with `syn` add a cold-build cost), and DXGI would stay hand-written (the `windows` `CreateDXGIFactory1` is a static import of `dxgi.dll`, which the hardening forbids; amendment 2026-11-05), so two binding styles would coexist.
- **Recommendation:** keep the hand-written binding and raise the firewall threshold to about 800 lines for the write side of P4-5b; reconsider `windows` only if a third COM area is added (phase 6 or later). **Decided 2026-11-09 (lead): keep the hand-written binding, threshold about 800 lines for the firewall binding; no new dependency.**
